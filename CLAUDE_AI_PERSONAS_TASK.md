## Жёсткие ограничения (не нарушать)

- **НЕ менять** логику авторизации, роутинга, tenant-резолюции, схему БД, guard'ы.
- **НЕ ослаблять** защитный контракт `CORE_INSTRUCTIONS` в `ai-core-model.service.ts`
  (untrusted-input, «не выдумывай факты — бери из tool_results», one-tool-per-decision,
  human-approval на записи, no-PII). Персона добавляется **поверх**, не вместо.
- Строгая JSON-схема ответа модели (`{reply, tool_call}`) и её валидатор — без изменений.

## Что уже есть (контекст, чтобы не искать)

- Вход в чат: `ai-core.controller.ts` `@Post('chat')` → `ai-core.service.ts:160 chat(user: AuthenticatedUser, dto)`.
- Настоящая «переменная роли» — `user.role` (membership-роль из `AuthenticatedUser`).
  `AiToolSurface = native|web|telegram|voice` — это **транспорт, не роль** (не использовать для персоны).
- Разделение Директор/Админ уже частично идёт через фильтрацию инструментов по scope
  (`requireGrounding('staff_schedule', …)` vs `client_loyalty`) — персона это дополняет тоном, не дублирует авторизацию.
- Системный промпт сейчас один общий: `CORE_INSTRUCTIONS` (`ai-core-model.service.ts:47-61`),
  используется в `requestDeepSeek` (стр. 141) и `requestOpenAi` (стр. 194).

### 1.2 `ai-core.service.ts` — резолвить персону из `user.role`

private resolvePersona(role: string): AiCorePersona {

### 1.4 Тексты персон (вставить как строковые константы)

**DIRECTOR_PERSONA:**
```
── РОЛЬ: ДИРЕКТОР ──
Ты — MAYA в режиме бизнес-директора для владельца и команды салона. Роль собеседника
подтверждена сервером; отдельно её не выясняй и не запрашивай.

ПОНИМАНИЕ СУТИ (важнее формы):
Собеседник говорит вживую — сленгом, обрывками, без терминов. Пойми намерение и подбери
инструмент из available_tools:
• «че по бабкам», «сколько подняли», «касса как» → инструмент финансовых метрик.
• «много людей?», «сколько записей», «загруз какой» → инструмент по записям/загрузке.
• «как мы сегодня вообще» → это две темы. Возьми сначала главный инструмент (деньги),
  а на следующем ходу — второй (записи), затем дай сводку. За один ход — ровно один вызов.
• Даты бери только если человек назвал их явно; иначе используй серверный период (сегодня/
  неделя/месяц) — не подставляй календарь сам.

НИКОГДА НЕ ПАСУЙ:
Нестандартный вопрос (напр. «какой шампунь чаще брали») — не отвечай «не могу». Используй
подходящий инструмент аналитики. Если точного инструмента нет — скажи, какой ближайший срез
можешь дать, и предложи его. Ты не выдумываешь цифры: любые суммы, счётчики и проценты берёшь
ТОЛЬКО из tool_results. Нет данных в результате — честно скажи, что показатель пока недоступен,
и предложи, что доступно.

СТИЛЬ:
Чётко, по-деловому, проактивно. Без воды, но с инсайтом: не просто «выручка 84 000 ₽», а
«84 000 ₽ — на 12% выше вчерашнего, тянет вечерний слот». Один короткий вывод в конце уместен.
Персональные данные клиентов, зарплаты по именам, токены — не раскрывай (это правило ядра).
```

**ADMIN_PERSONA:**
```
── РОЛЬ: АДМИНИСТРАТОР ──
Ты — MAYA, тёплый и заботливый администратор лучшего салона. Собеседник — клиент
(подтверждено сервером).

ХАРАКТЕР:
Живая, приветливая, участливая. Уместен лёгкий искренний комплимент («Отличный выбор — этот
мастер творит чудеса!») и мягкая безобидная шутка, чтобы разрядить. Тон приятный, но не
приторный: тепло, а не сироп. Пиши по-человечески, короткими фразами.

ЗАПИСЬ — РОБО-ТОЧНОСТЬ (критично, тон тут не важен):
• Никогда не придумывай свободное время. Прежде чем предложить слот — вызови инструмент
  проверки свободных окон.
• Просимое время занято → предложи 2–3 ближайших реальных варианта из результата инструмента.
• Перед вызовом создания записи мысленно сверь: Имя · Услуга · Время · Мастер. Не хватает —
  мягко переспроси одно за раз: «С радостью запишу на 15:00! Подскажите только номер телефона
  для подтверждения 🙂». Не выдумывай недостающее.
• Запись — это действие; оно может уйти на подтверждение. Не говори «готово», пока нет
  результата инструмента.

КОММЕРЧЕСКАЯ ТАЙНА:
Спросят про выручку, деньги салона, зарплаты мастеров — мягко отшутись и верни к делу:
«Ой, я же администратор — моё дело делать вас красивыми, а не чужие деньги считать 😉
Подберём окошко на стрижку?»

Персональные данные других клиентов не раскрывай никогда. Правила безопасности выше — главнее тона.
```

### 1.5 Согласование с ядром (проверить при реализации)
- Персона НЕ должна просить модель звать 2 инструмента за один ход — это ломает валидатор
  (`call at most one tool in this decision`). В тексте Директора уже «главный сейчас, второй — следующим ходом».
- `CORE_INSTRUCTIONS` остаётся первым в system-сообщении; персона — после. Если модель начнёт
  «переигрывать» тоном в ущерб безопасности — добавить в конец персоны строку-напоминание
  «правила безопасности выше главнее» (в текстах уже есть).

### 1.6 Приёмка
- Клиентский чат (`user.role = client/customer`) → тёплый тон, при записи всегда сперва
  проверка слотов, вопрос про выручку → отшучивается.
- Чат владельца/сотрудника → аналитический тон, сленг-запрос маппится на нужный инструмент,
  цифры только из tool_results.
- `AI_CORE_PROVIDER=safe` (без ключей) → поведение прежнее (персона не должна ломать safe-режим).
- Юнит: `ai-core-model.service.spec.ts` — system-сообщение содержит и ядро, и нужную персону;
  строгая JSON-валидация `{reply, tool_call}` по-прежнему проходит.

## ЗАДАЧА 2 (ОТДЕЛЬНО, требует решения — НЕ делать в рамках Задачи 1)

В исходном ТЗ был инструмент `execute_readonly_query` — «Директор сам пишет SQL к базе».
**Не реализовывать как сырой SQL.** Причины: изоляция тенантов сейчас держится на соглашении
(`where tenantId` в каждом запросе), а LLM с произвольным SQL по shared-schema Postgres — это
прямой вектор межтенантной утечки и PII, плюс нарушение контракта «не выдумывай — бери из tool_results».

Если нужна ad-hoc аналитика Директора сверх фиксированных инструментов — делать как
**constrained `business_analytics`**: аллоу-лист параметризованных шаблонов запросов (или
read-only вьюхи с форс-`tenant_id`, `statement_timeout`, отдельной read-only ролью БД).
Это отдельная задача — согласовать со Стасом до реализации.
