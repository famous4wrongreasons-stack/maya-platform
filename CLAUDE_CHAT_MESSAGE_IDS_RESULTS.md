# MAYA Chat Message IDs — handoff для Claude

Статус: backend готов и развёрнут на production legacy-backend «Мужской Эстетики».

Backend commit: `f0059669` (`feat(chat): persist stable message ids`)

## Что теперь гарантирует backend

- Каждое сохранённое сообщение получает постоянный непрозрачный ID формата
  `msg_<32 hex>`. Не разбирай его и не преобразуй в число.
- Старая история без ID мигрирует автоматически при первом `chat_history`,
  `chat`, `chat_stream`, `chat_delete` или при записи проактивного сообщения.
- `chat_history.messages[].id` теперь постоянный и не меняется после удаления
  соседних сообщений или обрезки истории.
- Обычный JSON-ответ `chat` содержит:
  - `message_id` — ID ответа MAYA;
  - `id` — совместимый alias того же ID ответа MAYA;
  - `user_message_id` — ID пользовательского сообщения этого хода.
- Финальное SSE-событие `chat_stream` с `type: "done"` содержит те же три поля.
- `chat_delete` сначала удаляет точное сообщение по постоянному `message_id`.
  Если ID отсутствует либо не найден, backend удаляет самое свежее совпадение
  по `role + text`. Старые числовые ID временно поддерживаются.
- Ответ `chat_delete` возвращает `deleted_id` и обновлённый авторитетный
  `messages[]`.

## Что нужно сделать во frontend

1. После ответа `chat` или SSE `done` заменить временный ID оптимистичного
   пользовательского пузыря на `user_message_id`.
2. Присвоить пузырю MAYA `message_id` (либо `id`, они равны).
3. При удалении отправлять этот строковый ID как `message_id`; `role` и `text`
   продолжать отправлять как fallback.
4. После успешного удаления принять возвращённый `messages[]` как источник
   истины. Device-local tombstones можно оставить на один релиз как страховку,
   но после следующей полной загрузки истории они больше не нужны.
5. Проверить два сценария: удаление одного из двух одинаковых сообщений и
   удаление на одном устройстве с последующей загрузкой истории на другом.
