## A. Что является подтверждённой выручкой — с поправкой

### Формулировка Phase A

> «только кассовые операции из `transactions/{company}`, и только при
> `status === 'available' && verified === true`»

### Что на самом деле

Маршрут подтверждён: деньги читаются **только** из `transactions/{company_id}`
(`yclients-crm.adapter.ts:2257`), и все три финансовых метода зовут одну функцию.
Гейт `available && verified` существует, но живёт **не в адаптере**, а ниже —
в аналитике (`operations-analytics.service.ts:1498-1503`), и только после него
ставится `source: 'crm_financial_transactions'`.

🔴 **Но слово «подтверждение» означает не то, что кажется.**

```ts
interface YclientsFinanceTransactionApiItem {
  id?, amount?, sold_item_type?, record_id?, master_id?, staff_id?, master?, staff?, account?
}
```
`yclients-crm.adapter.ts:187-201`

**Поля подтверждения, статуса или удаления в модели транзакции НЕТ.** Запрос
тоже ничего не фильтрует — только `start_date`, `end_date`, `count`, `page`
(`:2250-2255`). А флаг ставится безусловно:

```ts
return { status: 'available', verified: true, ... }
```
`yclients-crm.adapter.ts:2403-2405`

**Точное определение:** подтверждённая выручка Maya = сумма **положительных**
операций с **непустым** `sold_item_type`, вернувшихся из эндпоинта кассовых
операций, при условии что запрос не упал и каждая сумма распарсилась.
«Подтверждённость» — свойство **источника и успешности чтения**, а не признак
у отдельной операции.

Следствие: константа
`CONFIRMED_REVENUE_UNAVAILABLE.crmUnverified = 'crm_returned_cash_revenue_without_confirmation'`
(`operations-analytics.service.ts:206`) описывает состояние, которого **не
существует** — пары `available + verified:false` не производит ни одна ветка.

## B. Где цена записи ошибочно называется выручкой

Подтверждено дословно. В обзоре `revenue` — это сумма `totalPriceKopecks`, а в
CRM-режиме она берётся из журнала:

```ts
totalPriceKopecks: appointment.total_price === null ? null
  : Math.round(appointment.total_price * 100),
```
`operations-analytics.service.ts:1028`

То есть **стоимость записанного, а не пробитая касса** — и в режиме внутреннего
календаря, и в режиме CRM.

### 🔴 Поправка, которая делает находку хуже

Словарь правды в системе **уже есть**:

```
'profit_is_calculated_only_from_till_confirmed_cash_and_a_complete_expense_ledger_never_from_booked_prices'
```
`operations-analytics.service.ts:230`

Но он навешен на `net`, а не на `revenue`. У самого `revenue` нет ни `status`,
ни `verified`, ни `basis`.

**И для внутреннего календаря пометки снимаются намеренно:**

```ts
if (overview.data_source !== 'maya') return overview;
// иначе — удалить 'net_status' | 'net_unavailable_reason'
```
`operations-analytics.service.ts:377-384`

То есть в самом уязвимом режиме — где касса не существует в принципе — ответ
остаётся **вообще без машиночитаемой пометки**.

## C. Расхождение AI и HTTP — подтверждено и шире, чем «поле revenue»

| Понятие | HTTP | AI |
|---|---|---|
| Выручка | цены журнала как есть | в CRM-режиме гасит в `[]` и подставляет кассу |
| Средний чек | цены журнала ÷ записи | от подтверждённой кассы |
| Прибыль | `net` из цен журнала | отказ с причиной |
| Зарплата | `/analytics/me` не запрашивает вовсе | отдаёт мастеру его расчёт из CRM |
| Нет данных | молчание или ноль | причина строкой |

### 🔴 Но правило «AI честнее» **не универсально**

```ts
private businessOperationalAnalyticsVerified(value: unknown): boolean {
  const data = this.record(value);
  return data.data_source === 'maya' || data.data_source === 'crm';
}
```
`ai-tool-handler.service.ts:3503-3506`

**AI-инструмент помечает операционный обзор как `verified` в ОБОИХ режимах** —
включая тот, где числа суть цены журнала. Здесь AI не честнее HTTP, а хуже:
HTTP хотя бы не называет это подтверждённым.

Второе место инверсии: `safeAnalytics` строит новый литерал и **не переносит**
`net_status` / `net_unavailable_reason` — AI-инструмент отдаёт `net` без
причины его недоступности.

## D. Возвраты и отрицательные операции

Подтверждено, с тремя уточнениями.

**Отсев не один, а два и в двух методах:**

```ts
const type = String(transaction.sold_item_type || '').trim();
if (!type) continue;                       // ← пустой тип товара
const amountKopecks = this.requireMoneyKopecks(transaction.amount);
if (amountKopecks <= 0) continue;          // ← возвраты и нули
```
`yclients-crm.adapter.ts:2333-2340` и то же в `:1926` (`getAppointmentRevenue`).

Знак до этого сохраняется (`requireMoneyKopecks` — просто `Math.round(x*100)`),
то есть возврат доезжает целым и выбрасывается **голым `continue`** — без
счётчика, лога и пометки в `warnings`.

Понятия возврата в системе нет вовсе: все совпадения на «возврат» относятся к
возврату **клиентов**, не денег.

### 🔴 Прямое следствие для прибыли

```ts
const amount = revenue.total.amount_kopecks - expenseTotal;
```
`operations-analytics.service.ts:1804`

А двумя строками выше стоит принцип:

> «Отбросить чужую валюту значило бы занизить расходы и завысить прибыль —
> именно в ту сторону, в которую ошибаться нельзя.»

Возврат не гасит выручку и не попадает в расходы, **то есть завышает прибыль
ровно в ту сторону, которую код сам объявил недопустимой.** Принцип
сформулирован и нарушен тихим фильтром через два файла.

## E. Что YCLIENTS реально предоставляет

Адаптер вызывает **16 эндпоинтов**:

```
companies · company/{id} · company/{id}/staff · staff/{id} · book_staff/{id}
company/{id}/staff/schedule · schedule/… · book_times/…
records/{id} · record/{id}/{recId} · company/{id}/clients/search
book_services/{id} · services/{id} · service_categories/{id}
loyalty/client_cards/{clientId}
transactions/{id}                          ← единственный источник денег
company/{id}/salary/calculation/staff/{id} ← зарплата
```

**Фискального контура нет вовсе:** ни документов, ни ККМ, ни касс, ни чеков, ни
кассовых смен. Подтверждено полным перебором путей.

Пагинация транзакций: `count=200`, до 40 страниц; на 40-й — исключение «exceeds
the safe page limit». Годовой отчёт до этого места не доходит: `CrmService`
отбивает диапазон длиннее 31 дня раньше адаптера (`crm.service.ts:1582`,
`crm_finance_range_too_large`). То есть версия Phase A про «нехватку прав на
годовом отчёте» **неточна** — до сообщения о правах дело не доходит.

## F. Что в `CrmFinancialSummary` уже правильно — и это НЕ трогать

| Хорошо сделано | Где |
|---|---|
| Недоступность выражена **null-ссылкой**, а не нулём суммы | `unavailableRevenue()` `:2679-2697` |
| Трёхзначный `CrmFinanceStatus` `available\|partial\|unavailable` | `:262` |
| `coverage_percent` и `unattributed_*` — доля и остаток нераспределённого | `:354-361` |
| `warnings[]` с машинными кодами | `:371-374` |
| `verified` отдельно у выручки и у зарплаты, конверт — их конъюнкция | `:1820` |
| `CrmAppointmentRevenueSnapshot.verified: true` литералом — отказаться нельзя by design | `crm-adapter.interface.ts:172` |

**Точная оценка:** правильный здесь — **каркас неполноты**. Он честно
описывает, ЧЕГО МЫ НЕ ЗНАЕМ. Чего он не описывает — **что мы сознательно
выбросили**: возвраты, нулевые операции и строки без типа товара исчезают, не
оставляя следа ни в `warnings`, ни в счётчиках.

## G. План P4

### P4.0 — назвать вещи своими именами (без изменения чисел)

Ввести в домен `RevenueBasis`:

```
'till_confirmed'   — касса из кассовых операций провайдера
'booked_prices'    — стоимость записанного, не деньги
'unavailable'      — не знаем, с причиной
```

Обзор начинает отдавать `revenue_basis` рядом с `revenue`. **Числа не меняются**,
поле аддитивно. Это снимает главную ложь: одно и то же слово перестаёт значить
две разные вещи.

### P4.1 — выброшенное перестаёт быть невидимым

`aggregateRevenue` считает то, что отбросил, и кладёт в `warnings`:
`discarded_negative_count`, `discarded_zero_count`, `discarded_untyped_count`.
**Суммы не меняются** — меняется только то, что владелец видит их существование.

Это же закрывает прибыль: при непустом `discarded_negative_count` прибыль обязана
отказать с причиной, а не завышаться молча.

### P4.2 — убрать инверсию честности

`businessOperationalAnalyticsVerified` перестаёт называть цены журнала
подтверждёнными. `safeAnalytics` переносит `net_status` и `net_unavailable_reason`.
`withLegacyNet` перестаёт удалять пометки — либо, если legacy-контракт это
требует, удаляет их **только** для явно перечисленных потребителей.

### P4.3 — исправить мёртвые причины

`crmUnverified` описывает несуществующее состояние. Либо убрать, либо сделать
достижимой — если решим отличать «касса неполна» от «кассы нет».

### Чего в P4 НЕ делаем

- Не строим свою книгу кассы и не дублируем деньги CRM.
- Не трогаем `CrmFinancialSummary` — каркас неполноты хороший.
- Не меняем существующие числа ни в одном поле.
- Не трогаем главу 3 (события) и владение лояльностью.
- Не строим слои Prediction / Opportunity / Action.

### Порядок и риск

| Пакет | Меняет числа | Меняет провод | Риск |
|---|---|---|---|
| P4.0 | нет | аддитивно | низкий |
| P4.1 | нет | аддитивно (`warnings`) | низкий |
| P4.2 | нет | **да** — `verified` перестаёт врать | средний, нужен ваш выбор |
| P4.3 | нет | нет | низкий |

P4.2 — единственный, где ответ системы изменится по существу: инструмент
перестанет утверждать, что цены журнала подтверждены. Считаю это исправлением
лжи, но выношу отдельным решением.

## Поправка к формулировке Phase A

Phase A писала «только при `status === 'available' && verified === true`», и эта
формулировка перешла в ваше одобрение цикла. Она описывает механику верно, но
задаёт неверное ожидание: звучит как фильтр по признаку подтверждения от CRM,
тогда как такого признака у провайдера нет. Считаю нужным зафиксировать это
здесь, чтобы дальше не строить на нём выводов.
