## 1. Кто сейчас источник истины

**Реестр легаси-бота.** Не YCLIENTS и не Maya.

```sql
CREATE TABLE IF NOT EXISTS loyalty_transactions (
  id, client_id, type, points, visit_record_id, note, at
);
```
`ai администратор/database.py:246`

```python
def loyalty_balance(client_id: int) -> int:
    "SELECT COALESCE(SUM(points), 0) AS bal FROM loyalty_transactions WHERE client_id = ?"
```
`database.py:3432-3439`

Баланс **вычисляется**, а не хранится. Это настоящий журнал, а не число.

### Ключевой инвариант, объясняющий всё остальное

```sql
CREATE UNIQUE INDEX idx_loyalty_tx_yc_import_unique
  ON loyalty_transactions (client_id, type) WHERE type = 'yc_import';
```

Остаток карты YCLIENTS импортируется **ровно один раз**, как стартовая
проводка. Дальше журнал бота живёт сам. **YCLIENTS — историческое зерно, а не
владелец.**

Типы операций: `earn`, `redeem`, `backfill`, `yc_import`. Кэшбэк — 5 %
(`loyalty.py:44`).

## 2. Что хранит SQLite бота

| Таблица | Что |
|---|---|
| `loyalty_transactions` | журнал; баланс = `SUM(points)` |
| `loyalty_redeem_codes` | одноразовые коды списания: `code`, `points`, `expires_at`, `used_at`, `used_by_admin_id` |

Три уникальных индекса держат идемпотентность: начисление один раз за визит,
приветственный бонус один раз на клиента, импорт YCLIENTS один раз.

Списание — **двухшаговое и с участием человека**: бот выдаёт код, администратор
его гасит (`consume_redeem_code`, `loyalty.py:919`).

## 3. Что реально умеет YCLIENTS

Единственная точка: `loyalty/client_cards/{clientId}` — **чтение**
(`yclients.py:1639`). Метода списания баллов у карты интеграция не использует.

### 🔴 Списание НЕ уменьшает карту YCLIENTS

```python
# 2) Пометка в YClients — обнуляем cost + дописываем comment. Если
# не получится (сетевая ошибка) — не откатываем списание; админ
# увидит баллы в нашем боте, а в YClients поправит руками.
```
`loyalty.py:647-650`

Списание оформляется **обнулением стоимости услуги и комментарием**. Баланс
карты в YCLIENTS остаётся прежним. Значит две величины расходятся **по
построению** — это свойство конструкции, а не сбой синхронизации.

## 4. Где Maya читает баланс

`getForUser` → две ветки по источнику календаря
(`loyalty.service.ts:37-68`):

| Календарь | Источник |
|---|---|
| внутренний | собственный `LoyaltyAccount` Maya, `authoritative: 'maya'` |
| внешний | `getExternalAccount` — приоритет ниже |

Приоритет для внешнего (`:288-330`):

1. **мост к боту** — первым, до CRM;
2. CRM `getClientLoyalty` по телефону;
3. кэш `LoyaltyAccount` со `stale: true` и причиной;
4. пусто с причиной.

---

### 🔴 Три обхода сервиса лояльности

Приоритет из §4 действует только для тех, кто идёт через `LoyaltyService`.
Три места ходят мимо:

| Место | Что делает | Чего лишается |
|---|---|---|
| `customers.service.ts:117-139` | читает `loyaltyAccounts[0]` **прямо из таблицы**, отдаёт `loyalty_balance` и `loyalty_source` | нет `stale`, нет `sync_status`, нет `authoritative` |
| `customers.service.ts:176` | то же во втором методе | то же |
| `ai-tool-handler.service.ts:592` | зовёт `crmService.getClientLoyalty` **напрямую** | минует и мост, и кэш |

**Живое следствие третьего:** для боевого салона авторитетен журнал бота, а
AI-досье клиента показывает баланс **карты YCLIENTS**. Один человек, две
поверхности Maya, **два разных числа** — и ни одна не помечена как расходящаяся.

Первые два: список клиентов владельца показывает кэшированное число как
текущее, хотя словарь честности лежит в соседнем файле.

## 6. Какие операции доходят до авторитетного источника

| Операция | Доходит? |
|---|---|
| Чтение баланса через мост | **да** — сумма журнала бота |
| `adjust` при внутреннем календаре | **да** — Maya и есть владелец в этом режиме |
| `adjust` при внешней CRM | **нет** — отбивается 409 |
| `spend_options` | **ничего не меняет** — это витрина |
| Списание баллов | **не проходит через Maya вообще** — только бот и админ |

**У Maya нет ни одного пути, который менял бы баланс бота.** Это хорошо и
соответствует вашему принципу.

## 8. Что делают три моста

| Направление | Что несёт | Защита |
|---|---|---|
| Maya → бот | `/api/internal/loyalty-snapshot`: `{found, balance}` | только loopback, токен ≥32, белый список слагов |
| бот → Maya | карточки инбокса | платформенный токен |
| бот → Maya | точки касания Recovery | тот же токен |

Обратные мосты **не несут уникальной способности**: `publishForTenant` и
`recordConsentSafeTouchpoint` у Maya уже есть. Они существуют по одной причине:
**приёмника вебхуков YCLIENTS в NestJS нет ни одного.**

### Боевое состояние — мост включён

| | |
|---|---|
| `MAYA_LEGACY_BRIDGE_TOKEN` | задан, 64 символа |
| `MAYA_LEGACY_LOYALTY_TENANT_SLUGS` | `muzhskaya-estetika-3` |
| `LoyaltyAccount` | **1 строка, source = `legacy_maya`** |
| `LoyaltyTransaction` | **0** |

То есть единственный известный Maya баланс пришёл из бота, а собственный реестр
Maya **пуст**.

## 9. Что можно спрятать за канонической границей уже сейчас

### 🔴 Главная находка: словарь на два значения при трёх источниках

```ts
authoritative: 'crm' | 'maya'
```
`loyalty.service.ts:651`

Баланс из журнала бота помечается `'maya'` — **потому что третьего значения
нет**. Это тот же класс дефекта, что `revenue` в P4: честный каркас
(`authoritative`, `sync_status`, `stale`) есть, но применён неточно.

**Практическое следствие, а не вкусовщина:**

```ts
verification_required: loyalty.authoritative === 'crm'
```
`loyalty.service.ts:563`

Для баланса бота `verification_required` = **false**. Maya говорит клиенту
«эти баллы можно тратить, подтверждение не нужно», опираясь на кэш чужого
журнала. В проде это ровно тот единственный аккаунт, который есть.

### Предлагаемый P5.0 — назвать владельца

Ввести в домен `LoyaltyAuthority`:

```
'crm'         — карта провайдера
'legacy_bot'  — журнал старого бота (сегодня прячется под 'maya')
'maya'        — собственный реестр Maya (внутренний календарь)
```

Домен Maya перестаёт знать, что данные приходят «из старого бота через
localhost»: он видит только `authority` и `sync_status`. Реализация моста
остаётся за границей.

**Ничего не переносим, dual-write не вводим, мосты не удаляем.**

### P5.1 — `verification_required` от владельца, а не от одного значения

Подтверждение требуется всегда, когда владелец **не** `maya`. Для боевого
салона это меняет ответ с «тратить можно сразу» на «нужно подтверждение» —
изменение поведения, выношу отдельным решением.

### P5.2 — граница становится единственным входом

Три обхода (§4) сводятся к `LoyaltyService`, чтобы `authority`, `sync_status` и
`stale` доезжали до **каждой** поверхности. Иначе канонической границы нет:
она есть у одного потребителя из четырёх.

Самое ценное здесь — AI-досье: сегодня оно показывает карту YCLIENTS там, где
авторитетен журнал бота, то есть два разных числа про одного человека.

### P5.3 — дрейф перестаёт быть невидимым

Когда мост ответил, а карта YCLIENTS тоже доступна и числа разошлись — записать
предупреждение с обоими значениями. **Не выбирать победителя**, не чинить: D1
неустраним по построению.

Отдельно учесть известную неустойчивость провайдера: YCLIENTS иногда отдаёт
**пустой список карт с кодом успеха**, и адаптер уже переспрашивает до трёх раз
(`yclients-crm.adapter.ts:2016-2023`). Пустой ответ — не доказательство нуля.

## Поправка к формулировке Phase A

Формулировка «баланс — сумма, отдельной таблицы балансов нет» верна, но
недоговаривает главного: у бота **есть идемпотентность на уровне схемы** — три
уникальных индекса, включая одноразовый импорт YCLIENTS. Это не наспех
сделанный кэш, а корректный журнал. Отсюда и вывод: владельцем в главе 2 должен
остаться он.
