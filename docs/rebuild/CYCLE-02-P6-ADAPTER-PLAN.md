## 1. Три заглушки

`dikidi`, `salon-online`, `whitelines` — по **104 строки** каждая. Различаются
только именем провайдера в тексте ошибки: после нормализации имён их тела
остаются структурно одинаковыми.

Из девяти обязательных методов контракта:

| Поведение | Методов |
|---|---|
| `Promise.reject('… scaffolded but not implemented yet')` | **7** |
| `Promise.resolve({ ok: false, … })` — честный отказ | 1 (`testConnection`) |
| 🔴 `Promise.resolve([])` — **ложь** | **1** (`getClientAppointments`) |

Ровно один метод из девяти утверждает «данных нет» там, где верно
«не поддерживаю».

## 2. Какие провайдеры поддерживаются на самом деле

| Провайдер | Статус | `connectable` | `productionReady` | Реальность |
|---|---|---|---|---|
| YCLIENTS | ready | да | **да** | боевой |
| ALTEGIO | ready | да | нет | тот же адаптер, другой `baseUrl` |
| MOCK | development_only | да | нет | для разработки |
| DIKIDI | planned | **нет** | нет | каркас |
| WHITELINES | planned | **нет** | нет | каркас |
| SALON_ONLINE | planned | **нет** | нет | каркас |

**В боевой базе существует ровно одна интеграция: `yclients / active`.**

### Достижимы ли заглушки

`connectable: false` — **безусловный** гейт (`assertProviderConnectable`), а не
только производственный. Он стоит и на подключении
(`createOrUpdateIntegration:207`), и на чтении адаптера арендатора
(`getAdapterForTenant:1783`).

Три остальных вызова фабрики (`recheckIntegration`, `synchronizeCrmTeamAccess`,
`loadConnectionPreview`) работают от **уже сохранённой** интеграции, а строку с
непроверяемым провайдером через API создать нельзя.

**Вывод: заглушки недостижимы ни в одном окружении через API.**

## 3. Обязательные и опциональные возможности

**Обязательных методов девять:** `getServices`, `getStaff`, `getAvailableSlots`,
`createAppointment`, `cancelAppointment`, `rescheduleAppointment`,
`getClientAppointments`, `getClientLoyalty`, `testConnection`.

Всё остальное опционально (`?`): журнал, операции над визитом, финансы,
реестр клиентов, расписание мастера, профиль компании.

### 🔴 Асимметрия, которую стоит назвать

Опциональные методы имеют **честный механизм отказа**: провайдер их просто не
объявляет, а `CrmService` отвечает понятным кодом
(`crm_journal_not_supported`, `crm_finance_not_supported`, …).

У обязательных такого механизма **нет вовсе**. Провайдер, который чего-то не
умеет, обязан либо бросить произвольную ошибку, либо соврать. Отсюда и `[]`.

## 5. Кто примет «не поддерживается» за «данных нет»

Единственный потребитель — `appointments.service.ts:412-416`:

```ts
const remoteAppointments = await this.crmService.getClientAppointments(...);
await this.syncExternalClientAppointments(clientId, remoteAppointments);
```

### Оценка ущерба — честно, без преувеличения

`syncExternalClientAppointments` **перебирает** массив и делает upsert. Пустой
массив означает «ничего не добавили», а **не** «удалили существующее». Данные
не теряются: клиент видит свои записи Maya, просто не получает обогащения из
CRM.

То есть дефект реален по форме — «не умею» подано как «пусто» — но его радиус
меньше, чем «потеря данных». Сегодня он к тому же недостижим (§2).

## 6. Mock и его выдуманные поля

`mock-crm.adapter.ts` фабрикует то, чего у него быть не может:

| Строка | Что выдумано |
|---|---|
| `:219, :235, :263` | `raw: { provider, … }` — сырой ответ провайдера, которого нет |
| `:286` | `external_card_id: 'mock-card'` — карта лояльности, которой нет |

**Это не недостаток mock'а — это улика против контракта.** Поля существуют
только потому, что так выглядят ответы YCLIENTS; второй провайдер вынужден их
изобретать. Ровно этот аргумент был в P3: контракт не канонический, а извлечён
из одной реализации.

Часть уже смягчена в P3: `raw` больше не читается в решениях. Оставшееся —
`external_card_id` в обязательном `getClientLoyalty`.

## 7. YCLIENTS и ALTEGIO — один адаптер

Подтверждено дословно (`crm-adapter.factory.ts:36-52`):

```ts
case CrmProvider.YCLIENTS: return new YclientsCRMAdapter({ ...config,
  baseUrl: config.baseUrl || process.env.YCLIENTS_BASE_URL || 'https://api.yclients.com/api/v1' });
case CrmProvider.ALTEGIO:  return new YclientsCRMAdapter({ ...config,
  baseUrl: config.baseUrl || process.env.ALTEGIO_BASE_URL  || 'https://api.alteg.io/api/v1' });
```

Один класс, два адреса. Это **не дефект**: Altegio — тот же API под другим
брендом. Но из этого следует, что «поддержка двух провайдеров» в каталоге
завышает разнообразие: **реализация одна**.

## 8. Каталог и объявления возможностей

Каталог хороший: `implementationStatus`, `connectable`, `productionReady`,
`bookingMode`, `operations`, `limitations`. Публичный
`GET /api/crm/providers` уже фильтрует список по `productionReady` в проде.

### Что в нём неточно

`operations` у трёх заглушек объявлены как `NO_OPERATIONS` — верно. Но у
каталога **нет способа сказать «метод обязателен, а я его не умею»**: он
описывает намерение, а не проверяемую способность. Соответствие каталога и
кода ничем не проверяется.

## План P6

### P6.0 — механизм отказа для обязательных методов

Ввести `CrmUnsupportedCapabilityError` в границе CRM: типизированный отказ,
который `CrmService` превращает в понятный код, как уже делает для
опциональных (`crm_*_not_supported`).

Сегодня у обязательного метода выбор только между произвольной ошибкой и ложью —
именно поэтому появился `[]`.

### P6.1 — убрать единственную ложь

`getClientAppointments` в трёх заглушках возвращает отказ вместо `[]`.

🔴 **Формально это изменение поведения провайдера.** Но провайдеры недостижимы
(§2), в проде их нет, и наблюдаемого эффекта быть не может. Выношу отдельным
пунктом, чтобы вы решили осознанно.

### P6.2 — сократить дублирование заглушек

Общий базовый класс `ScaffoldedCrmAdapter`: три файла по 104 строки становятся
тремя объявлениями по ~10. Поведение не меняется, форма для будущего провайдера
сохраняется.

### P6.3 — барьер соответствия каталога и кода

Тест: у провайдера с `connectable: false` **все** обязательные методы обязаны
отказывать, и ни один не должен возвращать пустой успешный результат.
Это и есть механизм, не дающий лжи вернуться.

### Чего P6 НЕ делает

- Не удаляет ни одного адаптера и ни одного провайдера из каталога.
- Не трогает YCLIENTS и ALTEGIO.
- Не меняет публичный `GET /api/crm/providers`.
- Не трогает `external_card_id` в контракте — это часть общей темы «контракт
  извлечён из одной реализации», её место в главе 5.
- Не начинает главу 3.
