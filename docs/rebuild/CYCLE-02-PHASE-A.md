## A. Executive Summary

**Граница адаптера физически существует и держится.** Ни один модуль вне
`src/crm/` не делает HTTP-запросов к провайдеру: единственный выход в сеть —
`request()` в `yclients-crm.adapter.ts:2941`. Весь домен ходит в CRM через
`CrmService`, привязка к арендатору строгая, `assertTenantId` стоит в начале
каждого публичного метода. Это зрелая работа, и её не нужно переделывать.

**Но граница проведена не там, где нужно.** Файл
`src/crm/crm-adapter.interface.ts` (542 строки) — это одновременно контракт
адаптера **и словарь домена**: его типы импортируют 10 модулей вне `src/crm`,
включая `internal-calendar`, у которого CRM нет вообще. Отдельного канонического
слоя не существует — есть контракт адаптера, который все притворяются
каноническим.

**Зависимость направлена обратно целевой.** Собственный календарь Maya приводит
СВОИ данные к форме CRM: `serializeService` отдаёт `duration_minutes` и
`category: 'Услуги'`, `serializeProvider` — `avatar_url` и `rating: null`
(`internal-calendar.service.ts:939, 966`). Не CRM приспосабливается к Maya, а
Maya к CRM — даже там, где никакой CRM нет.

**Пять адаптеров — это один.** `YclientsCRMAdapter` (3272 строки) обслуживает и
YCLIENTS, и ALTEGIO (различаются базовым URL). `MockCRMAdapter` синтетический.
DIKIDI, Whitelines, Salon Online — три побайтово одинаковые заглушки по 104
строки, недостижимые из-за `connectable: false`. Из 27 методов контракта 18
объявлены опциональными и реализованы **только** YClients-адаптером — то есть
аналитика, AI-инструменты, журнал, напоминания, Maya Recovered и маркетинговые
аудитории работают исключительно на YCLIENTS.

**Главная находка: у Maya нет собственной идентичности клиента.** Внешний
`external_client_id` вычисляется адаптером и **выбрасывается** — пять вхождений
в коде, ни одного потребителя, ни одного поля в схеме. Единственный ключ сверки
— последние десять цифр телефона. Реестр клиентов не хранится нигде: каждый
вопрос об удержании — это полная постраничная выгрузка базы гостей из CRM (до
500 страниц по 200) с кэшем в памяти процесса на пять минут.

**Идентичность мастера — это внешний id CRM.** `staffExternalId` встречается 65
раз в 10 файлах, ключ `CrmStaffAccess @@unique([tenantId, externalStaffId])` не
содержит провайдера. Своей сущности «сотрудник» у Maya нет.

**Денежный контур, наоборот, зрелый и уже канонический.** `CrmMoneyAmount`,
`CrmFinancialSummary` со статусами `available|partial|unavailable`, флагом
`verified` и машинными кодами предупреждений — это правильная модель, и она не
формы CRM. Выручка считается по кассовым операциям, а не по цене визита, а
AI-слой честно гасит «записанные» суммы в CRM-режиме. Переписывать здесь нечего.

**Мостов к старому боту не один, а три, и они разнонаправленные.** Maya → бот
тянет баллы лояльности. Бот → Maya пишет карточки инбокса и точки касания
Recovery. Причина существования обратных мостов проста и не имеет отношения к
лояльности: **приёмника вебхуков YClients в NestJS нет ни одного**, их владелец
— старый Python.

**Общий уровень риска: СРЕДНИЙ.** Ни одной находки CRITICAL. Шесть HIGH, из них
четыре — доказуемые боевые дефекты, не архитектурные претензии.

## C. Data Flow Map

### Клиент
```
YClients  →  адаптер (getClientRegistry, постранично 500×200)
          →  CrmClientRegistrySnapshot (только в памяти запроса)
          →  Map-кэш в процессе на 5 минут
          →  потребители
```
В базу Maya **не попадает ничего**. `external_client_id` вычисляется и
выбрасывается. `CustomerProfile` содержит четыре поля — язык и два согласия
плюс шифрованные заметки; данных CRM в нём нет. Сверка — по телефону.

### Сотрудник
```
YClients  →  адаптер (getTeamMembers)
          →  reconcileCrmTeamAccess
          →  CrmStaffAccess [tenantId, externalStaffId]   ← персистентно
          →  10 модулей
```
Ветка INTERNAL идёт мимо: `InternalProvider`. Выбор ветки продублирован у
каждого потребителя. При пропаже мастера из CRM доступ гасится, членство
приостанавливается, сессии отзываются — это сделано хорошо.

### Услуга
```
YClients  →  адаптер (getServices, price_min ?? price_max ?? 0)
          →  прямо потребителю
```
Владельца записи нет вообще: прайс и длительность читаются из CRM при каждом
обращении. `InternalService` — только для INTERNAL. `TenantCatalogItem` к
услугам отношения не имеет, хотя комментарий в схеме обещает зеркалирование
адаптерами — **ни один адаптер в него не пишет**.

### Визит
```
через Maya:   клиент → CrmService → YClients → строка Appointment (тень)
через журнал: мастер → CrmService → YClients → ✗ в Maya не появляется никогда
из YClients:  вебхук → старый Python → карточка InboxItem → мост → Maya
```
`Appointment` — теневая копия с `crmExternalId`, `staffExternalId`, `serviceIds`
и **сырым ответом провайдера** в `providerPayload`. Ленивый импорт при открытии
«Мои записи» подтягивает визиты по телефону.

### Расписание
Внешний арендатор: график живёт в CRM, правится сквозной записью с
оптимистичной ревизией. HTTP-маршрута нет — единственные вызовы из
AI-инструментов. Внутренний: `InternalAvailabilityRule/Exception`.

### Филиал
```
Branch (cuid Maya, без внешнего id) → адаптер → эхом обратно
все запросы  →  единственный settings.companyId
```
Филиал создаётся один раз при создании арендатора и **никогда не обновляется** —
`branch.update` в коде отсутствует.

### Финансы
```
YClients  →  transactions/{company}          →  aggregateRevenue
          →  salary/calculation/staff/{id}   →  зарплата
          →  loyalty/client_cards/{clientId} →  баллы
```
Чеков, ККМ, документов, кассовых смен Maya не запрашивает вообще. Понятия «чек»
в системе нет.

## F. Canonical Model Proposal

Предложение сознательно **узкое**. Восемь таблиц не создаём.

### Приоритет 1 — то, без чего не встанут главы 6 и 7

**`CrmClientLink`** — недостающее звено идентичности.

| | |
|---|---|
| Назначение | Устойчивая связь клиента Maya с карточкой во внешней CRM |
| Внутренняя идентичность | cuid Maya |
| Владение арендатором | `tenantId`, составной ключ |
| Внешняя идентичность | `provider` + `externalId` |
| Канонические поля | `userId?`, `phoneHash`, `displayName?` (шифрованно) |
| Метаданные провайдера | `firstSeenAt`, `syncedAt`, `sourceUpdatedAt?` |
| Хранение | **персистентно** |
| Владелец записи | CRM |
| Направление | CRM → Maya |
| Свежесть | по обращению, допустимо устаревание сутки |
| Удаление | мягкое: `unlinkedAt`, строка живёт |
| Потребители | лояльность, кампании (гл. 6), атрибуция (гл. 7) |

Обоснование: сегодня клиент опознаётся только телефоном, а карточки-дубли в
YClients — **не гипотеза, а разобранный боевой случай** (комментарий в адаптере
`yclients-crm.adapter.ts:2107`).

**`provider` в `CrmStaffAccess`** — одна колонка, не новая таблица. Сейчас ключ
`[tenantId, externalStaffId]` не различает провайдеров: при смене CRM внешний id
нового провайдера может совпасть со старым и отдать доступ чужому креслу.

### Приоритет 2 — закрепление словаря

**`AppointmentStatus`** как настоящее доменное перечисление из четырёх значений,
которые адаптер уже производит: `confirmed | completed | no_show | canceled`.
Сегодня enum знает два, адаптер выдаёт четыре, нормализаторов пять, а колонка в
базе — свободная строка.

**`AttendanceMark`** — доменные слова вместо `1|0|-1` с переходным алиасом:
мобильное приложение шлёт и читает число.

### Приоритет 3 — не создавать

`Client`, `Employee`, `Service`, `Location` как полноценные таблицы Maya **не
предлагаю**. Прайс и состав услуг живут в CRM и меняются там; хранить их копию
означало бы построить вторую CRM внутри Maya — ровно то, чего запрещает раздел
28. Ссылка + свежесть достаточны.

## G. Identity Strategy

**Образец уже существует в этом же репозитории и он боевой:**
`AuthIdentity @@unique([tenantId, provider, providerUserId])` — внутренний cuid
Maya плюс провайдер плюс внешний id. Изобретать нечего, нужно распространить.

Правило: **внешний id CRM никогда не становится первичной идентичностью Maya.**

| Требование | Решение |
|---|---|
| Уникальность | `@@unique([tenantId, provider, externalId])` |
| Область арендатора | `tenantId` первой колонкой, всегда |
| Область провайдера | `provider` в ключе — иначе смена CRM даёт коллизию |
| Столкновение | нарушение уникальности → конфликт, не молчаливая перезапись |
| Переподключение | та же CRM, тот же id → та же строка |
| Смена CRM | старые связи получают `unlinkedAt`, история Maya сохраняется |
| Несколько провайдеров | ключ уже это допускает |

**Что произойдёт при переходе арендатора с YClients на другую CRM сегодня:**
`CrmIntegration` имеет уникальный ключ по `tenantId` — подключение
перезаписывается **без следа**. `CrmStaffAccess` сохраняет внешние id прежнего
провайдера как боевые ключи доступа. Вся история визитов, привязанная к
`staffExternalId`, указывает в никуда. Это и есть цена отсутствия провайдера в
ключе.

## H. Adapter Contract Proposal

**Единый интерфейс на 27 методов сохранить, разбивать на способности сейчас не
нужно** — потребитель один, и дробление ради эстетики запрещено правилами
цикла. Предлагаю три точечных изменения:

1. **Разделить файл.** Сегодня `crm-adapter.interface.ts` — и контракт адаптера,

   `CrmJournalAppointment`, денежные типы) в `src/crm/canonical/`, оставив в
   контракте адаптера только сигнатуры. Импорты 10 модулей переезжают на
   канонический путь — механически, без изменения поведения.
2. **Типизировать статус** в `CrmJournalAppointment` вместо свободной строки.
3. **Объявить опциональность честно.** Каталог провайдеров описывает 6 операций
   из 27 и никак не связан с реальным адаптером. Либо каталог отражает
   реальность, либо его не должно быть.

Три заглушки — `DELETE AFTER MIGRATION`: удалить сейчас, они недостижимы
(`connectable: false`), не имеют тестов и один их метод **лжёт пустым списком
вместо отказа**.

## I. Legacy Bot Bridge

### Что это на самом деле — три моста, а не один

| Направление | Что несёт | Защита |
|---|---|---|
| Maya → бот | Баланс лояльности: `{found, balance, source:'maya_ledger'}` | только loopback, секрет ≥32, белый список слагов |
| бот → Maya | Карточки инбокса | общий платформенный токен |
| бот → Maya | Точки касания Recovery | тот же токен |

### Источник истины

Баллы боевого салона живут в **SQLite старого бота**: таблица
`loyalty_transactions`, баланс — сумма, отдельной таблицы балансов нет. Карта
YClients импортируется в этот реестр **ровно один раз**. Списание в YClients
только помечается комментарием и обнулением стоимости услуги — **баланс карты в
YClients не уменьшается**. Значит две величины расходятся по построению, и это
не сбой синхронизации, а свойство конструкции.

Мост проверяется **первым, до CRM**. Для боевого салона карта YClients не
читается вовсе, пока бот отвечает.

### Почему Maya всё ещё зависит

Обратные мосты **не несут уникальной способности** — `publishForTenant` и
`recordConsentSafeTouchpoint` у Maya уже есть нативно. Они существуют по одной
причине: **приёмника вебхуков YClients в NestJS нет ни одного**. Старый бот —
единственный владелец вебхуков, и мосты просто доставляют то, что он уже принял.

### Что сломается при отключении

- Владелец и мастера перестанут получать карточки о новых записях, отменах,
  переносах, зависших заявках и напоминаниях о смене — **пока Maya не начнёт
  принимать вебхуки YClients сама**.
- Клиенты боевого салона увидят баланс из карты YClients вместо реестра бота.
  Числа разойдутся, потому что списания в карте не отражались.
- Точки касания Maya Recovered перестанут поступать, атрибуция потеряет вход.

### Вердикт

**KEEP TEMPORARILY + WRAP.** Мост остаётся, но домен перестаёт знать, что данные
пришли из старого бота: сегодня `source: 'legacy_maya'` уезжает в поле, где
потребитель ждёт провайдера CRM. Физическое удаление — только после того, как
Maya научится принимать вебхуки YClients, а это **глава 3**, не эта.

## J. Loyalty Architecture

**Сейчас:** три представления одного баланса — реестр бота (истина), карта
YClients (расходится), `LoyaltyAccount.balance` в Maya (копия того, что ответил
мост). Мост пишет баланс **мимо собственного реестра Maya**, не создавая ни одной
`LoyaltyTransaction`: поэтому `/loyalty/me` показывает баллы, а
`/loyalty/me/transactions` — пустоту.

**Доказанный дефект (HIGH):** Maya обещает трату баллов как проверенную, не имея
ни одного пути списания. Для легаси-источника возвращается
`authoritative: 'maya'`, из-за чего `verification_required` становится `false`, и
карточка в приложении пишет «MAYA добавит его к записи и применит баллы».
Ответить действием нечем: реестр инструментов знает только чтение и внутреннюю
корректировку, а та отбивается для внешнего календаря. Единственное реальное
погашение живёт в боте.

**Целевое состояние — решение владельца, а не моё.** Развилка:

- **Лояльность остаётся внешней ответственностью.** Maya читает и показывает,
  но не обещает списание. Дешевле, честнее, снимает HIGH одной правкой флага.
- **Лояльность становится способностью Maya.** Требует собственного реестра,
  пути списания и переноса истории из бота — это отдельный объём, и он
  пересекается с главой 6.

В Phase B предлагаю только первое: перестать обещать то, чего система не умеет.
Балансы не мигрируем.

**Здесь я должен исправить собственное утверждение из главы 1.**

В Cycle 01 я отложил эту находку с обоснованием «включение проверки отрежет

| Факт | Значение |
|---|---|
| Арендатор | `muzhskaya-estetika-3` |
| Тариф | `business` |
| `crm.integration` в тарифе | **есть** |
| `journal` в тарифе | **есть** |
| Статус | `trial`, полный доступ до 2026-08-25 |

Салон прошёл бы проверку и сегодня (триал), и после него (тариф даёт обе фичи).
Опасение было предосторожностью без основания.

**Настоящая проблема глубже и она не в контроллере.** Права арендатора живут в
**базе**, а TS-каталог тарифов (`feature-catalog.ts`, `PRO_PLAN_FEATURES`,

**Целевое поведение:** каталог возможностей должен быть один и он должен быть
источником для базы, а не параллельным документом. Само включение
`@RequiresFeature('crm.integration')` — тривиально и безопасно, но ставить его
поверх расходящейся модели значит закрепить расхождение.

**Вердикт: DEFER в главу 5** (возможности и права), с исправленным обоснованием.
Не потому что опасно, а потому что чинить надо модель, а не одну строку.

## M. Historical Data Strategy

Сегодня история теряет опору в трёх местах:

1. **Имена услуг и мастера в карточке визита** берутся из живого каталога CRM.
   Услугу переименовали или удалили — история переписалась задним числом, а
   отказ каталога глотается молча.
2. **Визиты, заведённые в журнале, в Maya не существуют.** Для боевого салона
   это большинство визитов: аналитика читает их из CRM живьём, а собственной
   истории нет.
3. **`Appointment.crmExternalId` без уникального ключа** — параллельные
   обновления «Моих записей» дублируют визит.

Предложение минимальное: сохранять **снимок имён на момент визита** рядом с
ссылкой, и добавить уникальность `(tenantId, provider, crmExternalId)`.
Событийного источника не строим — это глава 3.

## N. Transaction / Revenue Semantics

**Что Maya может считать подтверждёнными деньгами:** только кассовые операции из
`transactions/{company}`, и только при `status === 'available' && verified === true`.
Это уже реализовано и помечено источником `crm_financial_transactions`. Прибыль
считается исключительно от этой кассы. Модель хорошая.

**Что Maya подтвердить не может:**

| Факт | Доступен? |
|---|---|
| Чек, ККМ, документ, кассовая смена | **нет** — Maya их не запрашивает, понятия «чек» в системе нет |
| Возврат | **нет** — любая транзакция ≤ 0 молча выбрасывается, и это закреплено тестом |
| «Оплачено» отдельно от «пришёл» | **нет** — оба схлопнуты в `completed` |
| Выручка за год | **частично** — годовой отчёт падает на лимите пагинации, а владельцу это объясняется как отсутствие данных и нехватка прав |

**Опасное место:** «записанная» сумма из журнала в CRM-режиме честно гасится в
AI-слое с прямым комментарием, **но HTTP-кабинет отдаёт те же цены в поле
`revenue` без пометки**. Один и тот же вопрос через чат и через экран даёт разный
по достоверности ответ.

Для главы 7 это означает: подтверждённая выручка есть, но **возвраты и неявки в
неё зашиты неразделимо**, а «активная запись» — это всё, что не отменено.

## U. Migration Plan

Схему меняет **только пакет P2**. Всё аддитивно.

```prisma
model CrmStaffAccess {
  provider  String?   // ← новая колонка, засыпка 'yclients' для существующих
  @@unique([tenantId, provider, externalStaffId])   // ← заменяет [tenantId, externalStaffId]
}

model CrmClientLink {                                // ← новая таблица
  id         String   @id @default(cuid())
  tenantId   String
  provider   String
  externalId String
  userId     String?
  phoneHash  String
  syncedAt   DateTime @default(now())
  unlinkedAt DateTime?
  @@unique([tenantId, provider, externalId])
  @@index([tenantId, phoneHash])
}

model Appointment {
  provider   String?                                 // ← новая колонка
  @@unique([tenantId, provider, crmExternalId])      // ← новый ключ
}
```

**Опасное место, требующее отдельной проверки:** замена уникального ключа
`CrmStaffAccess` и новый ключ на `Appointment` упадут, если в боевой базе уже
есть дубли. Перед миграцией — обязательный запрос на дубли; при их наличии
миграция не применяется, а разбирается отдельно.

Изменения внешних идентификаторов, разрушающих шагов и переписывания записей CRM
