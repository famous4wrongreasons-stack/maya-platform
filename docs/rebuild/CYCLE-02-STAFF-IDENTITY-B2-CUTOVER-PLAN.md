# STAFF IDENTITY — PHASE B2: AUTH / ACCESS CUTOVER PLAN

> Только план. **Код приложения не изменён**, миграций не создано, прод не тронут.
>
> **Главный инвариант:** ни одно решение об авторизации, доступе или сессии
> после CUTOVER не зависит напрямую от `externalStaffId`. Внешний id живёт
> только на границе интеграции:
> `provider + externalStaffId → StaffProviderLink → Staff.id`.

---

## 0. Что определяет форму перехода

### 0.1 Сравнения сегодня идут в пространстве провайдера

Три места стража сравнивают `boundStaffId` (из `CrmStaffAccess.externalStaffId`)
со значениями, пришедшими **из CRM**:

| Место | С чем сравнивается |
|---|---|
| `crm.service.ts:1184` | `staffId` из HTTP-DTO (внешний) |
| `crm.service.ts:1210` | результат `getAppointmentStaffId` (внешний) |
| `crm.service.ts:1258` | `detail.provider.id` (внешний) |

Значит перевод — не «подменить одно поле другим», а **перенести точку
сравнения**: значение со стороны CRM разрешается в `Staff.id` на границе, и
дальше сравниваются два внутренних идентификатора.

### 0.2 🔴 Запись обязана переключиться ВМЕСТЕ с чтением

`users.service.ts:675` и `crm.service.ts:1960` создают `CrmStaffAccess` **без**
`staffId`. Если переключить только чтение, первый же новый мастер, добавленный
после cutover, получит грант с `staffId = NULL` и **не сможет войти в журнал**.

Поэтому B2 — это чтение и запись одной ревизией. Разносить нельзя.

## 1. `journalStaffBinding`

```ts
// СЕЙЧАС — отдаёт внешний id провайдера
const access = await this.prisma.crmStaffAccess.findFirst({
  where: { tenantId, userId: actor.userId },
  select: { externalStaffId: true, status: true },
});
if (!access || access.status !== 'active') throw this.journalRecordForbidden();
return access.externalStaffId;

// СТАНЕТ — отдаёт идентичность Maya
const access = await this.prisma.crmStaffAccess.findFirst({
  where: { tenantId, userId: actor.userId },
  select: { staffId: true, status: true },
});
if (!access?.staffId || access.status !== 'active') {
  throw this.journalRecordForbidden();   // нет идентичности ⇒ нет доступа
}
return access.staffId;
```

Отсутствие `staffId` — **отказ**, а не откат на внешний id. Иначе legacy-путь
остаётся живым обходом инварианта.

Появляется один новый разрешатель, единственная точка, где читается внешний id:

```ts
/** Граница интеграции: значение провайдера → идентичность Maya. */
private async resolveStaffIdByExternal(
  tenantId: string, externalId: string,
): Promise<string | null> {
  const link = await this.prisma.staffProviderLink.findFirst({
    where: { tenantId, provider: await this.providerOf(tenantId),
             externalId, unlinkedAt: null },
    select: { staffId: true },
  });
  return link?.staffId ?? null;
}
```

Три сравнения становятся:

```ts
const target = await this.resolveStaffIdByExternal(tenantId, String(staffId));
if (target === null || target !== boundStaffId) throw this.journalRecordForbidden();
```

**Fail-closed.** Мастер, появившийся в CRM после последней сверки, не имеет
связи ⇒ доступ закрыт до сверки. Сегодня итог тот же (его id не совпал бы с
привязкой), так что поведение не меняется.

## 2. `reconcileCrmTeamAccess`

```
СЕЙЧАС: teamById.get(access.externalStaffId)      ← голое строковое равенство
СТАНЕТ: link = StaffProviderLink(tenantId, provider, externalId)
        → link.staffId → CrmStaffAccess(staffId)
```

| Событие | Целевое поведение |
|---|---|
| Член команды есть, связь активна | `syncedAt = now()`, грант живёт |
| Член команды есть, связь **отвязана** | НЕ активировать молча — вынести на подтверждение владельца |
| Член команды новый | создать `Staff` + связь + грант `pending_contact` |
| Связь активна, в команде нет | `unlinkedAt = now()`, грант `disabled`, сессии отозвать |
| Роль владельца/администратора | не трогать (существующее правило сохраняется) |

Именно это закрывает fail-open из анализа §6.4: совпадение числовых id между
провайдерами больше не может передать права, потому что ключ включает
`provider`, а старая связь отвязана.

## 3. `CrmStaffAccess`

| Поле | После cutover |
|---|---|
| `staffId` | **рабочий ключ**: по нему ищут, связывают, отзывают |
| `externalStaffId` | пишется как раньше, **не читается ни в одном решении**; только совместимый lookup §12 |
| `userId` | остаётся; источник истины переезжает в `Staff.userId` позже |
| `encryptedDisplayName` | остаётся; источник истины — `Staff` |
| `role`, `status` | без изменений, это и есть грант |

`NOT NULL` на `staffId` — **отдельный шаг в конце B2**, отдельной миграцией и
только после суток на проде без единого гранта с пустым `staffId`. Раньше
ставить нельзя: откат B2 стал бы невозможен.

## 4. Разрешение ролей и прав

**Изменений не требуется.** Роль приходит из `Membership`
(`jwt.strategy.ts:77-83`), а не из `CrmStaffAccess`. Грант лишь задаёт роль при
выдаче доступа.

Единственная правка — косметическая: `assertCrmStaffAccessActive`
(`crm.service.ts:748-755`) выбирает `externalStaffId`, но **не использует** его.
Поле убирается из `select`, решение и так принимается по `role` и `status`.

## 5. Проверки входа и «бизнес-аккаунта»

```ts
// СЕЙЧАС — social-auth.service.ts:554-558
businessIdentity.crmStaffAccess !== null
```

Забор не видит мастера внутреннего календаря (анализ §6.6): проверки на
`InternalProvider` в `social-auth` и `auth-session` нет вовсе.

**Целевое:** проверять наличие `Staff` — оно покрывает оба источника.

🔴 Это **изменение боевого поведения**: мастер на внутреннем календаре начнёт
удерживаться забором и не сможет открыть клиентский аккаунт на тот же телефон.
Считаю это исправлением дефекта, но выношу **отдельным решением** — включать
вместе с cutover или следующим шагом. По умолчанию в плане: **включить**, потому
что это дыра в границе бизнес-аккаунта.

## 6. Владение сессией

**Изменений не требуется, и это доказано составом токена.**

## 8. Отключение CRM

Сегодня `disconnectIntegration` (`crm.service.ts:708-722`) удаляет **только**
`CrmIntegration`; гранты, роли и сессии продолжают жить со старыми внешними id.

**Целевая политика:**

| # | Действие |
|---|---|
| 1 | Все связи арендатора для этого провайдера → `unlinkedAt = now()` |
| 2 | Гранты, державшиеся на этом провайдере → `status = 'disabled'` |
| 3 | Сессии этих пользователей отозвать, `revokeReason: 'crm_disconnected'` |
| 4 | 🔴 **Владельца и администратора не трогать** — их роли не выдаёт CRM, и отключение интеграции не должно запирать владельца снаружи |
| 5 | `Staff`, визиты и история сохраняются полностью |

🔴 Изменение боевого поведения. Сегодня отключение не гасит доступ вовсе.

## 9. Переподключение CRM

Связь ищется по `(tenantId, provider, externalId)`.

| Случай | Поведение |
|---|---|
| Связь активна | `syncedAt` обновляется, доступ продолжается |
| Связь отвязана | **не активируется молча** — владелец подтверждает восстановление |
| Связи нет | новая связь + грант `pending_contact` |

Остаточный риск, названный честно: если **тот же** провайдер переиспользовал
внешний id для другого человека — это не обнаруживается в принципе.
Подтверждение владельца при реактивации — единственное смягчение.

## 10. Смена провайдера

1. Старый отключается по политике §8.
2. Новый подключается, состав команды читается заново.
3. Для каждого члена — новый `Staff`+связь **или** предложение сопоставить с
   существующим `Staff`.
4. Сопоставление подтверждает человек. Автоматического по имени нет.

Совпадение внешних id между провайдерами передать права не может: ключ связи
включает `provider`, старая связь отвязана. Визиты не трогаются — они указывают
на `staffId`.

## 12. Совместимый `PATCH team-access/:externalStaffId`

URL **не меняется**. Внутри — единственный разрешённый путь чтения внешнего id:

```
provider (из CrmIntegration арендатора)
  + externalStaffId (из URL)
  → StaffProviderLink { provider, externalId, unlinkedAt: null }
  → Staff
  → CrmStaffAccess (по staffId)
```

Связи нет → 404 с существующим кодом ошибки. Аудит продолжает писать
`entityId = externalStaffId` (это уже в боевых данных).

## Двойные чтения только на переход

Их **нет**, и это осознанно. Двойное чтение `staffId ?? externalStaffId`
означало бы, что старый путь остаётся рабочим обходом инварианта. Вместо этого
отсутствие `staffId` — **отказ** (§1), а полнота гарантирована: backfill B1
доказал 6 из 6 грантов и 18 из 18 визитов, а запись переключается той же
ревизией (§0.2).

Двойная **запись** остаётся: `staffExternalId` и `externalStaffId` пишутся как
производные, но не читаются.

## Действующие сессии: затрагиваются ли

**Не затрагиваются. Отзыв не требуется.** Доказательство:

| Факт | Источник |
|---|---|
| В токене нет идентичности мастера | `jwt.strategy.ts:16-21` |
| `AuthenticatedUser` её не несёт | `common/authenticated-user.interface.ts` |
| Привязка разрешается на каждый запрос из базы | `crm.service.ts:1145-1155` |
| Роль приходит из `Membership`, не из гранта | `jwt.strategy.ts:77-83` |
| Все 4 гранта с аккаунтом уже имеют `staffId` | backfill B1: 6 из 6 |

Из четырёх активных сессий к мастерам относится **одна** (единственный грант с
`userId`, роль `tenant_admin`) — и она держит роль с полным доступом к журналу,
для которой привязка вообще не вычисляется.

Отзыв сессий предлагается **не делать**: он ничего не чинит и выкинет владельца
из кабинета без причины.

## Data-quality finding (зафиксировано, не чиним)

Два мастера, имеющих исторические визиты, ушли из состава команды провайдера.
Их идентичность создана технической: имя `Мастер yclients#<id>`, `active =
false`, связь с `unlinkedAt`. **Автоматически восстанавливать имена из истории
журнала не будем** — по вашему решению. Записано как долг качества данных, не
блокер.
