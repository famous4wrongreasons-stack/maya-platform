## 1. Изменения Prisma

**Новые модели:** `Staff`, `StaffProviderLink` — [prisma/schema.prisma](../../maya-saas-backend/prisma/schema.prisma).

**Изменения существующих:** `CrmStaffAccess.staffId String?` + связь;
`Appointment.staffId String?` + связь + индекс `[tenantId, staffId, startAt]`.
Обратные связи добавлены в `Tenant`, `User`, `Branch`.

### Два решения, отличающихся от первоначального предложения гейта

**`Staff.encryptedDisplayName` — nullable.** Шифровать средствами Postgres
нечем: ключ у приложения. Открытый текст как временное решение недопустим,
поэтому колонка пустует до прогона скрипта, а `NOT NULL` ставится на CUTOVER.

**Связи с `Membership` НЕТ**, хотя `InternalProvider` её имеет. Составной FK на
`Membership(userId, tenantId)` даёт `ON DELETE CASCADE` — снятие членства
стирало бы саму идентичность мастера вместе с историей. Это ровно то, чего
модель должна не допускать. `Client` из P2 такой связи тоже не имеет —
следуем утверждённому эталону.

## 2. SQL-миграция

[`20260817090000_staff_identity_phase_a`](../../maya-saas-backend/prisma/migrations/20260817090000_staff_identity_phase_a/migration.sql)
— только ADD:

```
2 таблицы      Staff, StaffProviderLink
2 колонки      CrmStaffAccess.staffId, Appointment.staffId   (обе nullable)
9 индексов     включая @@unique([tenantId, provider, externalId])
7 внешних ключей  все составные, (id, tenantId)
0 удалений     ни одной колонки, ни одной таблицы
0 NOT NULL
```

Порядок объектов: таблицы → колонки → уникальности и индексы → внешние ключи.
Составной FK требует уже существующего уникального индекса — обратный порядок
падает на `there is no unique constraint matching given keys` (урок цикла 02-R).

## 3. Алгоритм backfill

[`scripts/staff-identity-backfill.ts`](../../maya-saas-backend/scripts/staff-identity-backfill.ts).
**По умолчанию сухой прогон**, запись только по явному `--apply`. Идемпотентен.

| Шаг | Что делает |
|---|---|
| 1 | Внутренние мастера → `Staff` **с сохранением `InternalProvider.id` дословно** |
| 2 | Строки доступа → `Staff` + `StaffProviderLink` с провайдером из `CrmIntegration`; `CrmStaffAccess.staffId` заполняется |
| 3 | Мастера визитов без строки доступа → имя из **состава команды провайдера**; при недоступности — техническая неактивная идентичность с отвязанной связью |
| 4 | Визиты: внутренние тождественно, внешние через связь |
| 5 | Гейт: остались визиты без мастера → падение |

Скрипт **не пишет** колонки наследия, **не удаляет** `InternalProvider`, **не
ставит** `NOT NULL`, **не трогает** авторизацию, сессии и уведомления.

### Почему шаг 1 делает всё остальное простым

`Appointment.staffExternalId` у внутренних записей уже содержит
`InternalProvider.id`. После сохранения id он **становится валидным
`Staff.id`**, и перенос внутренних визитов — тождественное присваивание.

### Шифрование

Имя из `InternalProvider.displayName` (открытый текст) шифруется
`EncryptionService.encrypt`. Имя из `CrmStaffAccess.encryptedDisplayName`
переносится **как есть** — оно уже шифр, повторное шифрование испортило бы его.

## 5. Обработка коллизий

| Случай | Поведение |
|---|---|
| Один человек и как `InternalProvider`, и как `CrmStaffAccess` | Определяется по общему `userId`; **побеждает внутренняя строка** — её id уже в визитах |
| Обе стороны без `userId` | Автоматически не сопоставляются. Сопоставление по имени запрещено |
| Повтор `(арендатор, провайдер, внешний id)` | Отвергается базой |
| Тот же id у другого провайдера или арендатора | Разрешён — в этом весь смысл квалификации |
| У арендатора есть строки доступа, но нет `CrmIntegration` | Скрипт **останавливается на этом арендаторе** и пишет предупреждение: провайдера взять неоткуда, подставить `yclients` наугад значит соврать в ключе |

## 7. Два дефекта, которые нашёл стенд (оба в моём скрипте)

**Контекст арендатора.** `crm.getTeamMembers` требует
`assertTenantId`, а скрипт его не открывал. Вызов падал **всегда**, и каждая
идентичность становилась технической — то есть скрипт молча делал худшее из
возможного. Исправлено обёрткой `tenantContext.runAsSystemTenant`. После правки
код доходит до адаптера и падает уже на поддельном токене стенда — чего и ждём.

**Сухой прогон завышал счёт.** Поиск «мастеров без связи» не учитывал связи,
которые создаст шаг 2, и обещал 3 технические идентичности вместо 2. Отчёт
читает человек и по нему принимает решение — завышение недопустимо. Исправлено.
