## Инвариант

**Ни одно решение об авторизации, доступе или сессии не зависит напрямую от
`externalStaffId`.** Единственное допустимое использование:

```
provider + externalStaffId → StaffProviderLink → StaffId
```

Дальше система работает только с идентичностью Maya.

### Почему нет двойного чтения

`staffId ?? externalStaffId` оставил бы старый путь рабочим обходом инварианта.
Вместо этого отсутствие `staffId` — отказ, а полнота доказана до выката.

Из этого следует жёсткое требование, которое я вынес отдельным пунктом плана и
исполнил: **запись переключается той же ревизией, что и чтение**. Иначе первый
же новый мастер получил бы грант с пустым `staffId` и не смог войти в журнал.

## Находка, изменившая объём §14

Карта связки показала то, чего я не видел: кабинет **соединяет**
`staff_external_id` из `/analytics/business` с
`payroll.staff[].staff_id` из `/analytics/business/finance` (это id YCLIENTS) и
с `member.id` из `/staff` (`maya-os-site/index.html:12199, 31151, 31203`).

**Замена поля молча оторвала бы зарплату и результативность от мастеров** — не
ошибкой, а пустым списком. Поэтому `staff_id` **добавлен рядом**, а
`staff_external_id` оставлен нетронутым.

Тест `legacy-net-contract.spec.ts` с побайтовым снимком ответа сработал ровно
как задуман — его собственный комментарий предупреждал, что служебный ключ
сломает сравнение. Снимок обновлён один раз, осознанно, с обоснованием в коде.

## Барьер против возврата

**Тест-храповик** в `domain/boundary.spec.ts`: `externalStaffId` запрещён в
`auth/`, `guards/`, `tenancy/`, `appointments/`. Список исключений только
сокращается.

Одно исключение внесено **с причиной, а не ослаблением правила**:
`appointments/appointments.service.ts` адресует по внешнему id **уведомления**,
а не доступ. Там же живёт известный дефект (при внутреннем календаре в поле
уходит cuid, совпадения быть не может) — его исправление вы исключили из этапа.
Строка уйдёт вместе с ним.

**Брендированный `StaffId`** делает подмену пространств ошибкой компиляции.
