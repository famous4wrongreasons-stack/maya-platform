### Порядок объектов — не произвольный

`таблицы → колонки → ключи и проверки → индексы → внешние ключи`

Две ошибки порядка были найдены на прогонах и исправлены:

1. **Составной внешний ключ требует существующего уникального индекса.**
   Сначала ограничения шли раньше индексов — падало на
   `there is no unique constraint matching given keys`.
2. **`pg_indexes` включает индексы, которыми владеют ограничения.** Первичные
   ключи создавались дважды — падало на конфликте имён. Такие индексы теперь
   отфильтрованы: из 19 самостоятельных осталось 14.

### Ни одного `IF NOT EXISTS`

Каждый объект даёт **три исхода**:

```sql
IF NOT FOUND THEN
  ALTER TABLE "MarketingCampaign" ADD COLUMN "retryCount" INTEGER NOT NULL DEFAULT 0;
ELSIF actual.data_type      <> 'integer'
   OR actual.is_nullable    <> 'NO'
   OR actual.column_default <> '0' THEN
  RAISE EXCEPTION 'reconciliation: MarketingCampaign.retryCount отличается — тип=%, nullable=%, default=%',
    actual.data_type, actual.is_nullable, coalesce(nullif(actual.column_default, ''), '(нет)');
END IF;
```

Для ограничений и индексов сравнивается **полное определение**
(`pg_get_constraintdef`, `indexdef`), а не имя.

## Проверки — что доказано прогонами

| # | Проверка | Результат |
|---|---|---|
| 1 | Применение к чистой базе из миграций репозитория | `exit=0` |
| 2 | Повторное применение | `exit=0`, ноль операций |
| 3 | **Структура против прода** | **совпадает по всем пяти срезам** |
| 4а | Колонка есть, но другого типа | `exit=3`, `MarketingCampaign.retryCount отличается — тип=text` |
| 4б | Колонка есть, но другой обнуляемости | `exit=3`, `nullable=YES` |
| 4в | Индекс есть, но с другим определением | `exit=3`, `индекс ... отличается` |
| 4г | Ограничение есть, но с другим определением | `exit=3`, `MarketingPolicy_pkey отличается — PRIMARY KEY (provider)` |

Проверка 3 — главная: **чистая база, поднятая только из миграций репозитория,
даёт структуру, идентичную боевой.** Это цель 4 цикла.

### Оговорки честности

- Проверки 4в и 4г с первого раза дали ложное «прошло»: в одном случае я пытался
  подменить индекс, которым владеет внешний ключ, в другом — задал ровно то
  определение, которого миграция и ждёт. Оба теста были неверны, а не миграция;
  переделаны и подтверждены.
- Пара промежуточных прогонов выводила «применилось без ошибок» при фактической
  ошибке — код возврата прятался за `| tail`. Итоговые цифры выше сняты с явной
  проверкой `exit`.

## Чего миграция НЕ делает

- Не удаляет и не изменяет ни одной существующей колонки, таблицы, ограничения
  или индекса.
- Не трогает данные.
- Не переписывает и не удаляет строки `_prisma_migrations`.
- Не переиспользует имена трёх утерянных миграций.

Дубликат `20260814210000_outbound_messaging_delivery` с двумя контрольными
суммами остаётся зафиксированной **исторической аномалией**.
