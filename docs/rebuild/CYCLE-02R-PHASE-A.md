## A. Главный вывод

**Побайтовое восстановление трёх миграций невозможно.** Файлов не существует
нигде. Поэтому возвращать их в репозиторий под теми же именами **нельзя**: любая
реконструкция даст другую контрольную сумму, и `migrate deploy` начнёт падать на
проде с «migration was modified after it was applied».

Рабочий путь — **семантическое восстановление под новыми именами** с
идемпотентным SQL. Он достигает всех пяти целей цикла, не трогая ни структуру
боевой базы, ни уже записанные контрольные суммы.

начала обрываться. Harness для этого уже построен и описан в разделе E.

## E. Как получить точную разницу

Способ проверен и работает; на нём же строится приёмка.

1. `r_repo` — чистая база, на которую применены **только** миграции репозитория.
2. `r_prod` — структура прода (`pg_dump --schema-only`, **без данных**, поэтому
   персональные данные не участвуют).
3. Сравнение `information_schema.columns`, `pg_constraint`, `pg_indexes`.

Разница `r_prod` минус `r_repo` **и есть** содержимое пропавших миграций.

Обе базы уже созданы на сервере и **подлежат удалению** — см. раздел J.

## F. Безопасный способ вернуть в репозиторий

### Почему нельзя под теми же именами

Prisma сверяет sha256 файла с `_prisma_migrations.checksum`. Реконструкция даст
другую сумму → **каждый последующий выкат будет падать**. Единственный способ
сохранить имена — переписать `checksum` в боевой таблице, то есть править
служебные данные прода вручную. Отвергаю: риск выше выигрыша, а выигрыш
косметический.

### Предлагаемый путь: новая миграция-выравниватель

Одна новая миграция, например `20260817000000_reconcile_marketing_schema`, с
**идемпотентным** SQL:

```sql
CREATE TABLE IF NOT EXISTS "MarketingPolicy" (...);
ALTER TABLE "MarketingCampaign" ADD COLUMN IF NOT EXISTS "scheduledFor" TIMESTAMP(3);
CREATE INDEX IF NOT EXISTS "..." ON "..." (...);
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = '...') THEN
    ALTER TABLE "..." ADD CONSTRAINT "..." ...;
  END IF;
END $$;
```

Поведение:

| Где | Что произойдёт |
|---|---|
| Прод | **Ни одной операции DDL**: всё уже существует. В `_prisma_migrations` добавится одна строка |
| Чистая база из репозитория | Создаст всё недостающее и даст структуру, идентичную проду |

Четыре сиротские записи в журнале прода остаются навсегда и безвредны: Prisma
сверяет только локальные миграции, что подтверждено — `migrate status` на проде
отвечает `Database schema is up to date!`.

### Оговорка честности

Цель 3 звучит как «ничего не менять в боевой базе». Строго говоря, **одна строка
в `_prisma_migrations` добавится** — иначе миграционный подход невозможен в
принципе. Структура и данные не меняются. Считаю это допустимым, но прошу
подтвердить.

### Схема Prisma

Параллельно `schema.prisma` дополняется пятью моделями и двадцатью двумя полями,
чтобы описывать реальность. Это **не** меняет базу — только представление.

## H. `release:preflight` в выкате без `ts-node`

### Почему сейчас не работает

Скрипт написан на TypeScript и запускается через `ts-node`, а релиз ставится
`npm ci --omit=dev`. Ни `ts-node`, ни самого файла в релизе нет: `rsync` шлёт
только `dist`, `package.json`, `package-lock.json`, `prisma`, `prisma.config.ts`,
`tsconfig.json`.

### Предлагаемое решение: компилировать вместе с приложением

`release-preflight.ts` импортирует `validateRuntimeConfig` относительным путём
`../src/config/runtime-config`. Если собирать его в `dist/scripts/`, импорт
разрешится в `dist/src/config/runtime-config` — то есть в уже собранный
валидатор. Никаких dev-зависимостей.

Запуск на сервере:

```
node dist/scripts/release-preflight.js
```

Проверить перед реализацией: `@prisma/adapter-pg`, `@prisma/client` и `dotenv`
должны быть в обычных зависимостях, а не в dev.

### Куда встроить

В шаг 6 выката — **после** `npm ci` и **до** миграции, вместо нынешней ручной
проверки конфига. Preflight делает обе половины: валидацию боевой конфигурации и
сверку миграций, включая незавершённые, изменённые и отсутствующие.

### 🔴 Обязательный порядок

**Preflight нельзя включать до восстановления.** Сегодня он гарантированно
провалится на `Database has 3 migration(s) absent from this release` и
заблокирует любой выкат.

Порядок:

1. Выравнивающая миграция и схема.
2. Проверка, что чистая база совпадает с продом.
3. Выкат выравнивающей миграции (на проде — ноль операций DDL).
4. **Только теперь** включить preflight в выкат.

Шаг 4 — самая дешёвая профилактика: он навсегда закрывает класс проблемы,
породивший этот цикл.
