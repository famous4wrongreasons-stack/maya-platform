## 🔴 Проба вскрыла ложь в моём же классификаторе

Первая доставка дала событие `appointment.attendance_recorded`. Присутствие при
этом **никто не сравнивал**: в зеркале визита Maya его нет вовсе.

Провайдер шлёт `update` на **любое** касание записи, включая закрытие оплаты.
Назвать это «присутствие записано» — ложь того же класса, что убиралась в
главе 2: имя утверждало больше, чем было доказано.

**Исправлено:** тип выводится только из различимого — мастер, время, состав
услуг. Нечего назвать → события **не возникает** (`stale / no_observable_change`).
`appointment.attendance_recorded` остаётся в словаре, но в B2 не порождается ни
разу: он станет достижим, когда зеркало начнёт хранить присутствие.

Событие с этим типом в боевой базе одно — та самая проба до исправления. Не
удаляю: запись о том, как было, честнее подчищенной картины.

## Политика неразрешённой идентичности визита

Выбрана **вторая** из двух разрешённых: карантин, а не импорт.

Причина конкретна: строка визита требует `clientId` — внешний ключ на
пользователя Maya. Клиентов в проде **ноль** (`Client` и `CrmClientLink` пусты).
Импортировать визит значило бы выдумать ещё и клиента. Новой схемы для этого не
нужно — `IngestionQuarantine` из B1 покрывает случай причиной
`entity_unresolved`.

### 🔴 Разрыв измерен, а не предположен

Я сопоставил внешние идентификаторы из **боевого журнала за 7 суток** с зеркалом
визитов Maya:

| | |
|---|---|
| Внешних id в зеркале Maya | **18** |
| Доставок с `record_id` за 7 суток | **413** |
| Уникальных записей в потоке | **146** |
| Из них есть в зеркале | **1** |
| Нет в зеркале | **145** |
| **Доставок, которые нашли бы визит** | **1 из 413** |

То есть при полностью исправном приёме **99,8 % доставок уйдут в
`entity_unresolved`**. Это не сбой B2 и не ошибка настройки: Maya просто не
зеркалит визиты салона. Строка `Appointment` появляется только когда клиент
зарегистрирован в Maya и либо бронировал через неё, либо открыл «Мои записи».
Живые записи салона — с виджета, по телефону, из самой CRM — в Maya не попадают
вовсе.

**Что это значит для главы 3.** Наблюдение без сверки бессмысленно: приём будет
исправно складывать в карантин почти всё. Сверка (B3) перестаёт быть
«страховкой на случай пропущенного вебхука» и становится главным механизмом,
который вообще наполняет зеркало. Порядок работ это меняет.

## Приватность карантина

Проверено чтением боевых строк:

```
{"event": "record.create", "status": null, "resource": null,
 "external_id": "999999999", "payload_keys": ["resource"]}
{"event": null, "status": "update", "resource": "client",
 "payload_keys": ["resource", "resource_id", "status", "data"]}
```

Только **имена** ключей и неперсональные скаляры. Ни имени, ни телефона, ни
тела. Бот пересылает ровно это и ничего больше — значения могут нести ПД, а
Maya всё равно перечитывает запись у источника сама.
