## 2. Возможности API провайдера — по коду, а не по памяти

Метод `records/{company}` (`yclients-crm.adapter.ts:2192-2225`):

| Возможность | Факт |
|---|---|
| Диапазон дат | `start_date`, `end_date` |
| Постраничность | `count=200`, `page` 1…25 ⇒ **потолок 5000 записей** за проход |
| Признак «есть ещё» | нет: ни `total`, ни `has_more`, ни курсора — только эвристика неполной страницы |
| Удалённые | `with_deleted=1`, у записи поле `deleted` |
| Фильтры | `staff_id`, `client_id` |
| Окно журнала | 31 день — но см. §2.1: это правило СЕРВИСА, а не эндпоинта |
| Лимит запросов | ~200/мин — известен только из комментария легаси (`database.py:144`) |

### 2.1 🔴 Выборка записей молча недосчитывает

`fetchRecords` после цикла страниц делает просто `return records;`
(`:2237`) — **без проверки, упёрлись ли в потолок**. Если 25-я страница пришла
полной, метод вернёт усечённый массив, и вызывающий не отличит «записей больше
нет» от «мы прочитали не всё».

Соседние выборки в том же файле ведут себя иначе и **бросают**:

```
:1360  throw new Error('YClients client registry exceeds the safe page limit');
:2282  throw new Error('YClients finance result exceeds the safe page limit');
```

Записи — **единственная** выборка, которая может тихо соврать. Это тот же класс
ошибки, что чинился в главе 2 P6: «не смог» подан как «пусто».

**Легаси-бот делает это честно**: `get_company_records_snapshot`
(`yclients.py:1761`) возвращает `complete: false` и код
`yclients_records_page_limit_reached` с комментарием «Never label the truncated
register as complete». Поведение в проекте уже есть — в NestJS оно не
воспроизведено.

🔴 **Следствие для плана.** §8 требует «неполная выборка ⇒ никаких выводов об
отсутствии». Сегодня это **невыполнимо**: адаптер не сообщает о неполноте.
Значит появляется обязательный нулевой шаг — см. §12.

### 2.2 Правило 31 дня — не свойство эндпоинта

Проверка длины окна живёт в `crm.service.ts` и записана **литералом дважды**
(`:1062` журнал, `:1626` финансы), а не константой `CRM_JOURNAL_MAX_WINDOW_DAYS`,
заведённой в главе 2 ровно для этого. Сам `fetchRecords` длину окна **не
проверяет вовсе**.

Более того, собственный код адаптера её обходит: `getClientAppointments`
(`:757`) по умолчанию просит **730 дней назад** и 90 вперёд — около 820 дней
одним запросом, при потолке в 5000 записей и без признака неполноты.

Для плана это значит: окно сверки не обязано быть 31 днём — но и утверждать, что
эндпоинт примет больше, я не стану без проверки. Ширину окна определим
измерением на боевых данных, а не догадкой.

### 🔴 Метки изменения записи НЕТ

`YclientsRecordApiItem` (`:143-158`) содержит: `id`, `date`, `datetime`,
`length`, `seance_length`, `attendance`, `visit_attendance`, `paid_full`,
`deleted`, `comment`, `staff_id`, `client`, `staff`, `services`.

**Ни `updated_at`, ни `changed_at`, ни версии.** Значит выборка «изменённые с
момента» невозможна, и сверка обязана сравнивать состояние. Оговорка честности:
это состав полей, которые **читает наш адаптер**; шлёт ли провайдер что-то ещё —
из репозитория **UNKNOWN**.

Полезное следствие: `attendance` у провайдера **есть**. Как только зеркало
начнёт его хранить, `appointment.attendance_recorded` из B2 станет достижим
честно — сейчас он не порождается именно потому, что сравнивать не с чем.

## 3. Целевая семантика зеркала

CRM остаётся владельцем внешней записи. Maya хранит **наблюдение**:

| Для чего | Что нужно |
|---|---|
| WATCH | разрешение `провайдер + внешний id → идентичность Maya` |
| дедупликация | канонический отпечаток состояния |
| будущий UNDERSTAND | нормализованные поля, а не сырое тело |
| историческая непрерывность | запись не исчезает при отмене |

Maya **не становится владельцем**: она не пишет в CRM из сверки и не считает
своё представление первичным при расхождении.

---

## 4. 🔴 Что мешает сегодня — и почему нужен гейт схемы

`Appointment.clientId` (`schema.prisma:1412`) — **обязателен** и связан дважды:

```prisma
client            User       @relation(..., fields: [clientId], ...)
clientMembership  Membership @relation(..., fields: [clientId, tenantId], ...)
@@unique([id, tenantId, clientId])
```

То есть зеркалировать запись салона можно **только** если её клиент — уже
пользователь Maya **с активным членством в этом арендаторе**. Для записи с
виджета или по телефону это неверно почти всегда.

Обойти это без схемы нельзя:

- завести пользователя на каждого клиента салона — значит **выдумать
  идентичность** и втянуть ПД в Maya. Запрещено вами и главой 2;
- писать визит без клиента — запрещает внешний ключ.

```
B3 SCHEMA GATE REQUIRED: YES
```

### Два варианта, оба с ценой

| | **A. Ослабить `Appointment`** | **B. Отдельная таблица зеркала** |
|---|---|---|
| Суть | `clientId` → nullable, связь с членством — опциональная; добавить `clientRef` → `Client.id` | новая `CrmAppointmentMirror` с ключом `(tenant, provider, externalId)` |
| Идентичность события | `Appointment.id` — **как вы и просили** | id зеркала, а не визита |
| Цена | `@@unique([id, tenantId, clientId])` меняет смысл; каскад при удалении клиента больше не покрывает все строки; **47 мест** в 4 файлах читают визит через клиента и требуют аудита | появляется **второе представление визита** — ровно то, от чего предостерегает реестр переноса |
| Риск для брони | правки в горячем пути записи клиента | боевой путь не тронут |

**Моя рекомендация — A**, потому что вы поставили целью именно
`→ Maya Appointment.id`, а два представления визита в одной системе мы уже
однажды разбирали как источник расхождений. Но цена A реальна и я её не
преуменьшаю: обязательность клиента сегодня — это ещё и защита от появления
«ничьих» визитов.

Точную схему покажу в гейте до применения.

## 5. Политика первичного наблюдения

```
1. При включении сверки для арендатора берётся отметка watchStartedAt
   (уже есть в CrmIntegration, заполнена в B1).
2. Первый проход создаёт строки зеркала со статусом наблюдения
   observed_existing.
3. Доменных событий первый проход НЕ создаёт ни одного.
4. Событие появляется только когда отпечаток состояния изменился ПОСЛЕ того,
   как строка уже была известна.
```

🔴 История задним числом не сочиняется. Запись, созданная в салоне полгода
назад, не может дать `appointment.created` сегодня: это ложь о времени, из
которой глава 4 сделает ложные выводы о динамике.

## 6. Канонический отпечаток состояния

Сравнивается **нормализованное деловое состояние**, а не тело провайдера:

| В отпечатке | Почему |
|---|---|
| мастер (внешний id) | смена мастера — факт |
| начало и конец | перенос — факт |
| состав услуг (отсортированный) | смена состава — факт |
| присутствие | канон главы 2, у провайдера есть |
| признак удаления | отмена — факт |

**Не входит:** комментарий, суммы, сырое тело, время чтения. Сырьё целиком
отпечатком быть не может: любое несущественное касание записи выглядело бы
изменением — ровно то, от чего легаси защищается своим `record_state`.

Функция уже есть: `canonicalStateFingerprint` из B1. Сверка и вебхук считают
отпечаток **одной и той же** функцией — на этом держится §7.

## 7. Схождение вебхука и сверки

Обязательный инвариант: один и тот же внешний факт, увиденный любым порядком,
даёт **один** результат.

```
вебхук первым   → отпечаток F → событие создано
сверка следом   → отпечаток F → duplicate, нового события нет

сверка первой   → отпечаток F → событие создано
вебхук следом   → отпечаток F → duplicate
```

Держится тем, что `dedupFingerprint` уникален в базе (B1) и **не содержит
способа получения**: `ingestionMethod` (`webhook` / `reconciliation`) лежит
рядом как провенанс, но в отпечаток не входит. Иначе один факт, увиденный двумя
путями, дал бы два события — и счётчики главы 4 удвоились бы.

## 8. Пропавшие и удалённые записи

🔴 `не вернулась в выборке` ≠ `удалена`. Правило:

| Наблюдение | Вывод |
|---|---|
| запись пришла с `deleted: true` (`with_deleted=1`) | **доказанное** удаление → `appointment.cancelled` |
| запись не пришла, выборка **полная** (страниц меньше потолка, ошибок нет) | пометить «не подтверждена», событие **не** создавать |
| не пришла дважды подряд в полных выборках | кандидат на удаление — решение отдельным правилом, не молча |
| выборка неполная (ошибка, потолок страниц, таймаут) | **никаких** выводов об отсутствии |
| провайдер недоступен | сверка не состоялась; это не «записей нет» |

Последняя строка — прямое наследование инварианта главы 2: недоступность
провайдера не выдаётся за бизнес-факт.

## 9. Состояние сверки между запусками

Нужно хранить: арендатор, провайдер, покрытый диапазон, время последнего
успешного прохода, число обработанных и изменённых, признак полноты
(упёрлись ли в потолок страниц), последняя ошибка.

`CrmIntegration.lastSyncAt` для этого недостаточен: он одно поле без диапазона
и без признака полноты. **Это часть того же гейта схемы.**

## 10. Расписание

Исходя из измеренного объёма (≈60 доставок и ≈150 записей в неделю на один
салон) и лимита ~200 запросов в минуту:

| Контур | Окно | Частота | Зачем |
|---|---|---|---|
| ближний | −1 … +7 дней | 15 мин | догнать пропущенный вебхук |
| средний | −31 … +31 день | 1 раз в сутки, ночью | полнота месяца |
| исторический | помесячно назад | вручную, по решению | первичное наполнение |

Один проход ближнего контура — 1–2 запроса. Суточная нагрузка ничтожна против
лимита. **Планировщик в B3 не включается**: сначала ручной прогон и сверка
результата.

## 11. Клиент и мастер

| Сущность | Разрешение |
|---|---|
| Мастер | `provider + externalId → StaffProviderLink → Staff.id` — работает, 6 активных мастеров разрешаются |
| Клиент | **не склеивать по телефону автоматически** — ваше решение сохраняется |

Для клиента предлагается: запись зеркалируется **без** клиента Maya
(`clientRef = null`), а связь появляется только когда идентичность доказана
существующим путём (`ClientIdentityService`, теневая регистрация по HMAC
телефона). Идентичность визита при этом **не теряется** — она держится на
`(tenant, provider, externalId)`.

Услуги и филиалы собственной идентичности Maya не имеют; в зеркале остаются
внешние идентификаторы как провенанс.

## 12. Выкат

### 🔴 B3.0 — до всего остального: выборка обязана признаваться в неполноте

Пока `fetchRecords` молча недосчитывает, вся политика §8 держится на воздухе:
отличить «записей нет» от «мы прочитали не всё» невозможно.

Минимальная правка: вернуть из выборки признак полноты — так же, как это уже
делают финансы и реестр клиентов в том же файле и как делает легаси-бот
(`complete: false` + код причины). Без побочных эффектов, без изменения схемы.

Это условие входа в B3, а не пожелание: без него сверка будет уверенно
объявлять записи исчезнувшими.

```
1. B3.0: честная неполнота выборки (код, без схемы).
2. Гейт схемы → ваше утверждение → миграция на клоне прода → прод.
2. Ручной прогон сверки за узкое окно (один день), результат читается глазами.
3. Прогон за 31 день, сверка счётчиков: сколько создано, изменено, не найдено.
4. Проверка §7 вживую: доставка после сверки даёт duplicate.
5. Планировщик включается флагом отдельно от выката.
```

Легаси не отключается ни на одном шаге. Теневой приёмник побочных действий не
получает.
