## 1. 🔴 Фактическая семантика `Appointment.clientId` — доказана данными

Ваша гипотеза подтвердилась, и жёстче, чем формулировалась.

| Проверка на боевой базе | Результат |
|---|---|
| Визитов | 18 |
| **Уникальных `clientId`** | **1** |
| Все `clientId` ведут на `User` | 18 из 18 |
| У всех есть `Membership` в этом арендаторе | 18 из 18 |
| **Роль этого пользователя** | **`tenant_admin`** — владелец салона |
| `Client` (идентичность главы 2) | **0** строк |
| `CrmClientLink` | **0** строк |

Все восемнадцать «клиентских» визитов привязаны к **одному аккаунту — аккаунту
владельца**. Причина видна в коде: строка появляется, когда
`listClientAppointments` тянет из CRM записи **по телефону вошедшего аккаунта**
(`appointments.service.ts:407-432`).

**Вывод:** `clientId` сегодня означает *«аккаунт Maya, в чей кабинет
материализовалась эта строка»* — то есть **User/Membership identity**, а не
идентичность клиента салона. Он отвечает на вопрос «кому это показывать», а не
«кто пришёл стричься».

Отсюда и разрыв «1 из 413»: зеркало наполняется не записями салона, а тем, что
увидел в своём кабинете один аккаунт.

## 2. Все потребители — по категориям

47 обращений в 4 файлах.

| Категория | Где | Что делает | Готовность к `null` |
|---|---|---|---|
| **A. Личный кабинет клиента** | `appointments.service.ts` (28), `tenant-appointment.repository.ts` (10) | «мои записи», отмена, перенос — всё в контексте вошедшего аккаунта | требует аккаунта **по смыслу**; `null` сюда просто не попадёт |
| **B. Аналитика** | `operations-analytics.service.ts` (9) | уникальные клиенты, повторность | **уже терпит `null`**: тип `clientId: string \| null` (`:28`) и явная проверка `typeof visit.clientId === 'string'` (`:895`) |
| **C. AI-слой** | `ai-tool-handler.service.ts` (2) | досье и мотивация мастера | **уже терпит `null`**: `clientId: string \| null` (`:3445`) |

🔴 Существенное для цены варианта: **два из трёх контуров уже написаны под
отсутствующего клиента**. Ослабление не «ломает 47 мест» — оно затрагивает
контур A, который по смыслу и должен работать только с аккаунтом.

## 3. Целевая связь `Appointment → Client`

```
Appointment
  ├─ clientRef  → Client.id        // КТО пришёл (идентичность Maya, глава 2)
  └─ clientId   → User.id          // ЧЕЙ это кабинет (аккаунт), опционально
```

Разделение отвечает ровно на два разных вопроса, которые сегодня слиты в одном
поле. Внешняя запись салона получает `clientRef` (или ничего, §7) и **не
получает** `clientId`, пока клиент не завёл аккаунт.

---

## 4. Связь с аккаунтом и членством

`clientId` остаётся, но становится **опциональным**, и вместе с ним опциональной
становится связь с `Membership`.

Что теряется и это надо назвать: сегодня обязательная пара
`(clientId, tenantId) → Membership` гарантирует, что визит не может ссылаться на
человека без членства в арендаторе. После ослабления гарантия остаётся только
для строк, где аккаунт есть. Для строк без аккаунта её заменяет
`(id, tenantId)` и ключ `(tenantId, crmProvider, crmExternalId)`.

## 5. Запись CRM без аккаунта Maya

```
Appointment {

  crmExternalId   = '1912557456'

  staffId         = Staff.id | null

}
```

Идентичность визита держится на `(tenantId, crmProvider, crmExternalId)` —
ограничение уже стоит с B1 и проверено на клоне прода.

## 6. Разрешение клиента через `CrmClientLink`

Путь уже существует и не используется: `ClientIdentityService` регистрирует
`Client` + `CrmClientLink` по паре (провайдер, внешний id клиента), а телефон
хранит **только как HMAC**, не как значение.

Сверка вызывает тот же путь: у записи есть `client.id` провайдера, значит
`clientRef` разрешается **по внешнему идентификатору клиента**, а не по телефону.

---

## 7. Политика неразрешённого клиента

| Ситуация | Решение |
|---|---|
| у записи есть `client.id` провайдера | `clientRef` = `Client.id` через `CrmClientLink` |
| клиента у записи нет вовсе | `clientRef = null`, визит **всё равно зеркалируется** |
| телефон совпадает с чьим-то аккаунтом | 🔴 **не склеиваем**; связь появляется только через доказанный путь идентичности |

Идентичность визита при этом не теряется никогда: она не зависит от клиента.

## 8. Мастер

Без изменений: `staffId` → `Staff.id` через `StaffProviderLink`, резолвер уже
работает (P7.1). Мастер, которого нет в связях, даёт `staffId = null` — визит
зеркалируется, идентичность мастера остаётся неразрешённой и видимой.

Изменений не требует.

## 10. Ограничения арендатора

| Что | Как |
|---|---|
| `Appointment` ↔ `Client` | составной ключ `(clientRef, tenantId)` → `Client(id, tenantId)` — как у `CrmClientLink` |
| `Appointment` ↔ `Staff` | уже составной `(staffId, tenantId)` |
| `Appointment` ↔ `User` | остаётся обычным, но становится опциональным |
| уникальность визита | внутри арендатора |

Межарендаторное смешение остаётся невозможным на уровне БД — проверено вставкой
в B1.

## 11. Каскады и удаление

| Связь | Сейчас | Предлагается | Почему |
|---|---|---|---|
| `client (User)` | `onDelete: Cascade` | `SetNull` | удаление аккаунта не должно стирать **факт визита салона**: это история бизнеса, а не данные аккаунта |
| `clientMembership` | `Cascade` | связь снимается | членство больше не обязательный носитель |
| `clientRef (Client)` | — | `SetNull` | то же основание |
| `staff` | `Restrict` | без изменений | |

🔴 Смена `Cascade → SetNull` у аккаунта — **изменение поведения**: сегодня
удаление пользователя уносит его визиты. После правки визит останется без
аккаунта. Для 152-ФЗ это безопаснее (в визите нет ПД клиента), но решение ваше.

## 14. Порядок миграции потребителей

```
1. Схема: clientId → nullable, clientRef добавлен, каскады изменены.
2. Контур A (кабинет): запросы уже фильтруют по clientId — строки с null
   в них просто не попадают. Проверить, что «мои записи» не изменились.
3. Контур B и C: изменений не требуют — они уже терпят null.
4. Сверка начинает писать строки с clientId = null.
5. Только после этого включается расписание сверки.
```

Порядок обязателен: сначала схема и проверка кабинета, потом писатель.

## 16. Откат

| Объект | Откат |
|---|---|
| `clientRef` | `DROP COLUMN` — поле nullable, потребителей в проде нет |
| `clientId` nullable | обратно `NOT NULL` возможно, **пока нет строк с null** |
| каскады | восстанавливаются `ALTER TABLE` |

🔴 Точка невозврата — первая строка с `clientId = null`. До неё откат
безболезненный, после — потребует решения, что делать с зеркальными визитами.
Поэтому §14 ставит включение писателя последним шагом.
