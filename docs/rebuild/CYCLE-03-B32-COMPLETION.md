## Счётчики

### Сухой прогон

```
windows 4 · fetched 1969 · complete 4 · truncated 0
would_create 1968 · would_update 0 · unchanged 1
client_resolved 0 · client_unresolved 1969
staff_resolved 1969 · staff_unresolved 0
cancelled_or_deleted 219 · collisions 0
```

### Наполнение

```
would_create 1922 · unchanged 47 · would_update 0
appointments 18 → 1940 · DomainEvent 1 → 1
```

🔴 **Почему сухой прогон и наполнение дали разные числа создания.** Соседние
окна делят граничную дату, а провайдер фильтрует **по дате**, не по времени:
запись на стыке приходит дважды. В сухом прогоне ничего не пишется, поэтому
второе появление снова считается «создали бы»; при наполнении первое окно уже
создало строку, и второе видит её существующей.

`1922 + 47 = 1969` — сходится. Счётчик сухого прогона **завышает** создание
ровно на число записей на стыках окон. Это свойство измерения, а не расхождение
данных, и я называю его прямо, чтобы число из отчёта не считали точным
предсказанием.

## Отменённые и удалённые

219 записей пришли со статусом `canceled` и **сохранены в зеркале**: отмена — это
факт, а не исчезновение.

🔴 **Оговорка честности.** Провайдер отдаёт только признак `deleted`; отдельного
признака «отменена клиентом» в разбираемых полях нет. Наш канон сворачивает оба
в один статус `canceled`. Различать их сейчас было бы угадыванием — записываю
как отложенную находку, а не как реализованное различие.
