## 0. Что зеркало хранит на самом деле

Проверено на боевой базе после наполнения:

| Статус | Записей |
|---|---|
| `completed` | 1688 |
| `canceled` | 214 |
| `confirmed` | 23 |
| `no_show` | 15 |

🔴 **Отдельной колонки присутствия в зеркале НЕТ.** Присутствие свёрнуто в
`status` нашим же маппером (`recordStatus`), и свёрнуто **вместе с оплатой**:

```
deleted            → canceled
attendance = -1    → no_show
attendance = 1  ИЛИ paid_full → completed     ← две разные вещи в одном слове
иначе              → confirmed
```

Это меняет §7 задания. Утверждение «теперь зеркало хранит attendance» верно лишь
наполовину: оно хранит **следствие**, в котором приход клиента неотличим от
закрытия оплаты.

**Прямое следствие:** событие `appointment.attendance_recorded`, выпущенное по
переходу `confirmed → completed`, повторило бы ложь, которую B2 уже поймал —
имя утверждало бы приход, а данные допускали оплату. Поэтому честных вариантов
два: либо хранить присутствие отдельной колонкой (**гейт схемы**), либо не
выпускать событие о присутствии вовсе.

## 2. Каноническое состояние для сравнения


## 3. Семантика создания

`appointment.created` допускается, только если выполнены все три:

1. базовая линия наблюдения арендатора установлена (`watchStartedAt` заполнен —
   на проде `2026-08-17 17:02:47`);
2. записи с этим `(арендатор, провайдер, внешний id)` в зеркале **не было**;
3. наблюдение полное: либо проход сверки `complete`, либо вебхук по конкретной
   записи (он адресный и усечением не страдает).

Первый проход наполнения событием создания **никогда** не является — это уже
доказано в B3.2: 1922 записи созданы, событий ноль.

## 4. Схождение вебхука и сверки — один компаратор, два триггера

🔴 Главное решение плана. Оба пути делают **одно и то же**:

```
триггер (вебхук ИЛИ сверка)
   ↓ прочитать истину у источника
   ↓ сравнить с зеркалом
   ↓ вывести переходы по правилам §1
   ↓ В ОДНОЙ ТРАНЗАКЦИИ: обновить зеркало + записать события
```

Различие между путями — только в том, что их запустило.

### Почему одна транзакция обязательна

Если зеркало обновить, а событие не записать — переход исчезнет навсегда:
следующий проход сравнит новое состояние с новым и не увидит разницы.
Если записать событие, но не обновить зеркало — следующий проход выпустит его
второй раз. Разрыв между двумя коммитами и есть та самая проблема, ради которой
Phase A назвала transactional outbox.

### Дедупликация между путями

| Уровень | Механизм |
|---|---|
| одинаковый переход, оба пути | один отпечаток → уникальность `(tenantId, dedupFingerprint)` в базе |
| повторная доставка вебхука | зеркало уже обновлено ⇒ разницы нет ⇒ `no_observable_change` |
| гонка вебхука и сверки | транзакция сериализует: второй увидит уже обновлённое зеркало |

Отпечаток включает тип события — значит два разных перехода одной записи не
подавляют друг друга.

## 5. Несколько изменений сразу

**Правило: сколько доказано различимых фактов — столько событий.**
Изменились время, мастер и состав — три события с общим `occurredAt` и
возрастающим `entitySequence`.

Обоснование для будущего UNDERSTAND: «перенос» и «смена мастера» — разные
бизнес-факты с разными последствиями (первый касается клиента, второй —
загрузки мастера). Свернув их в `appointment.updated`, глава 4 получила бы
событие, из которого нельзя ничего заключить, и вынуждена была бы разбирать
полезную нагрузку — то есть заново выводить то, что мы уже знали.

Порядок событий детерминирован (фиксированный порядок проверок §1), поэтому оба
пути дают одинаковый набор и одинаковую последовательность.

## 6. Отмена и удаление

Провайдер даёт **только** `deleted`. Отдельного признака «отменена клиентом» в
разбираемых полях нет — доказано в Phase A.

**Предложение:** назвать событие `appointment.removed` — «запись больше не
активна у провайдера». Это ровно то, что доказуемо.

🔴 Это **переименование** существующего типа `appointment.cancelled` из словаря
B1. Цена нулевая: событий этого типа в проде **ноль** (единственная строка —
`attendance_recorded`). Позже, если провайдер начнёт различать, `removed`
распадётся на два типа новой версии контракта.

Статус в зеркале остаётся `canceled` — это наш канон состояния, менять его
сейчас не нужно.

## 8. Цикл сверки

### Ритм — из измеренного объёма

| Контур | Окно | Частота | Запросов в сутки |
|---|---|---|---|
| ближний | −2 … +7 дней | 30 мин | ~48 |
| средний | −31 … +31 день | 1 раз в сутки | ~4 |
| исторический | вручную | по решению | — |

Основание: 1969 записей за 121 день ≈ 16 в сутки; окно ±7 дней — около 230
записей, это 2 страницы. Потолок провайдера ~200 запросов в минуту, наш расход —
около 50 **в сутки**.

### Состояние сверки — чего не хватает

`CrmIntegration.lastSyncAt` есть (на проде `2026-08-15`, устарел и пишется не
сверкой), но это **одна метка** без окна, полноты, счётчиков и ошибок. Для §8
недостаточно.

```
B3.3 SCHEMA GATE REQUIRED: YES
```

Предварительный состав (точная схема — в гейте):

```
ReconciliationRun
  id, tenantId, provider
  windowFrom, windowTo
  startedAt, finishedAt
  completeness          — complete | truncated
  fetched, created, updated, unchanged
  eventsEmitted
  failureCode, failureMessage
  @@index([tenantId, startedAt])
```

Плюс `Appointment.attendance` из §7, если утвердите вариант A.

## 9. Первая живая проверка перехода

🔴 Реальную бронь живому клиенту ради теста не создаём.

Порядок предпочтения:

1. **Естественный переход.** Поток даёт ~21 запись в сутки и десятки
   обновлений; ждать придётся часы, не дни. Наблюдаем и фиксируем первый

2. **Служебная запись владельца.** Если ждать нельзя — владелец сам переносит
   собственную запись в CRM (их 18 в зеркале). Это его данные и его решение;

3. Синтетика в CRM **не создаётся**: запись в боевом салоне видна мастерам и
   попадает в отчётность.

Проверяется: одно событие на переход, повторная доставка не даёт второго,
сверка после вебхука видит `no_observable_change`.
