## Главный результат

Вебхук и сверка перестали быть двумя реализациями одного правила. Теперь это два
триггера одной службы:

```
триггер → прочитать истину у источника → привести к канону
        → сравнить с зеркалом → детерминированные переходы
        → зеркало + события ОДНОЙ транзакцией
```

Первый боевой проход сверки заполнил присутствие у **147** визитов и создал
**ноль** событий — ровно так, как обещано: первое наблюдение изменением не
является.

---

## Что оказалось не так, как выглядело

### 🔴 Карточка визита выдумывала присутствие ещё в адаптере

`attendanceFromCode` отвечает `awaiting` и когда поля не было вовсе, и когда
пришёл незнакомый код:

```ts
if (typeof code !== 'number') return 'awaiting';
return CODE_TO_ATTENDANCE.get(code) ?? 'awaiting';
```

Пока значение шло только на экран, это было терпимо — экрану нужно что-то
нарисовать. Для зеркала — нет: выдуманное `awaiting` осело бы в базе, а
следующий проход выпустил бы событие о переходе, которого не было.

Подстановка по умолчанию переехала на HTTP-край, где живёт остальной провод.
Внутрь системы приезжает `null`. **Выпущенный PWA не затронут**: контроллер
по-прежнему отдаёт число.

**Цифры показывают, что различие не теоретическое.** После первого прохода:

| Состояние | Записей | Что это значит |
|---|---|---|
| `arrived` | 119 | провайдер сказал: клиент пришёл |
| `awaiting` | 25 | провайдер сказал: отметки ещё нет |
| `no_show` | 3 | провайдер сказал: не пришёл |
| `NULL` | 1793 | Maya не спрашивала (вне окна сверки) |

До B3.3 первая и последняя строки были бы одним и тем же словом.

### 🔴 Канонический журнал присутствия не переносил вовсе

Из него наполняется зеркало, а `attendance` жил только в карточке одного визита
и был свёрнут в `status` вместе с оплатой. Расширен контракт журнала, а не
заведён второй словарь: тип тот же, из главы 2.

### 🔴 Повторное наполнение зеркала стало опасным — из-за этого же пакета

Наполнение пишет зеркало и НЕ выпускает событий: это его смысл. Но теперь у
зеркала есть второй писатель, который события выпускает. Прогон наполнения
поверх уже наблюдаемого арендатора молча перезаписал бы состояние и потерял
переходы навсегда — следующая сверка сравнила бы новое с новым.

Скрипт наполнения после установленной базовой линии работает только сухим
прогоном. Замок в коде, а не в комментарии.

| # | Решение | Как сделано |

Мок конвергенцию и атомарность доказать не может: и то и другое — свойства базы.
Прогон на чистой базе из миграций, **19 проверок, провалов ноль**:

```

✅ несколько изменений — детерминированный порядок в базе
   ["1:rescheduled","2:staff_changed","3:services_changed","4:attendance_changed"]
✅ снятие поглощает остальные переходы — ["appointment.removed"]
✅ повторная доставка не даёт второго события — событий 1, выпущено 1/0/0
✅ webhook-first: одна строка · одно событие · второй путь 0 · одно состояние
✅ reconciliation-first: одна строка · одно событие · второй путь 0 · одно состояние
```

**Атомарность проверена принуждением, а не намерением:** триггер в базе роняет
вставку события; если бы зеркало и события шли разными коммитами, зеркало
осталось бы изменённым. Оно не изменилось.

## 🔴 Чего НЕ доказано

**Органический переход в бою не наблюдался.** Салон закрыт (проверка шла в
00:0x МСК), переходов присутствия ночью не бывает. Реальную запись клиента ради
теста я не менял — ваше правило.

Что это значит честно: механика перехода доказана на настоящей базе во всех
режимах, но ПЕРВЫЙ живой переход у боевого провайдера ещё не проходил через
систему. Проверяется одним запросом после рабочего дня:

```sql
SELECT type, "entitySequence", "occurredAt", "ingestionMethod"
FROM "DomainEvent" WHERE "entityType" = 'appointment' ORDER BY "receivedAt" DESC LIMIT 20;
```

Пока там одна строка — проба B2.
