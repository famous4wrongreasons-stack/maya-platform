## 1. Что сегодня служит событиями

Шины событий нет — это доказано в главе 2. Роль событий выполняют четыре разные
вещи, и ни одна не является событием в смысле главы 3.

| Что | Где | Чем на самом деле является |
|---|---|---|
| Вебхук YCLIENTS | Python `webhook_server.py:1692` | **триггер перечитывания**, а не факт |
| `InboxItem` | `schema.prisma:1581` | сообщение **получателю**, не факт бизнеса |
| `AuditLog` | `schema.prisma:1374` | след действия **пользователя**, не изменения в CRM |
| `record_state` (SQLite бота) | `database.py:134` | снимок состояния для сравнения |

🔴 Ни один из них не различает «когда произошло» и «когда мы узнали».
`InboxItem` и `AuditLog` имеют только `createdAt`.

### Что уже есть и годится как образец

Три модели уже несут `occurredAt` **и** ключ дедупликации от источника:

| Модель | Ключ | Время |
|---|---|---|
| `BusinessReview` | `@@unique([tenantId, source, externalRef])` | `occurredAt` |
| `Expense` | `@@unique([tenantId, externalId])` | `occurredAt` |
| `RecoveryTouchpoint` | `@@unique([tenantId, externalEventId])` | `occurredAt` |

Плюс семь моделей с `@@unique([tenantId, idempotencyKey])` (глава 1 P5).
**Форма ключа в доме уже принята — изобретать не нужно.**

## 2. Опись входящих путей

### 2.1 Топология вебхука YCLIENTS

```
YCLIENTS
  ↓  HTTPS
malesthetic.pro/yclients-webhook.php        (Beget, PHP-реле)
  ↓  HTTP + общий секрет
VPS :8080 /yclients-webhook                 (Python, aiohttp)
  ↓  перечитывание записи через API YCLIENTS
Telegram / web-push мастеру                 ✅ работает
  ↓  мост в Maya OS
POST :3107 /api/inbox/internal/ingest       ❌ 403, см. 2.4
```

| Свойство | Факт |
|---|---|
| Проверка источника | **общий секрет** в заголовке `X-Webhook-Secret` или в query (`webhook_server.py:1683-1689`) |
| Подпись провайдера | **нет** |
| Идентификатор события от провайдера | **нет ни в одном из трёх известных форматов** (`webhook_server.py:164-194`) |
| Арендатор | не определяется вовсе: бот однопользовательский, компания зашита в конфиге |
| Повторы | **есть, измерено**: до 7 доставок одной пары (событие, запись) |
| Порядок | не гарантирован; `create` и `update` одной записи приходят с разницей в секунды |
| Дедупликация | `processed_records` (SQLite), ключ — **только `record_id`** |
| Сравнение состояний | `record_state`: `staff_id`, `datetime`, `services_sig`, `attendance` |

### 2.2 Что реально приходит — измерено за 7 суток

| Тип | Доставок |
|---|---|
| `record.update` | **288** |
| **не распознано** (`event=None`) | **221** |
| `record.create` | **126** |
| `record.delete` | **7** |
| Всего с `record_id` | 421 |
| Уникальных записей | **148** |
| Пар с повторами | 74 |

**Коэффициент размножения ≈ 2.8×.** Это не теория — это боевой журнал.

🔴 **221 нераспознанная доставка — треть всего потока.** `_extract_record_event`
возвращает `(None, None)`, когда `resource != "record"` или событие не
начинается с `record.`. То есть провайдер, по всей видимости, шлёт события и о
других сущностях, а мы их **молча выбрасываем**. Тела не логируются, поэтому
**что именно это — UNKNOWN**. Установить можно только безопасным захватом типа
ресурса (без ПД) — это первый пункт Phase B.

| Маршрут | Защита | Кто вызывает | Состояние |
|---|---|---|---|
| `POST /api/inbox/internal/ingest` | `@Public()` + токен моста | Python | **403 в бою** |

Обоим нужен `tenant_slug` в теле — арендатор ищется по слагу

### 2.4 🔴 Главная находка: единственный путь событий в Maya OS сломан

Бот настроен на слаг `MAYA_INBOX_TENANT_SLUG=muzhskaya-estetika`.
Такого арендатора **не существует** — есть `muzhskaya-estetika-3`.

Доказательство из боевого журнала бота (17.08, за сутки — десятки):

```
WARNING | inbox ingest HTTP 403: {"error":{"code":"inbox_tenant_not_found"}}
```

За 7 суток — **37 отказов**. В `InboxItem` всего 4 строки, и все четыре —
`daily_report` / `morning_brief`, созданные **планировщиком Nest** внутри
процесса (`publishForTenant`, слаг не нужен). Строк типов моста
(`new_appointment`, `shift_reminder`, `appointment_reassigned`, `hanging_lead`)
в проде **ноль**.

**Следствие:** мастер получает уведомление в Telegram, а Maya OS о записи не
узнаёт вообще. Глава 3 строится не на пустом месте, а на **разорванном** месте.

## 3. Аудит опроса (polling)

**Полноценного опроса CRM в системе нет.** Единственные циклы в Python —
опрос статуса платежа ЮKassa (`bot.py:4522`, `:5068`), к CRM отношения не имеют.

| Поток | Что наблюдает | Вердикт |
|---|---|---|
| Вебхук YCLIENTS | записи | **KEEP** — единственный источник низкой задержки |
| Опрос ЮKassa | платежи | **KEEP**, вне области главы 3 |
| Отчёты владельца (5 мин) | агрегаты CRM | **KEEP**, но это отчёт, а не наблюдение за изменениями |
| Ленивый импорт «Мои записи» | записи клиента | **REPLACE**: должен стать следствием событий, а не их источником |
| Сверка команды | состав мастеров | **KEEP AS RECONCILIATION** |

🔴 **Вывод, который стоит назвать прямо:** сегодня у Maya **нет механизма
догоняющей сверки записей**. Если вебхук не дошёл — не узнает никто и никогда.
Отсюда обязательный пункт плана: сверка (§8.6), а не только приём.

## 5. Готовность идентичностей

| Сущность | Идентичность Maya | Годится для события |
|---|---|---|
| Мастер | `Staff.id` + `StaffProviderLink` | **да** (внутренний мастер — нет, строки `Staff` у него нет) |
| Клиент | `Client.id` + `CrmClientLink` | **модель есть, данных нет**: 0 строк, никто не читает |
| Визит | `Appointment.id`, `crmExternalId` | 🔴 **нет**, см. ниже |
| Услуга, филиал, касса | своей идентичности нет | нет |

### 🔴 Разрыв идентичности визита

У `Appointment` **нет уникальности по внешнему идентификатору**: есть только
`@@unique([id, tenantId, clientId])`. Поиск идёт `findFirst` по
`(tenantId, clientId, crmExternalId)` — то есть **в пределах клиента**.

Значит: событие о записи из CRM сегодня **невозможно надёжно связать с одной
строкой Maya**. Два независимых пути приёма создадут два визита на одну запись
CRM, и база этому не помешает.

Это первый кандидат в **Schema Gate**.

## 6. Где нужна транзакционная развязка (outbox)

Найдено три места, где Maya пишет своё и сразу пытается сообщить об этом:

| Место | Запись | Сообщение | Разрыв |
|---|---|---|---|
| `appointments.service.ts:257` | создание визита | `void publishNewAppointmentInbox(...)` | **есть** |
| `:633` | отмена | `void publishAppointmentLifecycleInbox(...)` | **есть** |
| `:884` | перенос | то же | **есть** |

Все три — «выстрелил и забыл» с `.catch(...)` в лог. Падение процесса между
фиксацией строки и отправкой теряет факт **навсегда**: повторить некому.

Это и есть настоящая причина для outbox — не мода на архитектуру, а три
конкретные строки `void this.publish…`.

## 7. Решения, которые Phase A обязана принять

### 7.1 Отдельное хранилище событий — **ДА**

Причина не «так принято», а три проверяемых требования: пережить перезапуск,
уметь повторную обработку, различать три времени. Ни `InboxItem` (адресован
получателю), ни `AuditLog` (действие пользователя) этого не дают.

### 7.2 Очередь (Kafka/Rabbit/SQS) — **НЕТ**

| Мера | Значение |
|---|---|
| Арендаторов | 2 |
| Событий от провайдера | ~60 доставок в сутки |
| Узлов | один |
| Требование к задержке | секунды, не миллисекунды |

PostgreSQL с `FOR UPDATE SKIP LOCKED` покрывает это с запасом. Брокер добавил бы
второй источник истины и второй способ потерять сообщение. Контракт события
пишется так, чтобы транспорт можно было заменить, **не трогая домен**.

### 7.3 Семантика доставки

**AT-LEAST-ONCE + идемпотентная обработка.** Ровно-однократность не обещаем:
провайдер не даёт идентификатора события, и обещать её было бы враньём того же
рода, что чинили в главе 2.

### 7.4 Идентичность события

Идентификатора события от провайдера **нет**. Поэтому ключ дедупликации —
**детерминированный отпечаток факта**:

```
dedupKey = sha256(
  tenantId | source | entityType | entityId | eventType | stateFingerprint
)
```

где `stateFingerprint` — канонический снимок значимых полей (мастер, время,
состав услуг, присутствие). Это ровно то, что легаси уже делает в `record_state`
— только там оно живёт в SQLite бота и не переживает смену владельца.

🔴 Дедупликация **не** на времени: два одинаковых чтения обязаны дать один ключ.

### 7.5 Три времени

| Поле | Смысл |
|---|---|
| `occurredAt` | когда изменение произошло в бизнесе (из данных провайдера) |
| `receivedAt` | когда Maya приняла доставку |
| `processedAt` | когда обработала |

Совпадающими не считаются никогда: между `create` и `update` одной записи в бою
проходят десятки минут, а доставки приходят пачками.

### 7.6 Версионирование

`type` + целочисленный `version`: `appointment.created` v1. Смена формы полезной
нагрузки — новая версия, старые события остаются читаемыми. Имя типа без
номера в строке: номер в отдельной колонке, иначе его нельзя фильтровать.

### 7.7 Порядок

Глобального порядка не обещаем. Порядок нужен **в пределах сущности**:
`created → rescheduled → cancelled`. Реализация — `occurredAt` плюс
монотонный `entitySequence` на сущность. Событие с меньшим `occurredAt`, чем уже
известное состояние, помечается `STALE`, а не применяется молча.

### 7.8 Модель отказов

`INGESTION_FAILED`, `NORMALIZATION_FAILED`, `PERSISTENCE_FAILED`,
`PROCESSING_FAILED`, `DUPLICATE`, `STALE`. Каждый — **видимый** исход, а не
тишина. Прямое наследование урока главы 6 P6: «не умею» ≠ «пусто».

### 7.9 Первичное наблюдение (bootstrap)

При подключении CRM Maya видит уже существующий бизнес. Поэтому у события есть
происхождение наблюдения:

| Значение | Когда |
|---|---|
| `OBSERVED_EXISTING` | найдено при первом сканировании |
| `CREATED_AFTER_WATCH_STARTED` | изменение после начала наблюдения |

Момент начала наблюдения фиксируется на арендатора. Без этого первое включение
породит тысячи ложных «создано сегодня».

### 7.10 Приватность

В полезной нагрузке — идентичности Maya и минимальный факт. Ни имени, ни
телефона, ни email. Контур 152-ФЗ главы 2 не ослабляется. Сырое тело провайдера
в хранилище событий **не кладём**; если понадобится для разбора — отдельная
таблица с собственным сроком хранения, и это отдельное решение.

## 8. План Phase B

Порядок обязателен: каждый шаг проверяем до следующего.

### B0 — Узнать, что мы выбрасываем *(без изменения схемы)*

Безопасный захват **типа ресурса** нераспознанных доставок (221 за 7 суток) —
без тел и без ПД. Пока мы не знаем, что это, словарь событий будет угадыванием.

### B1 — SCHEMA GATE *(STOP, применение только после вашего одобрения)*

Гейт обязан разобрать минимум:

1. `DomainEvent` — состав, ключи, индексы, привязка к арендатору.
2. Уникальность визита по `(tenantId, provider, externalId)` — сегодня её нет.
3. Отметка начала наблюдения на арендатора.
4. Нужна ли отдельная таблица для сырых тел (предложение: **нет**).

Предлагаемая форма — как ориентир, а не как готовая миграция:

```
DomainEvent
  id, tenantId
  type, version
  entityType, entityId          — идентичность Maya
  occurredAt, receivedAt, processedAt
  source, sourceReference       — провенанс
  observation                   — existing | after_watch_started
  dedupKey                      — @@unique([tenantId, dedupKey])
  entitySequence
  payload                       — минимальный факт, без ПД
  status, attempts, lastError
  @@index([tenantId, entityType, entityId, occurredAt])
  @@index([status, receivedAt])
```

### B2 — Приём в NestJS рядом с легаси *(теневой режим)*

Новый маршрут в границе интеграции. Python **не трогаем**: реле шлёт копию, или
Python пересылает копию. Nest только принимает, нормализует и сохраняет —
**никаких уведомлений и никаких действий**.

Порядок в приёмнике: проверить источник → определить арендатора → разобрать →
нормализовать → разрешить идентичности Maya → дедуплицировать → **сохранить** →
и только потом подтвердить источнику.

### B3 — Сравнение с легаси *(доказательство, а не вера)*

Неделя параллельной работы. Сверяем: сколько доставок увидел каждый, сколько
уникальных фактов, где расхождение. Легаси остаётся владельцем уведомлений.

### B4 — Обработчик событий

Захват задачи через `FOR UPDATE SKIP LOCKED`, аренда, повтор с отступом,
терминальный отказ. Первый потребитель — **проекционный**: поддерживает зеркало
визита в Maya. Никаких внешних действий: их место в главе 6.

### B5 — Сверка

Периодическая догоняющая сверка окна записей. Уже известные факты **не** порождают
повторных событий — та же дедупликация. Это лечит §3: сегодня пропущенный вебхук
не заметит никто.

### B6 — Внутренний календарь как источник

Внутреннее изменение даёт тот же `appointment.created` с другим провенансом.
Здесь же снимается разрыв outbox (§6): событие пишется **в одной транзакции** с
визитом, а рассылка становится потребителем.

🔴 Зависимость: у внутреннего мастера нет строки `Staff` (реестр переноса 3.3).
Без неё событие внутреннего календаря не сошлётся на идентичность Maya.

### Чего Phase B НЕ делает

- Не удаляет ни Python-вебхук, ни мосты (правило §16 брифа).
- Не вводит брокер очередей.
- Не строит интерпретацию: ни `client.lost`, ни `opportunity`, ни `recovered`.
- Не рассылает уведомления из нового контура.
- Не начинает главу 4.

| `appointment.cancelled` | 1 | `record.delete` | 7 доставок | по сущности | да |
| `appointment.attendance_recorded` | 1 | `record.update` + смена присутствия | поле `attendance` | то же | да |

### Чего НЕ вводим в главе 3 — и почему

| Кандидат | Причина |
|---|---|
| `client.created` / `client.updated` | не наблюдаемо: событий о клиенте в потоке не доказано (см. 221 неизвестную доставку) |
| `staff.*` | приходит только сверкой по требованию, не потоком |
| `schedule.changed` | производный факт, а не источник |
| `transaction.observed` | касса приходит **чтением** аналитики, а не событием |
| `client.lost`, `revenue.recovered` | интерпретация, главы 4–7 |

`appointment.completed` и `appointment.no_show` намеренно не заводим отдельными
типами: провайдер отдаёт **присутствие**, а не «завершён». Канон присутствия уже
есть в домене (глава 2 P3) — событие несёт его, а вывод делает глава 4.

## 10. Наблюдаемость и хранение

Считать: принято, дедуплицировано, сохранено, обработано, отказано, попыток,
возраст самого старого необработанного — в разрезе арендатора, источника, типа.

обработанные события — усечение полезной нагрузки через N месяцев с сохранением
факта; ничего не удалять автоматически до утверждения политики.
