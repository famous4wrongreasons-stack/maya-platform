### Четыре состояния — типом, а не соглашением

```ts
type BusinessFactState =
  | 'measured'            // выборка полна: ноль означает «ноль»
  | 'measured_incomplete' // число есть, но ноль ничего не доказывает
  | 'not_measured'        // источник этого здесь не измеряет
  | 'unavailable';        // источник не ответил
```

`allowsAbsenceConclusion(fact)` — единственный владелец вопроса «можно ли по
этому факту заключить, что чего-то нет». Вызывающий больше не сравнивает
строки статуса сам: именно так неполнота и превращалась незаметно в
доказанный ноль.

У `not_measured` есть боевой производитель, а не только тест: внутренний
календарь присутствия не ведёт вовсе — значения не будет никогда, а не «пока».

## 2. Присутствие: один владелец вместо двух правил

🔴 **Корень, найденный состязательной проверкой.** В адаптере жили ДВА правила
присутствия:

```
hasAttendance(record, v)   →  record.attendance === v ИЛИ record.visit_attendance === v
observedAttendance(record) →  attendance ?? visit_attendance   (приоритет первому)
```

Первое питало `status`, второе — канон. На записи
`{attendance: 0, visit_attendance: -1}` они расходились буквально: статус
говорил **«неявка»**, канон — **«клиент ещё не приходил»**, и обе величины
уезжали наружу в одном ответе. Проверено запуском адаптера, а не рассуждением.

`hasAttendance` удалён. `recordStatus` спрашивает канон, `getClientVisitHistory`
спрашивает канон. Расходиться нечему по построению.

**Что это чинит по цепочке.** `appointments_no_show` считается из статуса и
печатается владельцу как «Неявок: N». Пока статус стоял на втором правиле, это
число могло противоречить каноническому блоку присутствия в том же ответе.
Теперь `status = no_show` ⟺ каноническое присутствие `no_show`.

`completed` при этом остаётся словом ПРОВАЙДЕРА и по-прежнему означает
«отмечен приход ИЛИ оплачено» — переопределять его молча было бы подменой.
Сколько человек действительно пришло, отвечает отдельный факт:

```
attendance: { arrived, no_show, awaiting, not_observed, records }
```

Боевое доказательство, что это разные вещи, лежит в базе: строка
`completed / awaiting` — визит помечен проведённым, при том что провайдер
прямо утверждает, что отметки о приходе нет.

Удалённая запись присутствия НЕ даёт: провайдер сообщает, что записи больше
нет, и отметка на ней — след прошлого состояния. Одно событие не считается
дважды.

## 3. Отмены: противоречие снято на обеих ветках

Было: `appointments_cancelled` попадала в `available_metrics` (у неё есть
число) и одновременно в `unavailable_metrics` с объяснением «ноль означает не
измерено». Один ответ утверждал про одну метрику две противоположные вещи.

Первая правка сняла противоречие только на ПОЛНОЙ выборке. Скептик показал,
что на усечённой оно осталось. Исправлено по смыслу списков:

| Список | Что означает |
|---|---|
| `unavailable_metrics` | числа **нет** (когорты, присутствие, деньги мастера) |
| `limitations` | число **есть**, но означает не то, что кажется |

Семантика отмены усилению не подлежит: провайдер сообщает только факт удаления
записи (реестр 3.6). Кто удалил и почему — не часть контракта, и оговорка
`cancellation_reason` присутствует всегда.

Инвариант закреплён тестом на всех четырёх комбинациях полноты и наблюдения
присутствия: **ни одна метрика не объявляется недоступной, будучи доступной**.

## 4. Окно: ответ источника окном не является

Реестр 3.8 измерил это на боевых данных: провайдер вернул 17 записей 2024–2025
годов на окно 2026-го. Фильтр по периоду был ровно у одного читателя из трёх.

Теперь окно и полнота собираются в одной чистой функции
(`collectPeriodRecords`), и её применяют все: обзор, журнал дня, клиентский
срез, история для мотивации. Отброшенное считается и называется
(`out_of_period_discarded`), а не выбрасывается молча — иначе смену контракта
провайдера заметить нечем.

Границы периода включительны с обеих сторон — ровно как было до P0. Сутки в
журнале дня стали `[00:00 … 23:59:59.999]`: полночь следующего дня в них
больше не входит.

## 8а. Где я вышел за буквальные пять пунктов — и почему

Ваш P0 перечислял пять предметов. Три правки лежат рядом с ними, и я называю

| Правка | Основание |

| Пометка о неполноте в утреннем брифе, брифе мастера и вечернем отчёте | §1 сформулирован абсолютно: «нельзя выдавать нулевую метрику без информации, позволяет ли источник заключить, что значение действительно равно нулю».
