# CYCLE 04 P2 — REVENUE / BOOKED VALUE SEPARATION

> Релиз `20260818-c04-p2-revenue-split`. Схема не тронута, персистентности нет.
>
> Двусмысленность снята полностью. Равенство с кабинетом **не достигнуто** — и
> не могло быть достигнуто без отмены действующего решения о раскрытии денег.
> Это гейт, а не недоделка.

---

## 1. Что было сломано

В денежной ветке композиции поле `revenue` **перезаписывалось** подтверждённой
кассой, а снимок метрик брал «стоимость записанного» из того же поля. Одно поле
после композиции означало два разных факта — в зависимости от того, ответил ли
финансовый контур.

Измерено в бою 18 августа: AI отдавал **60 105 000** копеек и как кассу, и как
стоимость записанного; настоящая стоимость записанного была **61 250 000**.

---

## 2. Что сделано

Стоимость записанного снимается **до** любых замен, живёт в собственном поле и
имеет собственное основание:

```
revenue_amount_kopecks      + revenue_basis       (provider_transactions | booked_prices | unavailable)
booked_value_amount_kopecks + booked_value_basis  (booked_prices | unavailable)
```

Основание выручки описывает **выручку**, а не «какое-нибудь число рядом»: у
арендатора на внешней CRM деньгами признаётся только кассовый контур, и нет
кассы — нет выручки. У внутреннего календаря другого понятия денег не
существует, там выручка честно стоит на ценах журнала.

Оба снимка метрик — салона и мастера — читают своё поле. Возврат к чтению из
перезаписанного запрещён тестом по исходнику: «`bookedValue = data.revenue[0]`»
больше не должно появиться нигде.

**Боевой случай сохранён фикстурой**, но не как вечная истина: 60 105 000 против
61 250 000 доказывают, что две величины законно расходятся и что касса больше
никогда не окажется в поле записанного.

---

## 3. 🔴 ГЕЙТ: почему равенства с кабинетом нет

Ожидание §10 — `canonical booked_value == dashboard booked value` — упирается в
решение, которое я не имею права отменить внутри пакета о разделении полей.

**Действующее правило (P7.1).** У арендатора на внешней CRM суммы цен журнала
**не выходят** из слоя бизнес-состояния вовсе: деньгами там признаётся только
кассовый контур. Правило охраняют три существующих теста, среди них дословно
«journal prices out of a CRM answer» и «цены журнала не подменяют кассу даже
без кассы». Это не побочный эффект, а осознанное решение о раскрытии денег.

**Что при этом делает кабинет.** Показывает владельцу ту же величину: на 18
августа — **61 270 000** копеек. То есть два контура применяют к одному числу
разные политики раскрытия.

**Что я сделал.** Снял двусмысленность (касса в поле записанного невозможна) и
впервые назвал пустоту причиной вместо молчания:

```
booked_value → "the AI layer does not publish journal price sums for a CRM
tenant: money there is recognised only through the financial contour
(fail-closed, P7.1). This is a disclosure decision, not a missing computation"
```

**Что решаете вы.**

| Вариант | Что меняется | Цена |
|---|---|---|
| **A. Публиковать** | канонический слой отдаёт стоимость записанного CRM-арендатору; равенство с кабинетом достигается; §10 выполняется | отменяется решение P7.1: суммы цен журнала начинают выходить в ответ AI. Три охраняющих теста переписываются. Модель получает величину, которую владелец может прочесть как выручку — ровно то, ради чего fail-closed и написан |
| **B. Оставить как сейчас** | ничего; двусмысленность уже снята, пустота названа | `canonical booked_value == dashboard booked value` недостижимо по построению, и §10 требует не мигрировать потребителей |
| **C. Публиковать под роль** | отдавать только тем, кому открыты деньги салона | компромисс: кабинет всё равно шире, полного равенства не будет |

Молча выбрать я не мог: §4 требует сохранить финансовые инварианты главы 2, а
раскрытие журнальных цен — один из них.

## 4. Боевая сверка после выката

Тот же период, два пути:

| Факт | AI | Кабинет |
|---|---|---|
| Записей | 325 | 325 |
| Отмен | 27 | 27 |
| Уникальных клиентов | 270 | 270 |
| Подтверждённая касса | **60 625 000** (`provider_transactions`) | не отдаётся |
| Стоимость записанного | **null**, причина названа | **61 270 000** |
| Полнота | `complete` | блока нет (снимается на краю кабинета) |
| Оговорки | `cancellation_reason`, `provider_window` | — |

Касса выросла с 60 105 000 до 60 625 000 между двумя измерениями — салон
работает, и это ровно та причина, по которой числа зафиксированы фикстурой как
пример, а не как истина.

🔴 **Главное:** ни одно число больше не встречается дважды под разными именами.

## 5. Обязательные тесты §9

| Требование | Как проверено |
|---|---|
| равные величины — два разных факта | внутренний календарь: одно число, два основания |
| величины расходятся | боевой случай: касса есть, записанное недоступно с причиной |
| записанное есть, денег нет | внутренний календарь без кассового контура |
| деньги есть, источник записей неполон | полнота `incomplete` + оговорка `incomplete_read` |
| финансовый вход неполон | касса `null`, основание `unavailable`, подмены нет |
| измеренный ноль кассы | `0` с основанием `provider_transactions` |
| измеренный ноль записанного | `0` c `booked_prices` отличим от `null` c `unavailable` |
| записи вне окна провайдера | оговорка `provider_window` называет число |
| снимок AI берёт правильный факт | эквивалентность: изменённые поля перечислены поимённо |
| ни один путь не выводит записанное из перезаписанного | тест по исходнику |

Плюс одиннадцатый, которого в списке не было: причина недоступности обязана
называть **решение**, а не изображать отсутствие данных.
