# CYCLE 04 P2.1 — BOOKED VALUE DISCLOSURE ALIGNMENT

> Релиз `20260818-c04-p21-booked-value`. Арифметика, источник и выручка не
> менялись. Схема не тронута. Мотивация мастера (4.22) не тронута.

---

## 1. Почему это не откат

P7.1 прятал суммы цен журнала целиком — и был прав: оба числа жили в одном
поле, и цены могли сойти за кассу. P2 развёл их физически. Правило, ради
которого пряталось, никуда не делось; оно теперь обеспечивается адресно:

| Запрещено | Разрешено |
|---|---|
| `bookedValue → revenue` | `bookedValue → booked_value` |
| `revenue_basis` = `booked_prices` у CRM-арендатора | `booked_value_basis` = `booked_prices` |

Это не возвращённое старое поведение, а **новый явно типизированный
операционный факт**.

## 2. Право решает вызывающий

Канонический слой ролей не знает — как и после P1. Решение приезжает готовым:

```
financeAllowed     — можно ли читать кассовый контур
bookedValueAllowed — можно ли показывать стоимость записанного
```

Списки РАЗНЫЕ намеренно. Право на операционный факт шире права на кассу;
объединить их значило бы снова связать два факта, которые P2 развёл. Отсутствие
права называется причиной (`not permitted`), а не изображает отсутствие данных.

## 3. Два независимых факта

```
revenue      : value + revenue_basis      + availability
bookedValue  : value + booked_value_basis + availability
```

Отсутствие выручки не удаляет стоимость записанного. Наличие стоимости
записанного не делает выручку доступной. Проверено обоими направлениями.

## 4. Три охраняющих теста переформулированы

Раньше они запрещали сумме цен журнала появляться в ответе вообще. Теперь
проверяют адресно: величина не должна оказаться в `revenue_amount_kopecks`, в
`current.revenue`, в строках мастеров и в разрезе услуг; `revenue_basis` не
должен стать `booked_prices`. И обязана присутствовать под своим именем с
основанием `booked_prices`.

## 5. Презентация называет факт своим именем

Карточка получила собственное поле и подпись **«Стоимость записанного»**. Тест
запрещает рядом с этой величиной слова «выручка», «касса», «получено»,
«заработано», «подтверждённая». Описание инструмента объясняет модели различие
словами и требует: если кассы нет, а записанное есть — так и сказать.

## 6. 🔴 Гейт пройден: канонический слой сошёлся с кабинетом

Один арендатор, один период, один часовой пояс. Два прогона подряд:

| Факт | Канонический слой | Кабинет |
|---|---|---|
| Записей | 328 | 328 |
| **Стоимость записанного** | **61 590 000** коп. | **61 590 000** коп. |
| Основание | `booked_prices` | `booked_prices` |
| Подтверждённая касса | 60 945 000 коп. (`provider_transactions`) | не отдаётся |

Совпало точно, в обоих прогонах, без органического дрейфа между ними.

### Что при этом чуть не уехало в отчёт как находка

Первый прогон дал `ai: null` против `кабинет: 61 590 000`. Причина оказалась в
моём **скрипте проверки**: он написан до P2.1 и не передавал решение о
видимости, поэтому канонический слой честно отвечал «не разрешено». Продукт был
ни при чём. Записываю это здесь, потому что при менее внимательной проверке
такая разница выглядела бы как расхождение вычислений — и остановила бы работу
на пустом месте.

## 8. Обязательные тесты

| Требование | Как проверено |
|---|---|
| выручки нет, записанное есть | касса `unavailable`, записанное с `booked_prices` |
| выручка есть, записанное есть | боевой случай: 60 105 000 и 61 250 000 рядом |
| величины различаются | тем же случаем, прямым сравнением |
| записанное не попадает в выручку | три охраняющих теста, адресно по четырём местам |
| `revenue_basis` не становится `booked_prices` | отдельное утверждение в каждом |
| основание записанного = `booked_prices` | во всех сценариях, где факт есть |
| роль без разрешения не получает факт | причина `not permitted` |
| роль с разрешением получает | и без записи в «недоступно» |
| презентация называет «стоимость записанного» | подпись + запрет пяти слов рядом |
