# CYCLE 04 P3 — DASHBOARD / HTTP CONSUMER MIGRATION

> Релиз `20260818-c04-p3-http-canonical`. Схема не тронута: ни таблиц, ни
> проекций, ни планировщиков, ни одной миграции.
>
> Кабинет перестал быть вторым владельцем бизнес-фактов. Опубликованный
> контракт при этом остался **побайтово прежним** — и это доказано против
> эталонов, снятых со старого пути до его удаления.

---

## Главное

`HTTP → BusinessStateService → операционное вычисление`. Обратного пути нет, и
это проверяется по исходникам, а не обещанием.

Совместимость выпущенного контракта переехала из вычисления в презентер на
HTTP-краю — под своим именем. Раньше она пряталась внутри сервиса аналитики и
потому выглядела бизнес-логикой: `net` считался прямо там, вторым владельцем
прибыли.

## 2. Удаление дублей (§6)

| Мигрированный факт | Старый владелец | Удалён |
|---|---|---|
| обзор салона для кабинета | `OperationsAnalyticsService.getBusinessOverviewForCabinet` | **YES** |
| личный срез для кабинета | `OperationsAnalyticsService.getEmployeeOverviewForCabinet` | **YES** |

Оставшийся владелец тех же фактов — `owner-reports` (утренние брифы). Он

Это следующий пакет, и матрица дублей уменьшится ещё раз.

## 3. Два собственных дефекта, найденных ДО выката

Оба нашлись потому, что миграция проверялась против эталонов и против списка
§10, а не «работает ли вообще».

### 3.1 🔴 `/analytics/me` вернул бы `{}`

Личный срез не получал `operationalDetail`, поэтому `sourceOverview` оставался
`null`. Презентер спокойно пропускает `null`: `{...null}` — это `{}`, ни одна
проверка не падает, ошибки нет. Кабинет мастера получил бы **пустой объект
с кодом 200**.

Закрыто: флаг протянут в личный путь, регрессия называет провал по имени —
«личный срез не превращается в пустой объект».

### 3.2 🔴 Кабинету молча приехал повтор чтения

Канонический слой читает источник с одной повторной попыткой: так делал
инструмент модели, и это его законная политика — диалог переживёт лишние
250 мс, а «источник не ответил» посреди разговора стоит дороже.

Кабинет не повторял **никогда**. При переносе повтор приехал бы вместе с
чужой политикой: удвоенная нагрузка на провайдера ровно в момент его отказа
плюс 250 мс к каждой ошибке, которую человек и так ждёт с таймаутом.

Закрыто: решение о повторе принимает вызывающий (`retryOnFailure`), умолчание
сохраняет поведение первого потребителя. Регрессия считает обращения к
провайдеру: у кабинета — одна попытка, у модели — ровно вдвое больше.

## 4. Эталоны (§5)

Пять срезов сняты прогоном СТАРОГО пути (`getBusinessOverviewForCabinet` /
`getEmployeeOverviewForCabinet`) на тех же фикстурах и лежат в репозитории:
`src/analytics/__fixtures__/legacy-http-contract.json`.

| Срез | Результат |
|---|---|
| внешняя CRM: полные данные | побайтово совпал |
| внешняя CRM: записей нет | побайтово совпал |
| внутренний календарь | побайтово совпал |
| внутренний календарь: пусто | побайтово совпал |
| личный срез мастера | побайтово совпал |

Плюс прежний побайтовый снимок `legacy-net-contract` — он и поймал первое
расхождение: канонический слой читает ПОЛНЫЙ операционный срез, где статусы
разведены главой 3 (`scheduled`, `completed`, `no_show`), а кабинет этих
ключей не публиковал никогда.

Решение: корзины снимаются на HTTP-краю, а не обедняется вход канона. Отдать
канону урезанное чтение ради формы ответа значило бы завести второе чтение —
ровно то, что P3 убирает. Ни одно число при этом не меняется: удаляются
только ключи, которых в старом ответе не было.

## 5. Обязательная регрессия §10

| # | Требование | Как проверено |
|---|---|---|
| 1 | полная внешняя CRM | полнота `complete`, счётчики на месте |
| 2 | неполная внешняя CRM | `incomplete` + причина `source_read_truncated`, оговорка `incomplete_read` |
| 3 | внутренний календарь | источник `maya`, совместимый `net`, без служебных ключей |
| 4 | измеренный ноль | `0` в доступных метриках, а не в «недоступно» |
| 5 | недоступное | касса `null` с основанием `unavailable`, в доступные не попадает |
| 6 | роль с деньгами | подтверждённая касса, основание `provider_transactions` |
| 7 | роль без денег | 990000 не встречается в ответе ни разу |
| 8 | стоимость записанного | цены журнала, основание `booked_prices` |
| 9 | выручка | при наличии цен журнала и отсутствии кассы остаётся недоступной |
| 10 | присутствие / неявка | канон из зеркала: пришло 1, неявка 1, отмен 0 |
| 11 | запись вне окна провайдера | не сосчитана, сумма не протекла, оговорка `provider_window` |
| 12 | текущий против прошлого | кабинет сравнения не публикует — и не начал; способность сравнивать на месте |

Плюс два сверх списка: §7 «AI и HTTP берут факты у одного владельца» и
регрессия на повтор чтения (см. 3.2).

**Про пункт 2 отдельно.** Презентер снимает блок полноты, но НЕ подменяет его
словом «полно»: ключа нет вовсе, и тест это фиксирует. Слепота кабинета к
неполноте — свойство выпущенного контракта фронта (реестр 4.2), а не решение
этой миграции.

## 6. Храповик направления (§8)

Проверяется по исходникам:

1. канонический слой не импортирует ни контроллер, ни презентер, ни HTTP-модуль;
2. четыре удалённых владельца кабинета не могут вернуться в сервис аналитики;
3. контроллер берёт факты только у канонического владельца — вызов обзора мимо
   канона запрещён отдельным утверждением;
4. презентер не имеет ни одного импорта: он переименовывает уже посчитанное и
   не может ничего измерить.

Круга модулей нет физически: контроллер уехал в новый `AnalyticsHttpModule`,
`OperationsAnalyticsModule` остался сервисом-примитивом.

## 7. Боевая сверка (§7, §11)

Один арендатор, один период (`2026-08-01` … сейчас), два пути:

| Факт | AI | HTTP-кабинет | Вердикт |
|---|---|---|---|
| Записей | **331** | **331** | совпало |
| Отмен | **29** | **29** | совпало |
| Уникальных клиентов | **273** | **273** | совпало |
| Записанных минут | **19 990** | **19 990** | совпало |
| Стоимость записанного | **61 990 000** | **61 990 000** | совпало |
| Основание записанного | `booked_prices` | `booked_prices` | совпало |
| Полнота | `complete`, отброшено вне окна 2 | то же | совпало |
| Оговорки | `cancellation_reason`, `provider_window` | те же | совпало |
| Подтверждённая касса | 60 965 000 (`provider_transactions`) | не отдаётся | по роли |
| Служебные ключи на проводе | — | **нет** | `__source_overview` не протёк |
| Корзины статусов на проводе | — | **нет** | контракт сохранён |

Маршруты живы после разделения модулей: `/analytics/business`,
`/analytics/me`, `/analytics/business/finance` отвечают `401` (охрана), а не
`404`. Ошибок в журнале нет.

### Наблюдение, которое сверка вытащила

При открытых деньгах подпись периода канонического состояния берётся у
финансового контура: `period: financeSummary.period ?? …`. Провайдер отдаёт
её с точностью до дня, поэтому AI видит `2026-08-01…2026-08-18`, а кабинет —
запрошенный момент времени. **Числа при этом одни и те же** — расходится
только подпись, и только на денежной ветке.

Это поведение старше P1: строка живёт в боевом коде с `9ce6ef6f`, и перенос
её не менял. К HTTP-поверхности отношения не имеет, чинить внутри P3 нечего.
Зарегистрировано (4.26).
