## 1. Три доказанных дефекта — закрыты (§2)

### 🔴 A. `earned_rub: earned ?? booked`

Виджет «Совет по допродажам» показывал мастеру **стоимость записанного под
именем «заработано»**, когда расчёт зарплаты недоступен. Соседний виджет делал
это честно — разными полями.

Эталон, снятый ДО правки (payroll недоступен, одна запись на 2 500 ₽):

```
earned_rub: 2500      ← это цена записи, а не заработок
booked_rub: —
```

Стало:

```
earned_rub: null
booked_rub: 2500
earned_unavailable_reason: 'crm_payroll_unavailable'
```

Заодно убран запасной путь апсайда `потенциал − записанное`: это разность двух
разных фактов, а не недополученный заработок. Формулу мотивации (4.22) не
трогали.

### 🔴 B. `[] → 0 ₽`

`formatMoneyEntries` возвращала `'0 ₽'` для **пустого** массива — а пустой
массив у канона означает противоположное: «денег показывать нельзя»
(fail-closed по роли или недоступный источник). Теперь возвращает `null`, и
компилятор нашёл все места, где результат считали строкой.

Там же, в карточке салона: поле выручки больше **не заполняется стоимостью
записанного**. Эталоны показывали это прямо —

| Сценарий | Было | Стало |
|---|---|---|
| финансовый контур не ответил | `revenue_rub: 2500` при `revenue_basis: 'unavailable'` | `revenue_rub: null` |
| роль без права на деньги | `revenue_rub: 2500` | `revenue_rub: null` |
| внутренний календарь | `revenue_rub: 2500` | `revenue_rub: null`, величина живёт в `booked_value_rub` |

И два счётчика перестали печатать ноль вместо незнания: «0 финансовых
операций» при непустой сумме и «0 % кассы» при статусе «привязана частично».

### 🔴 C. Присутствие

Текст про день брал «неявки» из **провайдерского статуса**. Теперь:

- ответ про дневной журнал читает блок присутствия и называет число
  ненаблюдённых записей, а при отсутствии наблюдения говорит «не сверено»;
- вопрос «сколько не пришло» отвечает `attendance_no_show` из зеркала главы 3;
- статусная корзина осталась доступной, но называется своим именем —
  «со статусом «не пришёл»», потому что это состояние ЗАПИСИ.

## 2. `?? 0` внутри канона (§3) — по случаям, а не по grep

Проверены все найденные места; исправлены два, у каждого доказанный триггер.

| Место | Доказательство, что ноль ложный | Решение |
|---|---|---|
| корзины статусов дневного разреза (`safeAnalytics`) | `scheduled` / `completed` / `no_show` существуют ТОЛЬКО у операционного чтения; запасной путь `getBusinessOverview` их не возвращает — канон публиковал измеренные нули по корзинам, которых источник не считал | `null`, счётчик выводится только из того, что пришло |
| число финансовых операций мастера (три места) | источник может назвать СУММУ и промолчать о числе операций — «0 операций» при непустых деньгах это деньги ниоткуда | `null`, презентация обязана сказать словами |

Остальные `?? 0` оставлены сознательно: там величина приходит из счётчика,
который по построению всегда число (например, длины массивов и агрегаты
внутри одного прохода).

## 4. Храповик границы (§6)

Шесть утверждений по исходникам, намеренно узких:

1. `earned ?? booked` и `revenueIsConfirmed ? … : bookedValue` не могут
   вернуться; оба факта обязаны существовать отдельными полями;
2. `formatMoneyEntries` не имеет права возвращать `'0 ₽'`;
3. ответ про день читает блок присутствия и не печатает статусную корзину как
   неявки;
4. вопрос «сколько не пришло» отвечает `attendance_no_show`;
5. карточки не складывают деньги (`reduce` запрещён);
6. отдельным тестом — **запрет не шире задуманного**: форматирование,
   склонения и проценты от готовых величин разрешены.

Комментарии из проверки исключаются: объяснение убранного дефекта не должно
ловиться как сам дефект.
