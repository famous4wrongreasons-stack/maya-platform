## 1. Три находки, ради которых написан этот отчёт

### 🔴 Н-1. Полнота выборки не доезжает до бизнес-факта

Глава 3 завела `FetchCompleteness` и доказала: по усечённой выборке нельзя
заключать отсутствие. Контракт журнала это поле несёт
(`CrmJournal.completeness`, `crm-adapter.interface.ts:287`).

**Читают его два файла: `appointment-mirror.service.ts` и
`appointment-reconciliation.service.ts`.** Оба — внутри WATCH.

Не читает никто из тех, кто отвечает владельцу:

| Потребитель | Что делает с неполнотой |
|---|---|
| `operations-analytics.service.ts:999` | игнорирует; отдаёт `verified: true` |
| `ai-tool-handler.service.ts:4944` (`readJournalRangeInChunks`) | игнорирует |
| `ai-tool-handler.service.ts:1831` (`readOperationsJournalDay`) | игнорирует |
| `appointment-notifications.service.ts:167` | игнорирует |
| `сайт и приложение/app.html`, `maya-ios/www/index.html`, `maya-os-site/index.html` | слова `completeness` нет ни в одном (0 вхождений) |

Адаптер сам это признаёт в комментарии к `warnOnTruncatedRecords`
(`yclients-crm.adapter.ts:2191`): «Менять их поведение в B3.0 намеренно не
стали — это отдельное решение». Глава 4 и есть это решение.

**Цена.** «Неявок 0» и «неявок не измерено» сегодня — одна и та же строка
ответа. Ровно тот класс лжи, который глава 2 вывела из отмен, а глава 3 — из
сверки.

**Попытка опровергнуть.** Может, фронт получает поле и молчит осознанно? Нет —
поле в кабинет доезжает (`GET integrations/crm/journal` отдаёт объект целиком),
но ни один из трёх фронтов его не упоминает. Опровержение не состоялось.

### 🔴 Н-2. Зеркало главы 3 не является источником НИ ОДНОГО бизнес-факта

`Appointment` (1950 строк) читают:

| Читатель | Ключ | Это бизнес-факт салона? |
|---|---|---|
| `tenant-appointment.repository.listForClient` | `clientId` (аккаунт) | нет — личный список клиента, 18 строк из 1950 |
| `customers.service.getCustomer` | `clientId` (аккаунт) | нет — счётчик в карточке |
| `internal-calendar.service` | арендатор на внутреннем календаре | в проде спящий путь |
| `operations-analytics.service` | **только при `calendarSource ≠ external`** | в проде НЕ выполняется |

Боевой арендатор — внешний. Значит **каждый ответ владельцу о записях сегодня
идёт в YClients по сети**, мимо 1950 строк, которые глава 3 научилась держать
сошедшимися. Зеркало есть, потребителя у него нет.

**Попытка опровергнуть.** Может, аналитика читает зеркало как кэш? Нет:
`buildOverview` выбирает ветку по `calendarSource` и для внешнего арендатора
идёт в `loadExternalAppointments` → `crmService.getJournal`. Опровержение не
состоялось.

### 🔴 Н-2а. Один ответ утверждает про отмены две противоположные вещи

Не отдельная находка, а доказательство строки «Отменённые записи» в матрице
ниже — и самое короткое из всех.

`businessMetricSnapshot` кладёт `appointments_cancelled` числом (в `aggregate()`
оно заполняется всегда), а `available_metrics` собирается фильтром «значение не
`null`». Значит метрика попадает в `available_metrics`. Одновременно
`cancellationUnavailableMetrics` безусловно, по одному лишь признаку
`data_source === 'crm'`, кладёт в `unavailable_metrics` объяснение, что ноль
здесь означает «не измерено».

**Один и тот же ответ говорит, что метрика доступна, и что она недоступна.**

Оговорка была верна до того, как аналитика начала просить отменённые записи
(`includeCanceled: true`). Что провайдер их действительно отдаёт этому салону,
доказано данными: в зеркале, которое наполняется тем же флагом, лежат **213**
отменённых визитов. Опровержение не состоялось.

### 🔴 Н-3. «Проведён» — это не «пришёл»

`recordStatus` (`yclients-crm.adapter.ts`) выводит `completed` из
`attendance == 1` **ИЛИ** `paid_full`. Два разных бизнес-факта — «клиент
пришёл» и «счёт закрыт» — свёрнуты в одно слово ещё в адаптере, и все
поверхности считают `appointments_completed` от него.

Глава 3 уже развела эти понятия в зеркале (`attendance` отдельной колонкой), но
разведены они только там.

**Доказательство на боевых данных, а не рассуждением:** одна строка
`completed / awaiting` — визит помечен проведённым, при том что провайдер прямо
утверждает «отметки о приходе ещё нет». Одна из 553 наблюдённых. Мало, но это
не гипотеза: состояние достижимо и достигнуто.

Обратный случай тоже есть: одна строка `canceled / arrived` — клиент приходил,
запись потом удалили; отмена перекрывает присутствие.

**Чего я НЕ утверждаю.** 1140 строк `completed` без присутствия — это **не**
доказательство того, что они «проведены по оплате». Их присутствие просто
никогда не наблюдалось: они лежат вне контуров сверки, а `attendance` появился
только в B3.3. Различать «не смотрели» и «посмотрели и не увидели» — та же
дисциплина, которой требует §12.

## 6. Минимальный Business Fact — контракт

Ни одно поле не взято из списка задания «на всякий случай». Каждое обосновано
уже случившейся ошибкой.

```ts
type BusinessFact = {
  key: string;                    // 'appointments.total', 'revenue.confirmed'
  tenantId: string;
  period: { from: string; to: string; timezone: string };
  value: number | null;           // null — значение ОТСУТСТВУЕТ, не ноль
  unit: 'count' | 'minutes' | 'percent' | 'kopecks';
  currency?: string;              // только при unit = 'kopecks'
  basis: string;                  // 'provider_transactions' | 'booked_prices' | 'observed_attendance' | ...
  availability: 'available' | 'unavailable';
  unavailableReason: string | null;
  completeness: 'complete' | 'truncated';
  observedThrough: string | null; // до какого момента источник реально прочитан
  calculatedAt: string;
};
```

Почему именно так:

| Поле | Чем доказано |
|---|---|
| `period` с `timezone` | «прибыль в июле» отвечали цифрами текущего месяца — числа настоящие, период чужой |
| `value: null` | нули когорт читались как «повторных нет», и владельцу сказали обратное правде |
| `unit` | «63» без единицы — это не факт |
| `basis` | `финансовая выручка ?? цены журнала` превращало забронированное в кассу молча |
| `availability` + `unavailableReason` | отказ обязан называть причину словом из жизни салона |
| `completeness` | глава 3 доказала: по усечённой выборке нельзя заключать отсутствие |
| `observedThrough` | 1330 из 1950 визитов вне контуров сверки — «свежесть» без границы это обещание |
| `calculatedAt` | кэш на 5 минут уже существует и уже невидим |

**Чего в контракте НЕТ и почему.** `confidence` — сегодня ни один факт не
вероятностный, а поле пригласило бы прогноз в главу 4. `verified` — это
`basis === 'provider_transactions'`, второе имя тому же. `provenance` целиком —
провенанс живёт в `DomainEvent`, дублировать его в факте значит завести второй
источник истории. Если после B4.2 окажется, что поля не хватает, — добавим,
доказав нехваткой, а не предчувствием.

## 7. Минимальный Business State

Композиция фактов, а не «всё о салоне». Первая версия — ровно то, что уже
собирает `queryBusinessAnalytics`:

```
BusinessState(tenant, period) = {
  period:       разрешённое окно + признак «период ещё идёт»
  appointments: total · active · scheduled · completed · cancelled · no_show
                · booked_minutes · cancellation_rate
  attendance:   arrived · no_show · awaiting · not_observed   ← НОВОЕ, из зеркала
  clients:      unique · repeat_in_period · returning · new · cohort_lookback_days
  staff[]:      идентичность Maya · записи по корзинам · booked_minutes
                · подтверждённая касса · начисление
  services[]:   записи · стоимость записанного · подтверждённая касса
  money:        confirmed_revenue(basis) · booked_value(basis) · average_ticket
  expenses:     по статьям · полнота · декларация владельца
  profit:       net · маржа · причина отказа
  loyalty:      баланс · владелец · требуется ли подтверждение
  completeness: полнота КАЖДОГО источника, из которого собран ответ
}
```

Чего в нём нет намеренно: загрузки за период (нечем считать без 180 запросов),
прогноза, возможностей, атрибуции, вероятностей.

**Роль каждого источника** (решение по §9, посемейственно):

| Семья | Откуда считать | Почему |
|---|---|---|
| Записи за период | канонический журнал с фильтром окна | окно — вопрос к источнику, а зеркало покрывает ±31 день |
| Присутствие | **зеркало** | единственное место, где присутствие вообще хранится |
| Переходы, история изменений | `DomainEvent` | для этого он и заведён |
| Деньги | финансовые операции провайдера | касса подтверждается только там |
| Расходы, декларации | база Maya | владелец Maya |
| Клиенты | реестр провайдера | идентичности клиента у Maya нет (0/0) |
| Мастера | `Staff` + `StaffProviderLink` | идентичность есть и работает (1936/1950) |

## 8. Материализация: решение — НЕ материализовать

| Вариант | Вердикт |
|---|---|
| Считать по запросу | **да, для всех семей на первой итерации** |
| Материализованная проекция | нет |
| Проекция, обновляемая событиями | нет |

Основания, а не вкус:

1. **Масштаб.** 1950 визитов, один арендатор с CRM. Медианный прогон сверки —
   3,4 с (среднее по прогонам планировщика, замер B3.4); локальный запрос к
   1950 строкам дешевле на порядки.
2. **Восстанавливаемость (§32).** Проекция, которую нельзя пересчитать, — это
   скрытый источник истины. Пересчитать факты за прошлое сегодня **нечем**:
   1330 из 1950 визитов лежат вне контуров сверки и присутствие у них не
   наблюдалось. Материализация закрепила бы неполноту в камне.
3. **`pending = 0` не цель (§10).** 19 событий ждут потребителя, и это
   нормально: событие означает «замечено», а не «обработано».

**Что материализовать всё-таки придётся — и это отдельный gate**: загрузка за
период. Рабочее время провайдер отдаёт по одному дню на запрос; иначе — это
180 сетевых вызовов на вопрос «какая загрузка была в августе».

## 11. Пакеты Phase B — в порядке реализации

Порядок не косметический: сначала правда о входе, потом один владелец, потом
всё остальное читает его.

### B4.1 — Окно и полнота доезжают до факта
`REPLACE`. Единый канонический читатель журнала: фильтр по бизнес-периоду
(а не по тому, что вернул провайдер) и перенос `completeness` наружу.
Потребители: аналитика, `readJournalRangeInChunks`, `readOperationsJournalDay`,
уведомления.
**Обязательный adversarial-тест (§14):** провайдер возвращает записи вне
запрошенного окна — факт «записей за период» их не считает; выборка `truncated`
— факт не имеет права сказать «нет».
Схема: не нужна.

### B4.2 — Один владелец: `BusinessFactsService`
`MOVE`. Вынести `queryBusinessAnalytics` + `businessMetricSnapshot` + сравнение
периодов + `reportingWindow` из AI-слоя. Контракт `BusinessFact` — в
`src/domain/business-fact.ts` (без Nest и Prisma, как требует барьер).
AI-инструмент становится тонкой обёрткой; **числа не меняются**, что
доказывается снимком ответа до и после.
Схема: не нужна.

### B4.3 — Отмены: убрать ложную оговорку
`DELETE AFTER MIGRATION`. `cancellationUnavailableMetrics` заменяется
утверждением, основанным на измерении. Отдельный тест: пока отмены измеряются,
оговорки нет; если источник перестанет их отдавать — оговорка возвращается сама.

### B4.4 — Один справочник статей расходов
`REPLACE`. Аналитика читает `expense-category.ts`; вторая таблица синонимов
удаляется. Защита от двойного учёта зарплаты переезжает на слаг `payroll`.

### B4.5 — Клиентские факты: три имени вместо одного слова
`MOVE`. Одна формула давности визита вместо четырёх. Явные раздельные имена:
`visits_in_period > 1`, `returned_within_90d`, `lifetime_visits ≥ N`. Термина
`churned` не вводить (§16): вводим `no_visit_for_N_days` и называем его так.

### B4.6 — Поверхности читают факты, а не считают заново
`REPLACE`/`MOVE`. `owner-reports.composers` перестают пересчитывать и перестают
подставлять `0` вместо неизвестности. `readOperationsJournalDay`, `readTeamKpi`,
`compareBranches`, `readNoShowRiskClients` переходят на факты.

### B4.7 — Присутствие становится фактом
`MOVE`. Первый бизнес-потребитель зеркала: `attendance.arrived / no_show /
awaiting / not_observed` с обязательным `observedThrough`. Это и есть честный
ответ на «сколько клиентов реально пришло» — впервые отдельный от «проведён».

### B4.8 — Кэш с границами
Ключ по факту и периоду, предел размера, `calculatedAt` наружу. Инвалидацию по
`DomainEvent` **не включать** — отдельное решение.

### B4.9 — Верификация пакета
Снимки ответов до/после, adversarial-тесты §14, прогон на клоне боевой базы,
выкат по `deploy.sh`, наблюдение.
