## Exact Slice

- **Action:** `issue_loyalty_redemption_grant`, the seventh action class in
  the accepted P4-03 Runtime Contract Gate order.
- **Initiators / legacy owner:** an authenticated client selects a redeemable
  service through Telegram or PWA. Today `bot.py` resolves a process-local
  client and calls `loyalty.generate_redeem_code`; that function reads the
  SQLite balance and provider catalog, generates a raw `LOY-*` bearer code,
  and asks `database.py` to insert `loyalty_redeem_codes`. Those Python/SQLite
  functions remain the actual grant owner during Shadow. The isolated adapter
  is not wired into production initiation in this step.
- **Canonical target identity:** authoritative provider/company integration ->
  exact tenant; tenant-qualified active `CrmClientLink` -> one unmerged active
  Client/User/Membership and existing `LoyaltyAccount`; exact service id -> one
  current server-side catalog service for that tenant/provider; server-owned
  redeemable-service allowlist and price derive eligibility and points. Phone,
  Telegram id, local client id, service title, caller-supplied price, or raw
  code is not identity authority.
- **Server-derived idempotency identity:** canonical caller request identity +
  tenant + canonical Client + exact service identity + server-derived point
  value + grant-policy/catalog-policy versions. Telegram and PWA labels do not
  affect the key. Reuse of a caller request for another service/value/policy
  collides and fails closed rather than issuing a second grant.
- **Durable model/binding:** Shadow creates only a non-executable
  `ActionExecution` plan. A future executable result is exactly one immutable,
  tenant-qualified `LoyaltyRedemptionGrant` whose `issueExecutionId` is bound
  1:1 to the issue execution, whose `clientId`/`serviceRef`/points/expiry are
  immutable, and whose bearer code persists only as a server-derived
  `codeHash`. Issue creates no `LoyaltyTransaction`; consumption and any
  balance debit belong exclusively to the eighth action class.
- **Policy/caps/approval:** `customer_value`, `financial_equivalent`,
  `one_time`, `bearer_secret`, `provider_evidence`, and `shadow_only`; feature
  `loyalty`; policy `SHADOW_ONLY`; autonomy `L2_5_SHADOW`; approval `NONE` only
  because this slice grants zero execution permission. Future issuance
  requires an authenticated eligible client or authorized staff principal,
  an allowed service, sufficient canonical balance, server TTL, and a hard
  server per-grant cap. The legacy bridge secret or possession of a requested
  service alone is not client authorization.
- **Provider boundary:** Shadow performs one read-only catalog read through the
  tenant calendar/CRM facade. It performs no provider write and no identity
  registration. Missing/ambiguous service, invalid currency/price, or catalog
  failure leaves evidence unresolved. Provider catalog evidence controls
  service identity and points; initiator title/points are comparison evidence.
- **Possible `UNKNOWN`:** none in Shadow. A future lost acknowledgement around
  the atomic grant/code-hash/issue-execution commit is `UNKNOWN`, never
  `FAILED`. Because raw code is intentionally not stored, an acknowledged-lost
  issue must never generate a second code under the same request.
- **Reconciliation contract:** none for Shadow and no retry. A future issue
  reconciles from the exact tenant-qualified grant whose `issueExecutionId`,
  client, service, points, expiry policy, `codeHash`, and correlation match the
  execution. Exact bound result proves success; proven rollback proves
  non-execution; missing or contradictory evidence remains `UNKNOWN` and
  forbids blind redispatch.
- **One-time semantics:** one issue execution can bind to at most one grant;
  the tenant code hash is unique; a grant can bind to at most one append-only
  `LoyaltyRedemption`; issue never marks a grant consumed and never debits the
  ledger. Generating or possessing a bearer code grants no consume authority.

Shadow never generates raw code material or even a proof-only code hash. It
records only the intended immutable grant facts and a fixed TTL policy. A
matching existing canonical grant produces a no-create plan; contradictory,
unbound, duplicate, cross-client, cross-service, or changed-value evidence
fails closed.
