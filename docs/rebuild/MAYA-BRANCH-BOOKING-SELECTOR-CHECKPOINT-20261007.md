# Branch-preserving booking — development checkpoint

The current Client booking path retains the selected Maya branch and the originating CRM source revision through the existing time selector, canonical preview, explicit confirmation and Action Engine. Personal booking preserves branch, service, staff and date when one choice changes. These are local development changes; the working website and production are untouched.

## What changed

- The existing availability READ records a current branch/source witness. The existing sealed slot owner reference has a bounded `slot_v2` form containing the instant, branch ID and source revision. Existing `service/staff/slot` noun sets remain unchanged; historical ISO-only slots are never upgraded into branch authority.
- The canonical create owner pins the source before target/timezone/catalogue reads and compares it after the read. The same witness is persisted in existing Action Engine evidence. Prepare, dispatch and reconciliation compare the original evidence, including after a process restart; a fresh caller cannot replace it. Changed mapping metadata inside the same company also invalidates a new proposal.
- Mapping removal/change and timezone drift refuse stale proposals. A durable accepted/UNKNOWN result retains its result path after source withdrawal. UNKNOWN never authorizes a second booking POST.
- The authenticated personal form reads existing `/branches` and requires a choice when branches exist. It rechecks the selected branch timezone before and after reading slots; mixed snapshots are discarded. Editing one parameter retains the other choices and invalidates slots and preview.
- Client semantic corrections resolve the branch through the current tenant-scoped CRM owner. Relative dates use that verified timezone and are retained as absolute local dates. This does not make names, labels, URL parameters or presentation into authority.
- A branch-specific partial request without a selected staff member follows that same owner check, retains the other preferences and asks for the staff member. Catalogue reads suppress widget emission. The next explicit turn revalidates the saved choices; a branchless service selector is not substituted.

One C9, the existing CRM/availability owners and the existing Action Engine remain in place. No new production schema, retention policy, orchestrator, background initiator, outbound sender or public website route was added.

## Limits

- Native YCLIENTS adapter transport is finite synthetic GET/booking POST plus a separately counted read-only reconciliation POST. No live YCLIENTS/model call, provider notification, production/site/device operation, push or merge is authorized or performed by these proofs.
- HTTP restart starts from a saved **MINTED widget confirmation**, not a persisted READY ActionExecution. Original READY source-witness behavior has focused unit evidence; it must not be described as the HTTP restart fixture. UNKNOWN is reached after that restart; this fixture does not restart an already UNKNOWN ActionExecution.
- The complete branch-qualified request enters a time selector. The generic service-first typed selector still lacks a retained branch/date context tied to its original turn; its existing automatic next-day behavior is not represented as fixed by the new slot reference. Personal branch selection is a separate supported flow.
- Scripted semantic decisions and canned model replies are explicitly synthetic. Real language quality, live provider behavior, release/deployment and full MAYA/C10 completion remain unaccepted.
