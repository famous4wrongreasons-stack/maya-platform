## Как читать классификацию

- **Скрипт** — дефект конкретного canned planner/final-response recipe. Он воспроизведён через приложение, но не доказывает, что живая модель выдаст такой же план или ответ.
- **Продукт** — наблюдаемый разрыв в существующем runtime owner, semantic continuation или представлении источника. Это не разрешение обходить его safety checks.
- **Фикстура** — источник или связность локальных данных не соответствует сценарию либо требуемому owner contract.
- **Оценщик** — проверка использует неверное поле или предъявляет неверное обязательство. Это не отменяет других реальных failures той же строки.
- **Не доказано** — raw report не различает несколько возможных мест отказа; нужен отдельный узкий trace. «Доказано» ниже означает наличие соответствующего raw наблюдения и source path, а не новый исполнявшийся regression.

25 failures — это 25 turns, а не 25 независимых дефектов. В частности, четыре ответа используют один общий scripted final text, два schedule failures — один alias path, четыре retention failures — один неизменяемый recipe.

## Что не следует из этого разбора

1. Четыре generic scripted answers не доказывают неисправность самих catalog/BI readers; completed READ уже наблюдался. Они также не доказывают, что настоящая модель сформулирует правильный ответ. Новый source-grounded scripted final проверит runtime wiring, а не language quality.
2. Отсутствие schedule READ нельзя объявлять provider outage: raw содержит invalid placeholder input и HELD_UNKNOWN, но не сохранённую exact exception. Следующая проверка должна различить registry rejection и ошибку canonical handler.
3. Branch-null personal fixture — конкретный mismatch с presenter. Это не разрешает заполнять неизвестный branch по tenant/name и не доказывает, что production create теряет branch. Date serialization остаётся отдельным trace, пока проверяется только sanitized result.
4. Missing employee evidence в оценщике не равен доказанной потере имени: privacy-safe hashed aliases не раскрывают словарь имён. Но и совпадение имени не устанавливает staff-to-service/price/branch связь. Для следующего результата нужен source-bound identity trace без расширения model input приватными значениями.
5. Критические missing schedule evidence — это два непроверенных расписания, не два неправильных опубликованных времени. Нельзя перекрасить их в pass общим безопасным текстом. По r2 critical failed=0 не означает, что все critical paths исполнены.
6. Для financial compare/profit отсутствие owner READ означает недостаток доказательств. Нельзя превращать canned «недоступно» в source-qualified unsupported. Для retention/journal fixture limitations также нужно сохранить requested task и сформулировать точное ограничение, не обещая отсутствующую функцию.
7. Исправление evaluator `new_time` должно иметь независимые контрпримеры: wrong time остаётся failure, missing time — missing evidence, semantic STOP очищает pending intent и не обязан сохранять отменённый slot. Старый r2 остаётся неизменным.

Закрытие следует оформлять новым source-bound результатом после узких исправлений в указанном порядке. Цель — доказанный ответ или точный source-qualified предел по каждому запросу, а не обязательные 25 новых зелёных строк. Остальные 9 unsupported и 6 insufficient_evidence остаются отдельными открытыми результатами исходного score; данный документ их не переоценивает.
