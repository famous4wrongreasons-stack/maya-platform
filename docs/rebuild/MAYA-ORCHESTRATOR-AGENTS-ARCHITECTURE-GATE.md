слой НАД тем, что есть, а не замена ему.

## 1. Executive decision

| Решение | Ответ | Основание |
|---|---|---|
| Maya становится оркестратором | **ДА** | пользователь уже разговаривает с одной Maya; сегодня роль «выбрать инструмент» несёт плоский каталог из 50 позиций и один системный промпт — это не масштабируется по числу доменов и по стоимости |
| Специализированные агенты нужны | **ДА, но их меньше десяти** | десять кандидатов из задания сводятся к **четырём** в v1 (§3); остальные — capability, policy или отложенная фаза |
| Агенты владеют бизнес-правдой | **НЕТ** | главы 1–4 завели по одному владельцу на каждый факт; второй владелец — это ровно тот класс дефектов, который глава 4 закрывала девять пакетов |
| Агенты сами исполняют побочные эффекты | **НЕТ** | побочный эффект проходит через один рантайм уже сегодня; агент получает право только **предложить** намерение |
| Action Engine нужен до автономных агентов | **ДА** | сегодняшний рантайм не умеет «исход неизвестен», повтор, сверку, ограничение частоты и сухой прогон; без них Level 3+ создаёт двойные записи и повторные рассылки |
| Главы 1–4 требуют перестройки | **НЕТ** | фундамент подтверждён по §33 (детально — §6 и §19) |
| Главы 5–10 требуют переосмысления | **ДА** | содержание меняется, число глав остаётся 10 |

**Одной строкой:** Maya становится оркестратором над существующим слоем
возможностей; специализация вводится там, где она снижает стоимость и риск, а
не везде; автономия открывается только после Action Engine.

## 2. Обязанности Maya Orchestrator

### 2.1 Что делает

| Обязанность | Содержание | Чего НЕ делает |
|---|---|---|
| Понимание намерения | классификация запроса, разрешение периода (уже есть владелец — `reporting-period.resolver.ts`), определение адресата (владелец/мастер/клиент) | не парсит даты сам заново |
| Декомпозиция | разбивает запрос на подзадачи, каждая из которых имеет единственного исполнителя | не «планирует» там, где хватает одного инструмента |
| Маршрутизация | выбирает агента ИЛИ прямой детерминированный вызов | не вызывает агента, если ответ даёт capability |
| Передача контекста | собирает минимальный срез (§11) | не отдаёт агенту весь state арендатора |
| Координация нескольких агентов | последовательный или параллельный вызов, сбор результатов | не даёт агентам звать друг друга (§12) |
| Разрешение конфликтов | если два агента предлагают несовместимые действия — выбирает или отказывается | не «усредняет» числа: числа приходят из канона, спорить о них нельзя по построению |
| Решение о необходимости действия | предлагать ли действие вообще | не исполняет |
| Подтверждение пользователя | формулирует, что именно будет сделано, и получает согласие | не подтверждает за пользователя |
| Соблюдение autonomy policy | сверяет предложенное намерение с уровнем автономии арендатора | не повышает себе уровень |
| Презентация | один ответ одной Maya, с оговорками об ограничениях | не пересчитывает факты для красоты |

### 2.2 Явные запреты (ратификация правила задания)

Оркестратор **не имеет права**:

1. считать бизнес-факт (любое число приходит от canonical capability);
2. хранить бизнес-состояние между запросами (кроме conversation memory, §11);
3. вызывать CRM, отправлять сообщения, менять лояльность напрямую;
4. становиться вторым Action Engine — он формирует **Action Intent**, а исполняет рантайм;
5. подменять отказ факта нулём или «примерно» — контракт `measured / measured_incomplete / not_measured / unavailable` доезжает до текста без потерь (это правило главы 4, оно не отменяется агентами).

### 2.3 Где он живёт

Оркестратор — это эволюция `ai-core.service.ts` (сегодня: системный промпт +
цикл вызова инструментов), а не новый сервис. Разделение внутри него:
`intent → routing → execution → composition`. Новый код — маршрутизатор и
контракт результата агента; всё остальное уже есть.

## 3. Модель агентов: разбор десяти кандидатов

Критерий, по которому кандидат становится агентом (иначе — capability или
policy). Агент нужен, когда одновременно верно:

1. **Есть неоднозначность**, которую нельзя закрыть детерминированным правилом («кого из 40 спящих звать первым»);
2. **Есть своя предметная рамка** — набор фактов и действий, который другой агент не должен видеть;
3. **Есть отдельный измеримый результат** (§16), за который можно брать деньги;
4. **Есть свой контур доверия или риска** (внешний текст, деньги, ПД, коммуникация).

| Кандидат | Решение | Обоснование |
|---|---|---|
| **Maya Admin Agent** | **ПРИНЯТ** — отдельный агент | Единственный, кто читает **внешний недоверенный текст** (клиенты пишут в мессенджеры). Другой контур безопасности (§10), другая задержка (секунды, не минуты), другой набор действий (запись/перенос/отмена/ответ). Смешивать его с аналитикой владельца нельзя ни по правам, ни по риску |
| **Retention Agent** | **СЛИТ** в Client Lifecycle | Работает на тех же фактах, что Reactivation: `client-recency-facts`, присутствие, когорты. Отдельный агент означал бы двух владельцев одного контакта с клиентом |
| **Reactivation Agent** | **СЛИТ** в Client Lifecycle | То же. Разница «спящий/уходящий» — это **порог сегмента**, а не отдельный разум |
| **Recovery Agent** | **СЛИТ** в Occupancy | «Освободилось окно» и «дыра в расписании» — одна задача с разным триггером: чем заполнить ёмкость. Один владелец очереди кандидатов исключает два предложения одному клиенту |
| **Schedule Agent** | **СЛИТ** в Occupancy | См. выше. Оставшаяся часть (загрузка, свободные мощности) — **факты**, а не рассуждение; они уже почти есть (утилизация кресла — 4.54, без владельца) |
| **Marketing Agent** | **ОТКЛОНЁН в v1** | Кампании уже машинерия: `marketing.campaign.preview/send` + аудитории. Рассуждение «кому и что» принадлежит Lifecycle. Отдельный агент появится, когда появится многоканальный креатив и оптимизация — не раньше |
| **Revenue Agent** | **ПРИНЯТ** в составе Business Intelligence | «Почему упала выручка и что смотреть дальше» — настоящая неоднозначность. Только чтение |
| **Staff Agent** | **СЛИТ** в Business Intelligence | Те же факты (выручка, записи, присутствие) в разрезе мастера. Отдельная **приватность** решается не отдельным агентом, а фильтром контекста (§11) и правами (§10). Коммерчески может продаваться отдельно — это billing, не архитектура |
| **Loyalty Agent** | **ОТКЛОНЁН** | У лояльности с главы 2 есть канонический авторитет и граница; «начислить/списать» — детерминированное правило, а не рассуждение. Остаётся capability + policy. Отдельный агент дал бы второго владельца баланса — прямой запрет |
| **Reputation Agent** | **ОТЛОЖЕН до главы 7** | Предмет есть (отзывы, негатив, запрос отзыва), но у семьи фактов нет канонического владельца: месяцы тренда режутся по UTC, `improving/declining` — интерпретация (4.42). Агент поверх неканонических фактов повторит ошибку, которую глава 4 закрывала. Сначала владелец фактов, потом агент |

### 3.1 Принятый набор v1

| Агент | Роль | Контур доверия | Класс действий |
|---|---|---|---|
| **Maya Admin** | фронт-офис: входящие обращения, запись/перенос/отмена, ответы клиенту | **недоверенный внешний текст** | `medium_write` по своим записям, коммуникация с клиентом |
| **Client Lifecycle** | удержание, спящие, возвращаемость, реактивация, адресные предложения | внутренний | предложение контакта; массовая рассылка — только через Action Engine с лимитом аудитории |
| **Occupancy** | заполнение ёмкости: освободившиеся окна, дыры расписания, кандидаты | внутренний | предложение записи/переноса, приглашение |
| **Business Intelligence** | деньги, расходы, прибыль, мастера, сравнения периодов, аномалии | внутренний | **только чтение** |

Четыре агента вместо десяти — это не экономия ради экономии: каждый слитый
кандидат был слит потому, что иначе появлялся **второй владелец** одного и того
же решения или контакта.

### 3.2 Что осталось не агентом

`Predict` и `Autopilot` — не агенты, а **свойства**: прогнозные capabilities
(§18, глава 8) и политика автономии (§9), применяемая к уже существующим
агентам. Заводить «агента-предсказателя» означало бы дать рассуждению право
порождать числа без владельца.

## 4. Правило «Agent thinks. Capability computes. Business State owns truth»

Формализация для ревью кода:

| Признак | Capability | Agent |
|---|---|---|
| Даёт ли один и тот же вход один и тот же выход | да | нет |
| Может ли ошибиться в **числе** | нет (по построению) | не имеет права его считать |
| Имеет ли право на побочный эффект | только через Action Engine | никогда напрямую |
| Тестируется | юнит/регрессия | сценарии + метрики результата (§16) |
| Стоимость | ~0 | токены |

Примеры на реальном коде:

| Вопрос | Кто отвечает |
|---|---|
| `getBusinessProfitability()`, `readExpensePeriod()`, `attendance-facts` | **capability** — детерминированно |
| «почему прибыль ниже прошлого месяца, что смотреть дальше» | **BI Agent** |
| `appointments.own.create` | **capability/action** через рантайм |
| «кого позвать в освободившееся окно в 15:00» | **Occupancy Agent** |
| «сколько у клиента баллов» | **capability** (граница лояльности главы 2) |
| «начислить ли бонус за возврат» | **policy** арендатора, не агент |

**Красная линия:** если функцию можно записать правилом, которое владелец
подтвердит словами, — это capability или policy. Агент нужен там, где правило
пришлось бы угадывать.

## 5. Agent Registry

**Нужен: да.** Но не как plugin-платформа, а как таблица в коде — точно так же,
как сегодня устроен `AiToolRegistryService` для инструментов.

Минимальный контракт (TypeScript-форма, для реализации в главе 9):

```ts
interface MayaAgentDefinition {
  id: 'admin' | 'lifecycle' | 'occupancy' | 'bi';
  purpose: string;                      // одна строка для маршрутизатора и для аудита
  supportedIntents: readonly string[];  // корпус намерений, а не свободный текст
  requiredCapabilities: readonly string[];   // имена инструментов из каталога
  deniedCapabilities: readonly string[];     // явный запрет сильнее умолчания
  requiredFeatures: readonly MayaFeatureKey[]; // энтайтлмент арендатора
  autonomyClass: 'observe' | 'recommend' | 'prepare' | 'execute' | 'autopilot';
  maxSideEffectClass: 'read' | 'low_write' | 'medium_write' | 'high_write';
  allowedSurfaces: readonly AiToolSurface[]; // native | web | telegram | voice
  contextProfile: string;               // какой срез контекста получает (§11)
  outputContract: 'AgentResult@1';      // §13 структурного результата
  reasoningBudget: { maxToolCalls: number; maxTokens: number; timeoutMs: number };
}
```

Почему именно так:

- поля 1:1 повторяют уже проверенную форму `AiToolDefinition` — новых понятий вводится минимум;
- `supportedIntents` не изобретается: корпус из **88 канонических интентов** (`maya-ci/1`) уже используется семантическим планировщиком, агент получает подмножество этого корпуса;
- `deniedCapabilities` существует отдельно от `requiredCapabilities` намеренно: запрет должен читаться в реестре, а не выводиться вычитанием;
- `autonomyClass` и `maxSideEffectClass` разделены: агент может иметь право «готовить» действие высокого класса и не иметь права его исполнять;
- бюджет рассуждения — часть определения, а не настройка рантайма (§14).

Чего в реестре **нет намеренно**: версий промптов, моделей, шаблонов текста.
Привязка агента к имени модели запрещена (§14.3).

## 7. Read vs Action

Архитектурное разделение (уже наполовину существует — надо довести до правила):

```
READ capability     → агент вызывает свободно в пределах бюджета и энтайтлмента
ACTION capability   → агент НЕ вызывает; он возвращает Action Intent
```

| | READ | ACTION |
|---|---|---|
| Кто может вызвать | агент, оркестратор, HTTP | **только Action Engine** |
| Идемпотентность | не нужна | обязательна (уже так в контракте) |
| Подтверждение | нет | по политике (§10) |
| Аудит | не обязателен | обязателен |
| Повтор при сбое | безопасен | только по правилам движка |
| Что видит агент | факты с контрактом полноты | подтверждение/отказ намерения |

**Правило для ревью:** любой новый инструмент с `riskTier !== 'read'` обязан
получить владельца среди действий и не может появиться в
`requiredCapabilities` агента иначе как через `proposed_action_intents`.

## 8. Граница Action Engine

```
Agent → Action Intent → Policy / Permission → Action Engine → External Side Effect
                                   ↑                    ↓
                             Autonomy policy      Audit + Outcome
```

### 8.1 Что уже есть (не переписывать)

- единственная точка исполнения `AiToolRuntimeService.execute` — чат и HTTP идут через неё;
- подтверждения со статусами `PENDING / APPROVED / REJECTED / COMPLETED`;
- ключ идемпотентности **обязателен** для всех write-инструментов;
- политика доступа: арендатор × роль × поверхность × энтайтлмент;
- `fallbackPolicy: fail_closed | last_verified_snapshot` в контракте инструмента.

### 8.1a Область движка: побочные эффекты живут в ЧЕТЫРЁХ несвязанных контурах

Единственность точки исполнения доказана только **для ИИ-поверхности**.
Инвентаризация показала четыре контура:

| Контур | Подтверждение человеком | Идемпотентность | Аудит | Аренда/жнец |
|---|---|---|---|---|
| 1. ИИ-инструменты (`AiToolRuntimeService`) | **да** | **да** (ключ обязателен для 13 из 14 write) | да | частично |
| 2. HTTP-контроллеры: журнал CRM (6 маршрутов), записи клиента, расходы, интеграции | нет | **нет** (`Idempotency-Key` разрешён в CORS и **не читается никем**) | да | нет |
| 3. Четыре планировщика на голом `setInterval` в процессе (напоминания, отчёты владельцу, сверка, биллинг) | нет | нет | частично | только у сверки |
| 4. Мост из Python-бота (inbox ingest, recovery touchpoints) | нет | нет | частично | нет |

Административные операции над журналом (`markAppointmentAttendance`,
`setAppointmentDuration`, `setAppointmentServices`, `rescheduleJournalAppointment`,
`cancelJournalAppointment`) существуют **только** на HTTP-краю — без
подтверждений и без идемпотентности. Это ровно те операции, которых захочет
Occupancy-агент.

Решение гейта: Action Engine главы 6 обязан стать точкой исполнения **для всех
машинных инициаторов** (агенты, планировщики, автоматические реакции на
события) и покрыть контуры 2–4 хотя бы регистрацией исхода. Действия,
инициированные человеком через обычный API, могут остаться вне движка — но
тогда движок обязан читать их исход при сверке, иначе агент будет действовать
поверх изменений, о которых не знает.

Решение гейта: Action Engine главы 6 обязан стать точкой исполнения **для всех
машинных инициаторов** (агенты, планировщики, автоматические реакции на
события). Действия, инициированные человеком через обычный API, могут остаться
вне движка — но тогда движок обязан читать их исход при сверке, иначе агент
будет действовать поверх изменений, о которых не знает.

### 8.2 Чего нет — и это и есть работа главы 6

| Пробел | Доказательство | Последствие без починки |
|---|---|---|
| **Исход неизвестен** не является исходом | глава 2 ввела три исхода для отмены; общего правила у движка нет | повтор поверх выполненного действия |
| Нет сверки после действия (reconciliation) | 6.1 «орфан при создании визита»: CRM создала, локальная запись упала, компенсации нет | расхождение зеркала и CRM |
| Нет управляемого повтора | `retryPolicy: 'none'` в контракте | ручной разбор каждого сбоя |
| Кампания застревает в `sending` | `marketing.service.ts:191` — переход `draft → sending` под ключ, возврата из `sending` нет | кампания не досылается и не повторяется никогда |
| Дедуп уведомлений ≠ доказательство доставки | 4.44: при усечённом чтении журнала напоминания просто не уходят и это нигде не объявляется | молчаливая потеря коммуникации |
| Нет ограничения частоты и аудитории | — | агент уровня 3 может разослать всей базе |
| Нет сухого прогона | — | нельзя показать владельцу «что бы произошло» |
| Аудит смешан с рассуждением | §17 | в разборе инцидента нет цепочки решения |
| Запись в CRM стирает присутствие | **4.43**: `attendance: … : 0` в неразрушающем PUT | автономный перенос записи ломает канон присутствия главы 3 |
| Нет состояния «исход неизвестен» нигде, кроме отмены записи | таймаут превращается в `FAILED` в рантайме, в биллинге и в жнеце | повтор поверх, возможно, выполненного |
| Нет повтора и отката ни у одного эффекта | единственный retry в проекте — на **чтении** бонусной карты; единственная компенсация — откат графика мастера | ручной разбор каждого сбоя |
| **Машина доставки кампаний уже есть в схеме БД и не используется кодом** | получатели, попытки, аренда, `retryCount`, лимиты — в боевой схеме; код шлёт напрямую | движок главы 6 не строится с нуля: хранилище готово |
| **Очередь `DomainEvent` с арендой есть, потребителя нет** | `claimBatch` не вызывает никто, 102 pending (4.80) | глава 5 получает готовый механизм задач |

**4.43 — блокер для любого автономного переноса записи.** Пока PUT затирает
отметку присутствия нулём, ни Admin, ни Occupancy не могут получить Level 3 на
`reschedule`.

## 9. Модель автономии

Уровни задания проверены. Принимаются с **тремя поправками**.

| Уровень | Название | Что можно | Требование к системе |
|---|---|---|---|
| **L0** | Observe | читать факты, отвечать | ничего сверх сегодняшнего |
| **L1** | Recommend | предлагать действие текстом | структурный результат (§13) |
| **L2** | Prepare | готовить намерение/черновик кампании/текст сообщения; исполняет человек | Action Intent + подтверждение |
| **L2.5** | **Shadow** (новое) | движок принимает намерение и записывает исход, **не исполняя**; человек сравнивает | аудит намерений, метрика совпадения |
| **L3** | Execute within policy | исполнять заранее разрешённые классы действий в пределах лимитов | **весь §8.2** закрыт |
| **L4** | Autopilot | связка действий по бизнес-политике, повторяющиеся циклы | L3 + измеримый результат (§16) + откат |

Три поправки к исходной модели:

1. **Уровень — свойство тройки (агент × класс действия × арендатор), а не агента.** «Admin — L3» бессмысленно: подтвердить запись клиента и разослать 400 сообщений — разный риск. В реестре хранится матрица, а не одно число.
2. **Введён L2.5 Shadow.** История проекта (главы 3–4) показывает, что расхождение обнаруживается только сравнением с наблюдением. Автономию нельзя включать «на веру»: сначала агент неделю предлагает, движок пишет, человек сверяет.
3. **Переход L2 → L3 требует не решения владельца, а выполненного условия:** закрытые пункты §8.2 для этого класса действий + пройденная метрика Shadow. Иначе владелец включит автономию раньше, чем движок умеет её обслуживать.

### 10.3 Безопасность (§30 задания)

| Угроза | Где реальна | Мера |
|---|---|---|
| **Prompt injection** через сообщение клиента | Admin читает inbox — единственный агент с внешним текстом | внешний текст помечается как **данные**, не инструкции; Admin не имеет инструментов вне своего списка; любые «инструкции» из текста не могут повысить класс действия |
| Tool abuse | любой агент | реестр: `denied` сильнее `required`; класс действия ограничен сверху |
| Data exfiltration | Admin (отвечает наружу) | контекст Admin не содержит финансов и ПД других клиентов (§11) |
| Cross-tenant | все пути | `TenantContextService` уже обязателен; агент не получает tenantId из текста |
| Unauthorized campaign | Lifecycle | `campaign.send` — только Intent + approval + лимит аудитории |
| Unauthorized booking modification | Admin, Occupancy | подтверждение владельца записи; **4.43 блокирует автономию до починки** |
| Social engineering («я владелец, сделай») | Admin | роль приходит из сессии, не из текста; повышение роли через диалог невозможно по построению |

**Проверено инвентаризацией — четыре дыры, которые агенты обостряют:**

1. **Непрямая инъекция не отражается ничем.** Провайдерские строки (`services[].name`, `staff_name`, `favorite_services`) и сохранённый человеческий текст (`task`, `reason` через `tasks.list`) уходят в `tool_results` **дословно**; вся защита — одна строка системного промпта. Пока агент только рассуждает, цена — неверный совет; на L3 цена — действие.
2. **У `tool_results` нет метки доверия.** Агент не отличает серверное число от строки, которой управляет посторонний. Требование к главе 9: провенанс на каждом поле (`computed` / `provider_text` / `human_text`), и правило «из `*_text` нельзя выводить действие».
3. **Один платформенный секрет на три `@Public` моста** (inbox, recovery, crm shadow), причём арендатор берётся **из тела запроса**. Это вход в контур Admin — пер-арендные токены и подпись тела обязаны появиться до L3.
4. **Механической опоры у изоляции арендатора нет**: ни middleware Prisma, ни RLS; составной ключ `(id, tenantId)` — у 25 моделей из 64. Новый агентный запрос без `where tenantId` никто не остановит.

Плюс два ограничения рантайма: ограничение частоты стоит только на `/ai/chat` (`/ai/tools/:name/execute` и `/ai/approvals/*` не ограничены), а `approvalPolicy: 'actor'` означает, что подтверждает **тот же человек**, который запросил, — включая `marketing.campaign.send` и `expenses.create`. Для автономии это отсутствие разделения обязанностей: на L3 подтверждающим должен быть человек, а инициатором — агент, и это разные субъекты.

## 12. Модель исполнения нескольких агентов

### 12.1 Гипотеза «агенты не разговаривают друг с другом» — проверена, ПРИНЯТА

Проверка велась поиском контрпримера: существует ли задача, где прямой вызов
агента агентом даёт то, чего не даёт возврат в оркестратор?

| Сценарий | Нужен ли A2A | Почему нет |
|---|---|---|
| «Освободилось окно — кого позвать» | нет | Occupancy получает кандидатов **фактами** (`clients.dormant.list`, recency), а не «спросив Lifecycle» |
| «Выручка упала — виноват мастер или спрос» | нет | BI читает те же факты о мастерах; спрашивать нечего |
| «Клиент пишет и он спящий» | нет | оркестратор кладёт результат Lifecycle во вход Admin, если сам решил, что это нужно |
| «Кампания и личные приглашения одному клиенту» | **нет, и это довод ЗА запрет** | конфликт разрешает оркестратор, зная оба намерения; при A2A два агента договорились бы мимо политики |

**Решение: hub-and-spoke.** Агент возвращает структурный результат оркестратору;
следующий вызов решает оркестратор. Это снимает циклы, скрытые зависимости,
неограниченный расход токенов и делает разбор инцидента линейным.

### 12.2 Бюджет и маршрутизация (§19 задания)

| Правило | Значение v1 | Основание |
|---|---|---|
| Дешёвая проверка до агента | **обязательна** | большинство вопросов владельца закрываются одним детерминированным инструментом; сегодня это уже так |
| Максимум агентов на запрос | **2** | третий агент в одном запросе не встретился ни в одном разобранном сценарии |
| Максимум вызовов инструментов внутри агента | **6** | текущие сценарии укладываются в 3–4 |
| Параллельно или последовательно | параллельно **только** при независимых входах | иначе второй агент работает по устаревшему факту |
| Условие остановки | достигнут ответ, исчерпан бюджет, факт `unavailable` | отказ факта прекращает рассуждение: угадывать запрещено |
| Стоимость при отсутствии специализации | **ноль лишнего** | агент вызывается только если маршрутизатор назвал его намерение |

**Что уже стоит в рантайме:** ≤3 шага инструментов, ровно один вызов за шаг, 4000 (native 1800) токенов ответа, таймаут 20 с, вход 16 КБ, 20 запросов в минуту на пользователя. **Чего нет:** сквозного бюджета токенов и стоимости за ход (расход пишется в аудит и нигде не суммируется), параллельных вызовов, стриминга ответа. Многошаговый агент упрётся в это раньше, чем в качество модели, — поэтому бюджет и стриминг входят в главу 9, а не «когда-нибудь».

### 12.3 Маршрутизация моделей

| Слой | Модель | Причина |
|---|---|---|
| Классификация намерения, выбор агента | дешёвая | задача — метка из закрытого списка |
| Разбор периода, извлечение сущностей | **без LLM** | владелец уже есть (`reporting-period.resolver`) |
| Рассуждение агента | сильная | здесь и есть ценность |
| Композиция ответа | средняя | текст поверх готовых фактов |

Сегодня роутинга нет вовсе: есть только failover `deepseek → openai`, одна модель на контур, различие лишь в температуре по персоне и в укороченном native-режиме. Имя модели **не хранится** в определении агента: реестр описывает класс задачи, рантайм выбирает модель. Иначе смена модели превращается в миграцию архитектуры.

## 13. Структурный результат агента

Свободный текст запрещён как единственный выход. Минимальный контракт:

```ts
interface AgentResult {           // AgentResult@1
  agent_id: string;
  intent: string;
  findings: Array<{ statement: string; evidence_refs: string[] }>;
  facts_used: Array<{ capability: string; status: 'measured' | 'measured_incomplete'
                      | 'not_measured' | 'unavailable'; as_of: string }>;
  confidence: 'high' | 'medium' | 'low';
  limitations: string[];          // чего агент НЕ мог узнать — обязательное поле
  recommended_next_capability?: string;
  proposed_action_intents: Array<{
    capability: string;           // имя инструмента из каталога
    arguments: Record<string, unknown>;
    risk_tier: AiToolRiskTier;
    rationale: string;
    audience_size?: number;       // для коммуникации — обязательно
    reversible: boolean;
  }>;
  presentation_hint?: string;     // подсказка оркестратору, не готовый ответ
}
```

Два поля обязательны и не имеют значения по умолчанию: **`facts_used`** (иначе
нельзя проверить, на чём стоит вывод) и **`limitations`** (иначе агент
промолчит об отказе факта — ровно тот дефект, который глава 4 закрывала
девятью пакетами).

## 15. Core / Paid / Premium

| Слой | Состав | Обоснование |
|---|---|---|
| **Maya Core** (входит всегда) | разговор с одной Maya, Business State, базовая аналитика, оболочка оркестрации, ручные действия с подтверждением | без этого продукт не существует; оркестратор — не фича, а способ доставки |
| **Paid Agents** (отдельно) | Admin, Client Lifecycle, Occupancy, Business Intelligence | каждый решает названную проблему и имеет измеримый результат (§14) |

Проверка состоятельности: **архитектурная идентичность ≠ billing identity.**
Агент существует в системе всегда; тариф решает, доступен ли он. Обратное
(«агента нет в коде, потому что не оплачен») породило бы разные сборки для
разных арендаторов — прямо запрещено.

## 16. Целевая модель энтайтлментов

Инвентаризация дала не три источника решения о доступе, а **пять**:

1. `FeatureGuard` + `@RequiresFeature` (30 применений) — через `EntitlementsService`;
2. `SubscriptionAccessGuard` → `402 subscription_required` (`TenantAccessStateService`); `platform_owner` исключён;
3. `QuotaService` — `maxBranches` / `maxStaff` / `isWhiteLabelEnabled` читаются **напрямую из плана, мимо entitlements**;
4. `AiToolPolicyService` — роль → `ai.owner`/`ai.admin`/`ai.consultant` + `requiredFeatures` 50 инструментов;
5. `RolesGuard` / `@Roles` (72 применения).

Плюс клиентский `__meFeatureReady` поверх `GET /features/registry` — шестой,
уже на фронте.

Доказанные расхождения: белый лейбл решает `plan.isWhiteLabelEnabled`, а ключ
`branding.custom` не проверяется нигде; `serializeTenantBookingState` читает
сырой `featuresJson`, а `assertLiveBookingEnabled` — эффективные права;
`FeatureGuard` и `QuotaGuard` не исключают `platform_owner`, а
`SubscriptionAccessGuard` исключает. Права **не зависят от роли** — единственный
мост «роль → фича» живёт в `AiToolPolicyService`.

Целевая модель:

| Слой | Право | Запрет |
|---|---|---|
| **Effective entitlement (сервер)** | единственный, кто **разрешает** | — |
| Каталог планов/аддонов | описывает, из чего складывается | не решает в рантайме |
| Реестр готовности (`implementationStatus`) | может **скрыть** незрелое | **никогда не разблокирует** |
| Клиент | рисует то, что разрешено сервером | не принимает решения о доступе |

Правило для агентов: `requiredFeatures` агента проверяются той же
`assertFeature`, что и у инструментов. Второй путь проверки не заводится.
Чинить расхождение сейчас не требуется — зафиксирована цель.

Три следствия, которые обязана учесть глава 9:

- **писателя `TenantEntitlement` нет вовсе** — персональный грант, компенсацию или покупку допмодуля выдать через API физически нечем; оркестратору некуда записать выданное право;
- **`notifications.core` недостижим при любой оплате** (нет ни в одном плане, ни в допмодуле, исключён из триала по readiness), а под ним — весь конвейер напоминаний и шесть ИИ-инструментов;
- **нет машиночитаемой карты «инструмент → требуемые фичи» для агента**: она размазана по 30 декораторам и 50 записям каталога, поэтому агент не может заранее узнать, что упрётся в `feature_locked`. Реестр агентов (§5) обязан её агрегировать.

## 17. Наблюдаемость и аудит

Разделяются два потока — это требование §21–22 задания и оно принимается:

| | Reasoning trace | Business audit trail |
|---|---|---|
| Что содержит | почему вызван агент, какие инструменты, какие факты, что предложено | решение, ссылки на доказательства, намерение, вердикт политики, исход |
| Скрытая цепочка рассуждений | допустима в отладке | **не хранится** |
| Срок хранения | короткий | долгий |
| ПД и сырые промпты | не логируются | ссылки, не содержимое |
| Кто читает | инженер | владелец, разбор инцидента, деньги |

Обязательный минимум ответов после введения агентов: почему Maya позвала
агента → какие capabilities он трогал → какие факты видел (с их статусом) →
что предложил → что Maya приняла или отклонила → какое намерение ушло в движок
→ какой исход вернулся.

## 20. План миграции

Шесть шагов, каждый — отдельная глава или пакет; ни один не требует переписывать
главы 1–4.

| Шаг | Что делается | Где | Условие входа |
|---|---|---|---|
| **М0** | Реестр агентов и контракт `AgentResult@1` — только типы и таблица, без поведения | глава 9 | одобрение этого гейта |
| **М1** | Маршрутизатор: дешёвая классификация → агент или прямой инструмент; бюджеты | глава 9 | М0 |
| **М2** | BI-агент первым (**только чтение**) — проверка модели на нулевом риске | глава 9 | М1 |
| **М3** | Action Engine: исход неизвестен, сверка, повтор, лимиты, сухой прогон, аудит; починка `sending` и 4.43 | глава 6 | М0 (контракт Intent) |
| **М4** | Примитивы возможностей + первый потребитель `DomainEvent`; владельцы «ёмкости» и присутствия по клиенту | глава 5 | М3 для действий; читающая часть — параллельно |
| **М5** | Admin, Lifecycle, Occupancy на L2 → Shadow (L2.5) | главы 5/9 | М3 + М4 |
| **М6** | L3 по классам действий, затем L4 | глава 10 | закрытый §8.2 + метрики Shadow |

Обратимость: до М3 включительно ни один шаг не меняет поведение боевых
поверхностей — агенты работают там, где сегодня работает один промпт.

## 21. Риски и отклонённые альтернативы

| Риск | Почему реален здесь | Мера |
|---|---|---|
| **Агент заводит второго владельца факта** | это происходило четыре главы подряд (4.9, 4.38, 4.47, 4.75) | `facts_used` в контракте результата + запрет арифметики в агенте + барьерный тест |
| **Автономия раньше движка** | сегодняшний рантайм не знает «исход неизвестен» | L3 закрыт до §8.2 |
| **Стоимость запроса ×N** | десять агентов на вопрос «сколько заработали» | маршрутизатор + максимум 2 агента + дешёвая проверка первой |
| **Prompt injection через клиента** | Admin читает внешний текст | внешний текст — данные; список инструментов закрыт; роль из сессии |
| **Рассылка не тому сегменту** | когорты считаются неверно (4.75) | Lifecycle не выходит на L3 до починки когорт |
| **Разъезд entitlement** | три источника прав | один runtime-авторитет (§16) |
| **Агенты «договариваются» мимо политики** | классическая беда A2A | hub-and-spoke |

Отклонённые альтернативы:

1. **Десять агентов как в задании** — отклонено: пять из десяти не проходят критерий §3 (нет неоднозначности либо нет своей рамки), а Loyalty и Reputation прямо опасны (второй владелец баланса; агент поверх неканонических фактов).
2. **Agent-to-agent коммуникация** — отклонено: §12.1.
3. **Новый Action Engine с нуля** — отклонено: рантайм с подтверждениями и идемпотентностью уже существует и уже единственный на пути; переписывание потеряло бы проверенные свойства.
4. **Vector-память агентов** — отклонено: доказанной необходимости нет, риск второго источника правды есть.
5. **Агент-предсказатель** — отклонено: прогноз обязан быть capability с явной погрешностью.
6. **Автономия как свойство агента** — отклонено в пользу матрицы (агент × класс действия × арендатор).
