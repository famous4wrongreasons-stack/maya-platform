## Что установлено из исходников

1. Канонический B26 уже разделяет обновление истории и её чтение:
   `AppointmentReconciliationService` → `AppointmentObservationService` →
   `AppointmentChangeService` записывает состояние CRM. `ClientAppointmentReadService`
   читает его по текущей проверенной связи с точным Client своего tenant.
   Вход, GET и ответ AChat не запускают импорт. Это сохраняет утверждённый
   [контракт B26](CYCLE-06-BLOCKING-PACKAGE-5-B26-LOCAL-REMEDIATION-REPORT.md).
2. Периодическая сверка по умолчанию выключена. Её предусмотренные окна — ±7 и
   ±31 день; явный существующий runner допускает отдельное ограниченное окно.
   В этом проходе окна и production-настройки не менялись. Полная удалённая
   история клиента автоматически не загружается при входе.
3. Сохранение и активация CRM в предыдущем owner-сеансе импортировали Staff,
   а не всю историю клиентов. Наличие active integration не доказывает полноту
   локальных Appointment. Текущая owner-БД здесь не перечитывалась.
4. Для собственного AChat-чтения прошедших записей существует отдельная настройка
   `client_capabilities.client_self_visit_history`, по умолчанию false. Её
   канонический писатель — A22 / `Package5Wave1CanonicalCutoverService`.
   Привязка Telegram не меняет эту настройку и не создаёт consent.
5. Состоявшиеся CRM-визиты могут иметь `status=completed`, неявки — `no_show`.
   Старый ответ AChat допускал только `confirmed/canceled`, поэтому наличие
   прошедшей записи могло блокировать даже ответ о предстоящей. Два новых
   regression cases воспроизвели этот отказ до исправления.

## Изменение продукта

- Существующий `appointments.own.list` передаёт минимальную отметку посещения
  `attendance` из того же канонического Appointment и описание доступного среза:
  `history_scope = maya_canonical / last_synchronized / enabled`.
- Остаётся прежняя проверка Client, роли и tenant. Включение истории требует
  строго boolean true от существующего reader настройки. Никаких новых
  разрешений, таблиц, endpoint или писателей истории нет.
- У существующего `booking.list_own` добавлены две формы запроса:
  `period=past` — до пяти последних сохранённых прошлых записей;
  `period=last_visit` — последняя из сохранённых записей с доказанным `arrived`.
  Это semantic slots, не поиск ключевых слов в тексте. Новый tool не добавлен.
- Ответ составляет сервер. Даты, услуги и история не отправляются второй
  внешней модели. В ответ не попадают идентификаторы, контакты и заметки.
- Оплата или `completed` сами по себе не доказывают посещение. Отмена/неявка
  не выдаются за состоявшийся визит. Используется пояс филиала либо явно
  квалифицированный пояс отображения tenant для записи без филиала.
- Ответ явно ограничен уже сохранённой историей; пустота не означает «никогда
  не посещал». Отключённая история не маскируется пустым списком. Неизвестный
  период и дополнительный status-фильтр не заменяются общим списком.
- Исправлено принятие существующих CRM terminal statuses при чтении. Writable
  `AppointmentStatus`, booking, подтверждения и Action Engine не расширены.

## Свежие локальные доказательства

На committed code/test checkpoint `178b3cc3` (исходники без рабочего patch;
документация этого отчёта сохраняется отдельным последующим коммитом):

- 800 unit/architecture/regression checks, 18 suites — PASS. Включены AChat,
  handler/runtime, semantic planner, личный SCHEDULE, B26, сверка, кабинет,
  native journal-source и governed settings.
- 72 HTTP/PostgreSQL checks — PASS: 53 initial Telegram/card/history и 19
  ранее существующих successor cases. Последние используют только synthetic
  transport; реальные SMS отсутствуют.
- 10/10 targeted mutations — KILLED. До мутаций и после восстановления
  394/394 выбранных unit cases и 53/53 HTTP/PG cases — PASS. Проверены снятие
  permission/source/coverage guards, неверный порядок истории, подмена факта
  посещения, потеря attendance при чтении, возврат старого status check и
  отключение нового server-composed пути. Исходники восстановлены byte-identical.
- Backend build types, live-test types, scoped ESLint — PASS.

Сквозной тест выполняет настоящий подписанный synthetic Telegram callback,
сверку, каноническую запись, Client-read и кабинет на отдельной PostgreSQL.
Проверены Client и TENANT_OWNER без смены роли, отсутствие consent от входа,
отдельное согласие для карточки, собственные past/upcoming и отказ от чужих
данных. Тестовые салон/компания A и B используют одинаковые внешние record IDs,
но результаты остаются изолированными. Повторная сверка сохраняет ID и не
создаёт дубли/ложные события создания исторических визитов.

Если Client появился позже уже загруженных записей, только следующая штатная
сверка дополняет связь; вход/GET не скрывают этот шаг. Ошибка либо усечённый
ответ CRM не удаляет локальную историю, а состояние запуска явно остаётся
failed/truncated. Отзыв сессии закрывает карточку/историю. Отзыв privacy consent
снова скрывает карточку, не стирая бизнес-историю. Отдельно настоящий A22 на
test DB включает/выключает history: клиент не может включить её сам, следующее
чтение после выключения закрыто.

Исходный журнал и Telegram issuer в HTTP-тестах синтетические; настоящий
YCLIENTS transport в них не вызывается. Отдельные source adapter unit checks
не заменяют реальную CRM-приёмку. AChat-план в тестах scripted, а не ответ
живой модели. Это не полная release certification или проверка браузера/iPhone.

## Провенанс и оставшаяся работа

[Структурированные receipts](evidence/maya-personal-history-20261011/summary.json)
сохраняют точный tested SHA, исходные hashes, имена проверок и hashes локальных
журналов. Неудачные промежуточные прогоны также перечислены: ошибки новых
fixtures (имя поля consent и повторная ConfigService spy) исправлены в harness;
failures не выдаются за product defects. Native terminal-status regression
воспроизведён отдельно до product fix.

Первая попытка final mutation baseline на `437cda66` завершилась 393 PASS /
1 FAIL ещё до мутаций: случайный opaque nonce старого dossier-теста включал
цифры тестового phone suffix `7346`. Сам query был скрыт. В соответствующем
describe nonce теперь детерминированный и различается между вызовами; строгие
full-payload no-PII assertions сохранены. Production randomness не менялась.
Неуспешный baseline сохранён; он не засчитан как mutation PASS.

Не выполнены и не подразумеваются:

- Живой Telegram-вход и чтение настоящей карточки/истории владельца. Старое
  разрешение разрешало только публичные services/staff/company; оно не
  распространяется на private customers/history и не продлено этим проходом.
- Выбор и запуск ограниченного окна реальной сверки, проверка её покрытия,
  включение действующей настройки истории через настоящий owner-контекст.
  Это отдельная реальная приёмка, не SQL bypass и не импорт во время GET.
- Реальная языковая приёмка новых вопросов через модель; frontend карточка,
  автозагрузка истории при входе и новые UI-экраны не добавлялись.
- Восстановление ранее отозванной owner-привязки. Initial Telegram path по-прежнему
  её не реактивирует; существующий SMS successor механизм не менялся.
- Доставка уведомлений в мессенджеры; Telegram-вход с phone consent сам по себе
  не является разрешением боту писать человеку.

Результат сохранён **локально**. Нового push в этом проходе нет. Production,
существующая owner-БД, entitlements/grants, OTP/SMS/YCLIENTS effects и iPhone
не затронуты. Новых миграций нет. Старые release certificates не перенесены.
