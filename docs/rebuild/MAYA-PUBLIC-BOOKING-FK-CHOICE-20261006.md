# Минимальное решение по трём связям гостевой записи

**Рекомендация: закрепить уже описанную в schema защиту связанной истории новой
миграцией. Обычные действия пользователя не изменятся.** До решения файлы schema
и migrations остаются без изменений; это не разрешение на production migration.

| Связь | Что она связывает |
| --- | --- |
| `PublicBookingSession.tenantId → Tenant.id` | Гостевая сессия относится к конкретному салону. |
| `PublicBookingQuote.(sessionId, tenantId) → PublicBookingSession.(id, tenantId)` | Сохранённое предложение окна относится к той же гостевой сессии и салону. |
| `PublicBookingAttempt.(quoteId, sessionId, tenantId) → PublicBookingQuote.(id, sessionId, tenantId)` | Попытка записи относится к конкретному сохранённому предложению, сессии и салону. |

**Какое пользовательское действие различается сейчас? Ни одного такого действия
в реализованных API не найдено.** Создание записи, повтор того же запроса,
просмотр статуса, остановка/активация салона и истечение гостевой сессии не удаляют
родительские строки. `TenantsService.deleteFailedTrialTenant` явно запрещает hard
delete. Guest API выполняет создание, чтение и отметку доказанного отказа до
dispatch; expiry/revocation закрывает использование, сохраняя историю.

Разница проявляется в служебной операции, которой в этих API нет: удалить салон,
гостевую сессию или предложение и немедленно создать другой объект с тем же ID,
оставив дочернюю историю на месте. Тогда история продолжит ссылаться на формально
тот же ключ. Применённые SQL-ограничения допускают такую замену в одном операторе;
текущая Prisma schema требует её запретить. Это подтверждено локальным
[контрпримером](evidence/maya-development-integration-20261006/release-qualification/fk-semantics-attempt2.txt),
включая nondeferrable ограничения. Обычное удаление родителя при оставшейся
дочерней истории запрещено в обеих версиях.

## Выбор владельца

1. **Рекомендуемый: запретить такую служебную подмену связанных родителей.**
   Одной новой forward-миграцией привести ровно три FK к уже объявленному
   `ON DELETE RESTRICT ON UPDATE NO ACTION`. Имена, ключи и таблицы остаются теми
   же. Исходные migrations/checksums не редактируются. Данные, сроки хранения,
   автоматическое удаление, guest/AE authority и пользовательские сценарии не
   меняются. При применении DDL потребуются блокировки этих таблиц; длительность
   и окно применения проверяются отдельно на целевой среде. Сначала проверяется
   только disposable local PG: миграция, пустой schema diff, отказ удаления и
   подмены родителей, существующие guest regressions.
2. **Альтернатива: оставить действующее разрешение на служебную подмену.**
   Явно согласовать Prisma с фактическим `ON DELETE NO ACTION`, без DDL. Обычные
   пользовательские сценарии также не изменятся, но более строгая задекларированная
   защита будет снята из schema. Это осознанный выбор поведения, а не признание
   двух вариантов эквивалентными и не техническое подавление diff.

При рекомендуемом варианте откат приложения может оставить усиленные FK:
существующие product paths не требуют служебной подмены. Если понадобится вернуть
именно прежнее поведение БД, это отдельная обратная миграция трёх FK с теми же
именами/ключами; восстановление всей БД, удаление таблиц или откат исходных
applied migration bytes не нужны. Ни один вариант не создаёт право удалять
гостевую/AE историю: политика хранения и erasure остаются прежними.
