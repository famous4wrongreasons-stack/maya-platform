# Goods chat → ephemeral photo → reviewed receipt: development checkpoint

The existing web chat now reaches `inventory.goods.read` through the existing C9 registry and produces a source-only goods answer: sale price, cost price, per-unit cost, sale/write-off units, ratio and observed fractional store quantities remain distinct. It does not infer the unit basis of the stock rows, complete stock coverage or zero for missing values. A changed explicit read observes changed source facts; an identical request dedupes. Active tenant-wide owner membership, features and current YCLIENTS integration are checked; branch-scoped membership is refused until an authoritative company/branch mapping exists.

The narrow photo vertical is implemented with **synthetic parser/provider edges only**: one bounded request-local photo → provisional fields → owner-corrected structured review versions → existing immutable `AiApprovalRequest` → exact confirmation → existing R10/Action Engine → one stock-receipt line. This is a development checkpoint, not a usable real OCR/receipt integration or a carrier money approval release. **Goods UI COMMIT remains BLOCKED** by the exact [FR-6d/APPROVAL contract fence and proposed finite delta](MAYA-GOODS-RECEIPT-CARRIER-DELTA-PROPOSAL-20261007.md). No pricing, schedule, website or booking lane was changed.

## Implemented boundaries

- `POST /api/ai/goods/photo-preview`: current owner/features, one PNG/JPEG/WebP up to 2 MiB, bounded signature/MIME check, at most 20 provisional lines. The default parser fails with `goods_photo_parser_not_configured`; no paid model, OCR SDK, network or storage default. The owned input buffer is cleared in `finally`. This is not an image-decoder/security or OCR-quality acceptance claim.
- Provisional line names, quantity, unit label, unit price/line total, explicit-or-unknown price meaning and supplied parser confidence remain provisional. Every line requires review, including high-confidence lines. Arbitrary parser fields, supplier and raw OCR are removed; nothing is stored until the owner submits reviewed structured facts. No TeamAttachment/TeamMessage/private invoice store is introduced.
- `POST /api/ai/goods/receipt-review`: one existing physical good and one scoped store; positive fractional quantity, chosen current unit, explicit **receipt purchase price per that unit**, currency and timestamp. Exact decimal multiplication rejects unrepresentable precision rather than rounding. Invalid calendar dates, ambiguous price meaning, missing unit/currency/permission and caller-added arbitrary fields refuse. Receipt cost does not change catalog sale price or assign an absolute balance.
- Reviewed facts reuse existing encrypted `AiApprovalRequest`, preview/hash and 10-minute decision TTL. `photo_sha256`, `source_line`, `review_version` correlate versions; the photo hash is owner-supplied provenance, not authorization or authenticated OCR proof. Corrected version supersedes only pending versions. Same-version changed facts conflict; retry uses saved source revisions, never reconstructs the effect from new OCR/current source. Prior approval row locks serialize supersession with approval CAS; projection rechecks ended states after waits.
- Finite registration: `inventory.goods.receipt.prepare` is C9 ADMIN/PROPOSE_ONLY; `crm.goods.receipt.create.v1` remains financial, one target, explicit actor approval, authenticated request, L2 confirmed request, at most one execution attempt. The exact requester/hash, current actor/features/company/integration/approval expiry and current goods/store/unit/permission revision are checked again after awaited source reads and before dispatch.
- Tenant/photo/line fence prevents a second admitted receipt, including another owner with a separate draft. UNKNOWN remains UNKNOWN, with manual continuation and no blind retry after restart. This conservative fence also blocks a fresh version after any prior canonical admission; it is not a claim of automatic recovery from a definitively refused receipt.
- Successful receipt requires a string receipt ID and exact attributed readback for company/good/store/quantity/unit/purchase unit cost/line total/currency/time. Only those checked fields reach the safe result. Missing acknowledgment, lost response or mismatched post-dispatch readback cannot become success.

No canonical schema changed. Structured facts use existing AiApprovalRequest/R10/AE audit owners and the existing inventory AE values (payload 30 days, audit 7×365 days). The 10-minute approval TTL is not a deletion guarantee; compatibility rows retain their existing audit lifecycle. No new retention window, purge permission, original-photo lifecycle or background initiation is inferred.
