# YCLIENTS management: authorization and three owner questions

Supersedes the earlier overbroad stop in this same brief. [Product scope](../product/README.md#yclients-first-scope-владельца--уточнение-2026-10-05) already authorizes development of chat management through available YCLIENTS APIs, including services/prices, staff/schedules and photo-derived goods. A new Action Engine name/registration is engineering work, not another product permission request. Production effects remain outside this development authorization.

## Three questions, with an important qualification

**1. First Client binding with no earlier verified channel — required identity decision.** May an authenticated account with a unique canonical account → Client → current CRM-card chain gain initial personal authority through strict OTP sent to the freshly read card number? OTP establishes control of that number, not ownership of all historic visits; shared/reissued numbers are the actual trust issue. Existing [A18 runtime](../../maya-saas-backend/src/crm/client-channel-runtime.service.ts) requires a verified source link. Approved [SB-1 V2](widget-release-programme/sb1-v2/CONTRACT.md#authority-and-flow) is a successor flow with an exact revoked predecessor; the [V2 migration](../../maya-saas-backend/prisma/migrations/20260929190000_client_link_challenge_json_v2/migration.sql) preserves that constraint. Extending the initial branch needs this explicit trust decision, not another login system. Existing verified booking/read/relink work continues.

**2. Scoped background C10 admission — required autonomy decision.** Admit one exact pilot tenant, actor/principal, C5 task/revision source, trigger, time window, run limit, dedupe key and revocation rule for proposal-only shadow work through the existing C9. No CRM mutation, contact list or outbound action. Current [C9 admission mapping](CYCLE-09-COMBINED-SCHEMA-ACTION-ORCHESTRATION-MAPPING.md) requires a signed explicit user event, and [C9 preflight](CYCLE-09-PREFLIGHT-AND-SCOPE.md) separates autonomous repeated initiation. A machine principal cannot be fabricated by renewing a user event. The [scoped brief](MAYA-C10-SCOPED-SHADOW-DECISION-BRIEF-20261007.md) is a proposed contract, not approval; suggested numeric limits are not accepted limits. Explicit request L0/L1/L2.5 continues independently.

**3. Original invoice photo visibility/retention — conditional, only if the original is retained.** Decide whether the document is shared with the team or private to admitted inventory actors, and the retention/erasure bound. Reuse existing object storage and AC6 lifecycle machinery. The [private object-store owner](../../maya-saas-backend/src/package5-wave4/package5-team-object-store.ts) uses the team namespace; the [R12 migration](../../maya-saas-backend/prisma/migrations/20260908010600_r12_approved_foundation/migration.sql) binds uploads to team/main, a one-hour upload deadline, 48-hour bound media and exact team retention claims. [Media admission](../../maya-saas-backend/src/team-communications/team-communications.service.ts) requires a live TeamMessage and admits current team members. Those are concrete conflicting visibility/lifecycle semantics for a private invoice, not an absence of storage. Public logo/avatar URLs are unsuitable. This decision does **not** block bounded processing without original-photo persistence, goods reads or preparing a normalized reviewed draft; any persisted normalized draft still needs an exact mapping to its existing approved owner/lifecycle.

There are two unconditional owner decisions here, not three manufactured blockers. The third becomes necessary only when retained private source photos are part of the chosen implementation.

## Already authorized; continue as engineering

- Complete the finite API → current CRM adapter → one domain/AE owner → chat → current rights/confirmation → outcome/readback mapping. [All 304 documented operations](evidence/maya-development-integration-20261006/yclients-api-inventory/operations.json) are inventoried from the saved public OpenAPI; mapping pending is not an owner decision or proof the provider lacks an operation.
- External staff/service create/update remains authorized development. Preserve internal A28's `assertInternalCalendar`; add finite external owner extensions with current rights, source-qualified preview and UNKNOWN reconciliation. Keep the existing pricing/schedule owners.
- Goods catalog create/update and stock receipt are separate effects under the requested workflow. Separate sale/cost/unit/line prices, sale/write-off units, absolute balance and receipt delta. Ambiguous extracted meaning requires the user to correct that particular draft, not reapprove the product feature. Never silently convert invoice quantity into absolute stock or line total into sale price.
- A27 currently owns local `TenantCatalogItem`; do not relabel its kopeck/absolute-quantity executor as YCLIENTS goods. Register the finite external executor and review hash under the existing AE, without arbitrary HTTP or a second inventory authority. F32a's existing subtype remains bounded; do not widen its signed payload by inference.
- Current API ambiguity (`goods_transactions` in the storage-operation schema versus `transactions` in its example), integration rights, units, and authoritative readback are technical qualification work. Local synthetic fixtures are allowed; real provider/model or production calls require separate admission.
- Photo OCR is suggestion only. No confidence score, missing currency, unit ratio, item match or receipt total can become mutation authority. Bounded memory-only processing avoids the retained-original decision but does not waive privacy or draft ownership.
