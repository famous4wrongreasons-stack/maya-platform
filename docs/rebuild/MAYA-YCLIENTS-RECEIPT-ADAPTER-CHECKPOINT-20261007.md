# YCLIENTS receipt adapter: implemented transport, blocked real admission

The existing `YclientsCRMAdapter` now contains actual typed current-context reads, a single receipt POST and document-attributed readback. This replaces the previous **missing implementation**, not the separate requirement to qualify current provider permissions and behavior. **The real receipt path deliberately refuses admission:** the official API does not define selected-store and selected-transaction-type scope semantics sufficiently. No YCLIENTS business request was made. This is not a ready app function, real provider acceptance, OCR/model acceptance or C10 completion.

## Implemented source and effect path

The context reader fetches current `user/permissions/{company_id}`, `storages/{company_id}` and `goods/{company_id}/{good_id}` through the existing adapter. IDs, company, one exact store, goods units and known permission booleans must be qualified. A minimal permission projection contributes to the revision; arbitrary permission data is not persisted. Source failure is a pre-dispatch refusal. Current application owner/tenant/features/integration/approval authority is rechecked **after** awaited provider reads, immediately before the POST. A changed source revision or revoked owner gives zero POSTs.

The writer follows the pinned official schema: `POST storage_operations/operation/{company_id}` with `type_id:3`, `storage_id`, string date-time `create_date` and one `goods_transactions` row. The row has exact good, explicit operation unit (1 sale unit or 2 write-off unit), positive fractional amount, purchase unit cost, zero discount and exact line total. It never invents a preexisting `document_id`, converts by unit ratio, writes sale price, or assigns absolute stock. Catalog create/update is a separate unimplemented effect. Result flags describe what this request asks to change; they do not claim to prove every automatic provider-side consequence.

The conflicting example (`transactions`, numeric timestamp) does not override the schema. Incoming numeric JSON lexemes are preserved before IEEE-754 conversion; invalid original JSON remains invalid. Outbound numbers must round-trip exactly, otherwise the request is refused. Array/object coercion cannot pass numeric code checks. Goods requests reject redirects, preventing implicit 307/308 POST resends; other adapter lanes are unchanged.

Success requires an acknowledgment with exact company/store/type/time, then fresh GET of the exact document and its transactions. Both must agree with the reviewed receipt: document/line IDs, good, chosen unit, amount, purchase unit cost, zero discount, total, nondeleted state and equivalent RFC3339 instant. The provider's independent `meta.count` must be exactly one, alongside exactly one returned line. Missing/contradictory count, wrong scope, malformed dates or extra rows cannot become success. Currency is the explicit validated tenant setting; these provider schemas do not echo currency, and no default RUB or provider currency confirmation is inferred.

There is no documented provider idempotency key or CAS in these endpoints. Every error after the POST begins remains UNKNOWN/manual reconciliation, including redirects, lost response and bad readback. No retry or alternative endpoint. A qualified acknowledgment ID is preserved in the existing `ActionAttempt.safeResultJson` together with the minimal pre-dispatch facts and `receipt_verified:false`; it is not a successful result. The existing kernel already supports that audit field; the runtime now forwards the owner's sanitized failure observation. No new schema, authority, retention or reconciliation loop was introduced. Remote changes between reads and effect remain a no-CAS qualification risk.

## Exact provider blocker

In `user_permissions_response_data_types.properties.data.properties.storages`, fields **`storages_ids`** and **`storages_transactions_types`** have `type:array`, `items:{type:object}` without item fields or empty/all semantics. Their rendered descriptions refer to booleans, while the sole example is `[]`. Neither an accessible store, an owner role nor `storages_create_transactions_buy_access:true` proves current-token write scope for the selected store/type. Other generic role permission endpoints do not resolve this binding. The reader therefore returns `can_receive:false` and these explicit blockers:

- `yclients_receipt_storages_ids_semantics_undocumented`
- `yclients_receipt_storages_transactions_types_semantics_undocumented`

Nonnegative historical-day limits additionally need qualified timezone/day-boundary semantics; only the documented scalar `-1` is treated as unrestricted. No user event, synthetic context or guessed meaning is used to grant real authority. Resolving this needs a documented provider contract/current authorized integration qualification, not an owner guessing which interpretation is correct.

The [official source projection](../../maya-saas-backend/src/crm/fixtures/yclients-receipt-openapi-20261007.json) pins capture SHA `9ba4c2deca4197aeee333c95b4d641f19073ef91b40279b0fc83651bd502157b`, source URL and date. Six method nodes, six schemas and storage permissions match that capture exactly after removal of examples. Run `node scripts/verify-goods-receipt-openapi.mjs /path/to/captured-openapi.json` from the backend to verify offline; it never fetches or rewrites the fixture. Official capture and examples were not re-fetched during this continuation.

## Local evidence and its limits

[Evidence archive](evidence/maya-development-integration-20261006/yclients-receipt-adapter/archive.json): **351 tests / 15 suites PASS**, production and full HTTP-probe types PASS, scoped lint and diff check PASS. Adapter tests use the actual transport/body/readback methods with mocked fetch. The real context-reader branch always blocks unsupported scopes. Successful **WIRE ONLY** tests explicitly substitute a qualified test context; they do not prove real permissions or admission.

The local HTTP proof uses actual Nest/auth/C9/approval/AE and migrated PostgreSQL, with **synthetic provider/model/parser edges**. It rechecks immutable review versions, concurrency/dedupe, stale/foreign/revoked/expired boundaries and UNKNOWN. Added coverage persists an acknowledged-but-unverified document ID and pre-dispatch facts, then restarts both PostgreSQL and the process. Retry retains UNKNOWN, one execution attempt and zero resend; completed retry also has zero resend, while a previously pending approval executes once. Prepare had six synthetic dispatches across two tenants (three main scenarios and three independent race fixtures); resume had one. All three observed review-vs-approve races were approve-winning; no all-interleavings claim. HAR-13 guard: two tests/one suite. External fetch count in the HTTP proof: zero. Owned cluster stopped.

Independent read-only review verified the source projection and identified two findings: redirect resends and discarded readback count. Both were fixed and rechecked, including the related array-coercion negatives. Final review found no remaining blocking issue in this delta. Earlier local iterations include a Jest table-shape error and a mistyped test filename; they are recorded, not counted as passing runs. No real model, OCR, provider, phone, production, notification, push or merge.
