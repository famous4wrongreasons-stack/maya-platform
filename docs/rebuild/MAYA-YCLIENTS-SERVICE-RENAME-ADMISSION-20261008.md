# Service title editing — exact remaining admission

Status: **proposed, not approved or implemented as a mutation**. The current local development slice supplies a callable text-only `catalog.service.rename.preview` through the existing chat/C9/CRM. It changes no YCLIENTS data and creates no approval. Product permission for external service management is already present in [YCLIENTS-first scope](../product/README.md) and the [management brief](MAYA-YCLIENTS-MANAGEMENT-DECISION-BRIEF-20261007.md); it is not requested again.

## One narrow normative decision

Proposed `YC-SR1-CHAT-1`: admit a separately named **operational, non-MONEY** service-title configuration descriptor for one existing local YCLIENTS service, tenant-wide current OWNER/BUSINESS_OWNER, changing **only `title`**. Proposed finite mapping: C9 `catalog.service.title.update` → existing CRM owner → AE `crm.service.title.update.v1`; exact immutable source-qualified `AiApprovalRequest` → separate typed service-title canonical-chat origin → standard APPROVAL → existing AE. These names are proposals, not registered capabilities.

The preview must show original and requested internal title, company/service identity, unchanged separate online-booking title and the protected settings. Current requester, active tenant/membership/features/integration/branch/source, exact immutable arguments/hash and existing owner expiry are rechecked at decision and immediately before dispatch. A correction is a new proposal version; rejection has zero provider effect. One attempt, no blind retry/rollback; uncertain provider reply or readback remains UNKNOWN. Existing proposal/audit lifecycle is reused; no schema, new retention, generic approval adapter or background principal is admitted.

This requires a separately named **canonical-chat origin clause** (proposed F74c), exact registry/positive policy/pairing admission and their proof. [F74a](MAYA-WIDGET-CONTRACT-V1.md) is explicitly price-only; F74b separately admits the goods receipt. Neither can be inherited by another service operation. The operative source is [widget contract](MAYA-WIDGET-CONTRACT-V1.md), F29–31, F37–38, F74/F74a/F74b and R3.11 (see archived owner preflight for exact lines). Rename must not be marked as the price MONEY subtype or mint a fictitious consumed REQUEST_APPROVAL.

An ordinary AE `approvalRequirement: REQUIRED` path with a genuine consumed REQUEST_APPROVAL is also allowed by the existing contract, but its finite service request/decision owner and positive registrations do not exist yet. It is an engineering alternative, not proof that the requested one-card direct chat path already exists. No generic ban on non-MONEY approvals is asserted.

The preview's new READ key is a qualified **development registration**, not F36a/F36b or widget/release certification. There is no widget eligibility, F38 mutation mapping, release-profile regeneration or COMMIT on that key. F28 still derives the required C9 policy metadata row (`consent_class: none`, `min_verification: SESSION_VERIFIED`); the independent SOURCE_READ floor is CHANNEL_IDENTITY. These are not positive widget admission. Exact owner-kind/projector lookups refuse this key, the frozen release profile has no successor, and the runtime suppresses widget composition. Existing historical registry objects/hashes are tested separately from this exact two-space addition.

## Separate provider qualification — not an owner choice

The fresh [official service API](https://developers.yclients.com/ru/#tag/Uslugi/operation/Изменить%20услугу) uses `PATCH /api/v1/company/{company_id}/services/{service_id}` with 14 required fields. The captured OpenAPI SHA-256 is `9ba4c2deca4197aeee333c95b4d641f19073ef91b40279b0fc83651bd502157b`, verified against a fresh public document on 2026-10-08. The old PUT is deprecated. No business endpoint was called.

The API does not guarantee that an incomplete GET can reconstruct that payload. Omitted technical break becomes null; omitted dates broaden the range. The [official UI description](https://support.yclients.ru/200) says empty online/printed names inherit the internal title. `print_title` occurs in a service response example but is absent from its writable request schema; importing the goods field by analogy is not valid. Consequently, exact preservation of the printed name during a real title update is not qualified. No writer is enabled by the current preview, and the proposed normative admission does not resolve this API gap.

The required fields are exactly `title`, `category_id`, `price_min`, `price_max`, `duration`, `booking_title`, `is_multi`, `tax_variant`, `vat_id`, `is_need_limit_date`, `seance_search_start`, `seance_search_finish`, `step`, `seance_search_step`. Only `title` is intentionally changed by the narrow proposal; the other required fields need current, qualified source values. A request containing only the new title is not the recorded write contract. Omission of optional `technical_break_duration` resets it to null/inheritance; omission of `dates` broadens availability. The complete GET/write/readback preservation set must therefore be qualified, not filled from defaults or unrelated catalog data.

The remaining **name-semantics decision** is distinct from carrier admission:

- Preserve the actually visible online and printed names while changing the internal title. With empty inherited fields this cannot be achieved merely by sending their old empty values. Materializing the former visible title into `booking_title`/`print_title` changes additional stored fields and their inheritance behavior; that is not literally a title-only change, and the service `print_title` write contract is still missing.
- Explicitly permit inherited online/printed names to change with the internal title, leaving their empty raw fields unchanged. This is a broader visible effect that the current proposal does not silently authorize.

Until a choice and its required provider facts are resolved, inherited/unknown printed-name cases must refuse before dispatch. Even an explicitly named-field cohort needs qualified preservation/readback; no conditional-write/CAS guarantee is established by the recorded API. An owner choice cannot make an undocumented field writable. F32b/F74b grant only the goods purchase-cost lane and do not apply here.

Before enabling that effect, qualify the exact writable/preservation contract and representative full source/readback under separately authorized provider access. A local synthetic provider cannot prove those real semantics or provider CAS, which the documentation does not specify. Missing facts must refuse before dispatch; a post-dispatch readback mismatch cannot undo an unintended change.

Until both boundaries are resolved, the concrete useful path is current source READ → explicit old/new preview → honest “application is not connected”, with **zero approvals, AE executions, provider mutations or notifications**. A27/A28 remain internal owners. Fixed-price edits keep their existing separate implementation and admission.
