# PRODUCTION SCHEMA DRIFT — repository cannot fully reconstruct current production database

> **HIGH · технический долг / задача восстановления · БЛОКИРУЮЩИЙ**
> Обнаружено 2026-08-16 при сверке миграций перед выкатом Cycle 02 P2.
> Требует **отдельного цикла восстановления**. Смешивать с P2 запрещено
> решением владельца.

---

## Суть

**Боевая база ушла вперёд репозитория, и репозиторий больше не описывает
реальность.** Окружение, поднятое из этого репозитория с нуля, получит **другую
схему**, чем прод. Точное восстановление боевой базы из репозитория сегодня
**невозможно**.

Это не деградация работы: прод здоров, код ветки к расхождению не обращается.
Это потеря воспроизводимости.

---

## Факты

### 1. Три миграции есть в проде и отсутствуют в репозитории

```
20260814205000_marketing_tenant_compound_keys
20260814210000_outbound_messaging_delivery
20260814223000_marketing_campaign_scheduling
```

Применены к боевой базе 2026-08-14, помечены завершёнными.

**Файлов не существует ни в одной ветке и ни в одном коммите** —
`git log --all --diff-filter=A` по каждому пути не находит ничего.

| | |
|---|---|
| Миграций в ветке | 42 |
| Применено в проде | 44 (без учёта P2) |
| Отсутствует в репозитории | **3** |

### 2. Пять таблиц существуют только в проде

```
MarketingPolicy
MarketingAudienceRecipient
MarketingCampaignRecipient
MarketingConsentEvidence
MarketingDeliveryAttempt
```

В `schema.prisma` этой ветки соответствующих моделей нет.

### 3. `MarketingCampaign` ушла вперёд на 22 колонки

В проде **37** колонок, в модели ветки — **17** полей.

**Есть в проде, нет в модели** (22 колонки):

```
acceptedCount, audienceSnapshotHash, cancelledAt, completedAt,
confirmationHash, confirmedAt, confirmedByUserId, costCurrency,
costEstimateKopecks, costEstimateStatus, failedCount, lastErrorCode,
leaseExpiresAt, leaseOwner, messageSnapshotHash, provider, queuedAt,
retryCount, scheduledFor, skippedCount, startedAt, unknownCount
```

**Есть в модели, нет в проде: ничего.** Единственные два имени, которые
выглядят отсутствующими (`audience`, `tenant`), — это поля СВЯЗЕЙ Prisma, они
не являются колонками.

Расхождение **одностороннее**: прод строго новее, ветка ничего своего не
добавляла. Это важно для восстановления — достаточно догнать прод, разбирать
встречные изменения не придётся.

> Поправка к первичному отчёту: сначала я привёл 30 колонок и утверждал, что
> `audienceId` и `channel` в проде отсутствуют. Это было следствием обрезанного
> вывода команды, а не фактом. Обе колонки в проде есть.

### 4. Происхождение неизвестно

`origin currently unknown`. Ни один коммит, ни одна локальная или удалённая
ветка не содержит этих файлов. Незапушенная рабочая копия или другая машина не
исключены, но подтвердить нечем.

### 5. Вероятная первопричина

`root cause likely historical deploy from dirty/uncommitted working tree`.

`deploy/vps/deploy.sh` синхронизирует **рабочее дерево**, а не коммит: `rsync`
отправляет каталог `prisma/` как есть. Миграции, созданные локально и не
закоммиченные, уезжают в прод и применяются, а затем теряются вместе с рабочей
копией.

Ровно этот риск записан в [BASELINE.md](BASELINE.md) разделом «Выкат из
рабочего дерева» и уже приводил к потере правки в другом случае.

Проверка чистоты дерева перед выкатом появилась **только в Cycle 01 P0**
(2026-08-16) — то есть уже ПОСЛЕ того, как это расхождение возникло. С тех пор
повториться оно не может.

### 6. Следствие

`current repository is not sufficient for exact production DB reconstruction`.

Конкретно это означает:

- аварийное восстановление из репозитория даст схему без пяти таблиц и без
  двадцати двух колонок;
- проверочный стенд, поднятый из репозитория, не воспроизводит боевое
  поведение маркетинга;
- любая будущая миграция, затрагивающая `MarketingCampaign`, писалась бы против
  неверного представления о таблице.

## Что НЕ входит в этот долг

Расхождение **не блокирует Cycle 02 P2**: миграция идентичности клиента не
пересекается с маркетингом ни одной таблицей и ни одной колонкой. Это доказано
отдельно перед выкатом P2.

## Требуется отдельным циклом восстановления

1. Выяснить происхождение трёх миграций (другая рабочая копия, незапушенная
   ветка, ручной DDL).
2. Снять фактический DDL с прода и оформить недостающие миграции как файлы,
   чтобы репозиторий снова описывал реальность.
3. Привести `schema.prisma` в соответствие с боевой `MarketingCampaign`:
   двадцать две колонки и пять таблиц описать моделями. Встречных изменений
   нет — догонять надо только в одну сторону.
4. Ввести регулярную сверку: `release:preflight` уже умеет ловить этот класс
   (`Database has N migration(s) absent from this release`), но в выкат он не
   подключён — подключить.
5. Проверить, что после восстановления чистая база из репозитория совпадает с
   боевой структурно.

Пункт 4 — самый дешёвый и предотвращает повторение.
