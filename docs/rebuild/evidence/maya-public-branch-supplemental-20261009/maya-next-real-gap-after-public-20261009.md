# Следующий real missing link: exact-policy dormant READ

Выбираю **первый ход `mt-retention_drill_down-0:1` / `-15:1`**, но только конечный product path, который сверяет запрос «больше двух месяцев» с уже подтверждённым C8 правилом. Это не объявляет выполненными cohort/regularity/ranking и не перекрашивает исходные 81.

Конкретный source counterexample: `src/ai-tools/owner-review-plan.ts:43–61` переводит singleton Lifecycle в clarification при любых entities; `ai-core.service.ts:1724–1764` возвращает fixed alternative до C8 READ. Поэтому даже tenant, у которого уже опубликован current C8 signal по точному правилу `{elapsed:{unit:'calendar_month',count:2},comparison:'gt'}`, не может получить соответствующий запрошенному порогу ответ по этому path. Это отличается от отсутствия фактов в текущем baseline.

Владелец уже существует: `c8.policy.ts:121–143` задаёт elapsed/comparison/evidence/coverage; `c8.read.ts:195–219` связывает параметры с exact current policy ID/hash и immutable result; `c8.read.ts:599–640` отдаёт privacy-safe projection. `clients.dormant.list` (`ai-tool.catalog.ts:693`, handler:1101) прямо запрещает caller threshold override. Existing C9 Lifecycle (`c9.lifecycle-source.ts:70–98`, `c9.orchestrator.ts:440–480`) владеет bounded selection, receipts, current refs и final authority/expiry fences.

Минимальная реализация: конечное допустимое semantic period → server-only exact rule constraint; включить этот constraint в existing C9 request/receipt hash. Existing C8 owner выбирает только current опубликованные client POLICY_SIGNAL с exact calendar_month=2, gt, proven_attendance, подходящими branch/service scope и явной coverage. Не конвертировать в60дней, не менять/создавать policy из чата, не пересчитывать asOf до today, не вынимать PII и не называть capped partial signals полным списком. Старый unconstrained command/replay сохраняется. Missing/mismatched/stale policy/result → точное unavailable/clarification, без молчаливого более широкого C8 обзора. Не смешивать три selected snapshots с полнотой всей клиентской популяции.

Проверка: component RED на существующем exact2month signal; counterexamples30/60days, gte, wrong service/branch, stale policy hash, late revocation/expiry, UNKNOWN history. Затем отдельный synthetic canonical A22/C8 setup до census → actual chat/auth/C9 owner READ → same-key/process+PG restart → immutable same refs и source/policy drift refusal. Синтетическая установка правила доказывает условную capability, не существование такой policy у реального бизнеса; исходный corpus не менять.

Ограничение baseline доказано: `test/widgets-live/support/current-candidate-sources.ts:390–403` публикует30day/gt/PARTIAL правило, rankingObjectives пуст. Поэтому ни этот baseline, ни simple fixture fill не закрывает requested2months. Без existing exact rule полезным результатом остаётся честное указание несовпадения; новый реальный threshold, регулярность и приоритет требуют отдельной семантики/policy. Это предложение конечной product интеграции с существующим owner, не разрешение применять policy к real tenant.

Почему не остальные: C7 `measurement.finance.ts:518–527` всегда emits confirmed_cash/refunds/net_profit=null/NOT_MEASURED; booked/provider gross не заменяют их. Pricing исключён текущим scope; public/journal/reviews повторно не предлагаются. Нужды в paid model/live provider для реализации и synthetic проверки finite C8 route нет.
