# B24 Web Push V1 — approved owner contract and candidate

Owner approval accepts checkpoint `e068772c` and the exact `package5-b24-web-push-delivery-endpoint-schema-v1-proposal.md`, Option A. This approval supersedes that proposal's pending-decision labels. It does not reopen Waves 1–6 or authorize a new business action class.

- One new model: `ClientWebPushEndpoint`; no backfill, new consent or Client creation. Endpoint episodes belong to an exact tenant-qualified Client and a verified active ClientChannelLink. Authenticated channel identity remains separate from the browser delivery capability.
- At most five unterminated endpoint episodes per Client, serialized under database locks. Sixth registration rejects atomically. No eviction or silent cross-Client/tenant reassignment; historical claims remain immutable. Revoked links immediately fail delivery eligibility, while their unterminated episodes conservatively occupy capacity until an explicit approved terminal operation.
- Opaque endpoint/material HMACs use separate namespaces. The entire normalized subscription is encrypted with the existing EncryptionService. HTTPS endpoint max 4096 UTF-8 bytes; plaintext JSON max 8192; encrypted persisted envelope max 10963. No plaintext endpoint, p256dh or auth in DB/log/audit/ActionExecution evidence. Public operation receipts contain only opaque episode ID, ACTIVE/INACTIVE and changed.
- Exact same-owner registration retries preserve ciphertext and evidence byte-for-byte. Explicit owner unsubscribe, explicit same-owner replacement, or a proven permanent invalidation terminates one exact episode. Inactive rows do not occupy capacity. An old delivery attempt cannot terminate a successor.
- Web Push is a transport of the existing canonical Communication Delivery action. It uses a bounded immutable device snapshot and existing campaign/recipient/attempt claims, dispatch boundary and outcomes. No business/AI/PWA route can send directly. No new business action class or outreach authority.
- Only an already accepted canonical Client communication with an explicit verified recipient HMAC can initiate the device continuation. The primary execution ID is its durable source identity. Supported existing Client intent types are appointment reminders and exact wanted-slot availability; other legacy raw-identity producers fail closed. B9 source code and its owner remain unchanged. Wanted-slot continuation verifies the immutable B9 intent identity against an actionable exact Client interest and cannot extend expiry past the requested slot start.
- Before each device dispatch: current active link, exact Client/tenant, authenticated encrypted material/HMAC, active endpoint, and existing consent/preferences/quiet-hour policy. Registration creates no consent. Missing authority/material or unsupported destination means no send.
- Provider acceptance is a transport acknowledgement, not proof the customer saw the message. RFC 8030 section 7.3 makes send-operation HTTP 404 an expired subscription result. Authentication failures, HTTP 410 without a stronger provider contract, throttling, timeouts and UNKNOWN do not authorize revocation. Ambiguous outcomes follow existing manual-only reconciliation with no blind retry.
- Canonical adapter uses pinned `web-push` 3.6.7 and existing VAPID key material, without rotation or a new secret store. Destinations are restricted to the existing standard FCM, Mozilla Push and Apple Web Push hosts; no arbitrary URLs or redirects. No live provider call is used for proof.

PWA shows the server-confirmed result and an explicit device disconnect operation. Browser permission alone is not registration success. Sixth-device rejection is visible. A confirmed local disconnect suppresses automatic re-registration on reconnect. Both active PWA variants, proxy and iOS mirror preserve their existing UI structure.

Legacy plaintext registry rows are preserved as history, not used as current authority or backfilled. Legacy raw-identity Client/staff Web Push senders are inert; the approved canonical staff inbox/APNS/Telegram paths remain separate. Client Web Push registration must be repeated after verified linking; this Client-only schema does not invent a staff device owner.

Protocol references: [RFC 8030 — subscription expiry](https://www.rfc-editor.org/rfc/rfc8030.html#section-7.3), [RFC 8291 — Web Push encryption](https://www.rfc-editor.org/rfc/rfc8291.html), [web-push Node adapter](https://github.com/web-push-libs/web-push).

The runtime candidate must pass the mandatory deployment gates and additive production migration preflight before activation. This document is not a production completion or Final Package 5 PASS. After production structural verification the entire 13-family Final Gate must run again; a new bypass requires exact evidence and STOP.
