## Proposed contract A

**Members and reads.** Send/read/upload requires current active exact-tenant `tenant_owner`, `business_owner`, `tenant_admin`, `administrator` or `staff` membership through R02's canonical current-principal boundary. User without Telegram is supported through the canonical endpoint; no synthetic legacy chat ID is created. Platform role alone and unrelated-tenant membership do not grant access. All such current members may read retained `team/main` history, including members who joined later; their joining does not add them to any earlier notification plan. Sender may withdraw only their own message while still an active member; management status alone cannot delete another sender's text. No global/PWA `conversation_id` supplied by a caller widens scope. Presence/typing remain ephemeral protocol state, never business/admission authority.

**Message command.** `send_team_message` admits an immutable normalized payload (at most 2,000 text characters and/or one exact owned finalized attachment). It persists one canonical message and the fixed notification plan before any notification effect. New and retry HTTP/PHP/AI/native initiators all use the same owner; a model may not create a synthetic sender `0` or post a reply in the background. In V1 automatic team MAYA replies are retired; separately authorized canonical AI/task surfaces remain available. A correction is an explicit new message; no implicit edit/version rewrite. `withdraw_team_message` creates a canonical tombstone/receipt and removes content from future reads. Repeated withdrawal returns that receipt; it does not add another business transition. Withdrawal cannot unsend an already observed notification or resurrect media.

**Attachment admission.** `reserve_team_attachment` first binds current User, tenant, immutable upload identity, expected content SHA-256, declared size, media kind/MIME, normalized display filename and server-allocated opaque object key. Only then may HTTP/PHP transport receive chunks into **quarantined, non-public staging** scoped to that reservation. This grants no route/PHP permission to publish, rename/copy into final storage, attach a final object or unlink one. No raw path, URL, basename guess, PHP session or upload token alone authorizes it: current principal plus the exact active reservation is required. Reservation expires after **one hour**. Existing transport size/type limits are retained; any expansion requires a separate reviewed change.

`finalize_team_attachment` verifies staged bytes, size, detected MIME and expected digest, then its **canonical AE executor** exclusively performs final object publish/commit to the reservation's already allocated object key. The final effect belongs to that reservation and original finalize ActionExecution; HTTP/PHP/chunk-finish handlers are initiators only. The executor persists/reconciles the final storage receipt and marks SEALED only after a proven final commit. Staging identity derives deterministically from the reservation; verified staged-content evidence lives in the existing encrypted normalized AE input, so no extra model/column is needed. `storageReceiptHash` is the effect's observed final receipt, not caller evidence authorizing that effect. A byte mismatch fails and never attaches. `send_team_message` consumes one finalized attachment only once for the same tenant/owner; no cross-message re-use or third-party URL. Its read lifetime becomes **48 hours from message admission**, preserving the existing two-day media lifetime while moving enforcement to a canonical owner. Byte chunks/normalization scratch are not a published attachment; any final object remains governed by the reservation until bound or disposed. Media is served only after current tenant membership, exact message attachment relation and non-expired/non-withdrawn state checks. No unauthenticated public static URL. Expiry returns unavailable without a DB write or unlink during read.

“Private managed object store” is an ownership/access abstraction over the existing documented storage surface, **not selection or installation of a new cloud/storage provider**. No new infrastructure, credentials or subscription is approved by this proposal. The existing storage adapter must support a bounded canonical executor and exact key/hash observation; if it cannot, implementation must report that concrete gap rather than select another provider automatically. Direct public PHP final-file publication is retired, not rebranded as that adapter.

**Identity, concurrency, crashes.** Four new AE classes: `send_team_message`, `withdraw_team_message`, `reserve_team_attachment`, `finalize_team_attachment`. Each uses the existing ActionExecution unique tenant/scope/request-key binding and immutable normalized-input hash; booking-specific fields are unused. Same key/same intent returns the same execution/message/object; same key/changed text, attachment, scope or upload digest conflicts. New key means a deliberately new message even if text is identical. Concurrent first requests have one key winner; attachment consume is an atomic one-message claim. Stable original identity survives all PHP aliases, chunk completion and native adapters.

A lost upload/finalize/send response is **UNKNOWN receipt**, not proof of failed business admission. Query/reconcile the original reservation/object digest/message/execution. Never unlink the final object on curl timeout, non-2xx with ambiguous outcome, or local cancellation. Do not mint a new message key, object key or provider operation. A crash after message commit but before fan-out preserves the committed receipt. A crash after final publish but before its receipt is reconciled by the same finalize AE/reservation and exact final object key/digest. UNKNOWN cannot issue a second publish, allocate another key or unlink the final object; absence/mismatch remains unresolved or proven failure under the canonical adapter policy. An unrelated same-named file is not evidence.

**Delivery plan.** The canonical message is the shared team surface; notification is a separate A12 projection. At message admission snapshot exact active eligible team User recipients excluding sender, deduplicate and order by canonical User ID. V1 admits **one Inbox slot per recipient only**; content is a generic “new team message” pointer, not raw message/media text. No raw staff/admin list, no Telegram/Web Push/APNS effect and no deferred R11 mute contract is assumed. Existing applicable canonical preference/eligibility checks still apply; membership alone is not a marketing-consent assertion. If a required eligibility proof is absent, the slot is explicitly skipped, not rerouted.

Slot identity is tenant/message/User/`inbox`; materialization links exactly one existing A12 ActionExecution/envelope. Confirmed slots skip, pending slots continue, UNKNOWN reconciles the original slot; other recipients are independent. Revoked recipient skips before effect; new members/devices are never added. Notification failure does not undo message acceptance. **Cross-channel retry after UNKNOWN, deterministic fallback and route reselection: NO.** No durable bulk sender is added: the message plan and slot links orchestrate existing per-slot CD. Inbox transactional reconciliation remains the sole delivery truth.

**Retention and deletion.** Proposed `team-lifecycle-retention/1`: message text visible for 365 days from admission; attachments for 48 hours after binding; abandoned reservations for one hour. Withdrawal immediately hides message and attachment but is a tombstone, not an erasure claim. New narrowly scoped AC6 classes `purge_team_message_payloads` and `purge_team_attachment_payloads` handle encrypted payload/object disposal after the relevant deadline or explicit withdrawal. They require canonical owner/policy, exact tenant/object/content hash, no live execution/lease and no unresolved upload/send/delivery reference. Deletion is restart-safe through existing MaintenanceRun/ItemClaim; missing exact object after a claimed purge is reconciled, not a new arbitrary unlink. No cleanup in public read/fetch, no whole-directory TTL sweep, no deletion of unclaimed legacy media. Idempotency/audit hashes and tombstone rows remain; automatic row/audit destruction is not authorized. These two policy additions are explicit proposals, not a general expansion of A30 or B23 Client-history deletion.

**Historical state.** New canonical foundation applies to new messages/uploads only. Raw `sender_chat_id`, sender name, old media filename and HTTP success logs do not prove canonical Member/tenant or accepted intent. No backfill invents them. Old data/files remain untouched and excluded from the new authorized team feed; any later migration requires independently proven source bindings. `/clear` must return the already-approved unsupported/server-history-retained response with no shared-history persistence, no PII/history error payload and no false “cleared” success. It does not clear canonical team messages either.

## Canonical intent fingerprint

Canonical hash contract for this proposal: a versioned, explicitly named object; recursive sorted object keys and UTF-8; Unicode NFC text with CRLF→LF and trimmed outer whitespace; opaque IDs are exact, not lowercased; dates are UTC ISO milliseconds; absent optional business values become explicit null; arrays retain specified order or are sorted/deduplicated only where declared sets. No raw JSON serialization contract, random encryption bytes, HTTP headers, retry time, worker ID or transport metadata. Caller intent hash is separate from immutable admission-plan hash: retries first match the original command, then reuse the original plan, never recompute recipients/routes from current discovery. Current eligibility is a dispatch check, not permission to rewrite that plan.

Exact intent inputs: send = `{contractVersion,tenantId,senderUserId,conversationKey:"team/main",normalizedText,attachmentId,attachmentContentHash}`; withdrawal = `{contractVersion,tenantId,senderUserId,messageId,expectedRevision}`. Reserve = `{contractVersion,tenantId,ownerUserId,contentSha256,declaredSize,mediaKind,mime,normalizedFilename,retentionPolicyVersion}`; finalize = `{contractVersion,tenantId,ownerUserId,attachmentId,expectedDigest,verifiedStagedSize,verifiedStagedMime,stagedContentHash}`. Finalize resolves verified staging facts for that reservation server-side before admission; its later final storage receipt is an outcome, excluded from input fingerprint. Retries resume the original normalized intent/reservation and inspect the exact final key/hash when needed, without requiring vanished staging to be republished or accepting a caller receipt hash. Message plan hash freezes content/version, sorted canonical recipient IDs, policy/eligibility snapshot and one exact Inbox slot each. Allocation timestamps/object keys and recipient discovery are first-admission state reused on retry, not reasons to mint another logical message.

Constraints: TeamMessage unique `(tenantId,conversationKey,senderUserId,identityHash)`, CHECK `conversationKey='team/main'`, exact sender/withdrawer Membership FKs, unique non-null attachment link and send/withdraw execution links, `(id,tenantId)` uniqueness. Withdrawer must equal sender; withdrawal fields are all present or absent together. TeamAttachment unique `(tenantId,ownerUserId,uploadIdentityHash)` and server objectStoreKey; exact Membership/AE FKs, positive bounded sizes, reservation-before-finalization state checks; the message's `(attachmentId,tenantId,senderUserId)` FK references attachment `(id,tenantId,ownerUserId)` so another owner's object cannot attach. ActionExecution unique `(tenantId,teamMessageId,teamMessageSlotKey)` and restrictive composite message FK. Scoped capability CHECK requires both fields at admission; the key is exactly recipient User plus `inbox` in the frozen plan. Existing MarketingCampaignRecipient Membership FK and dispatch-time manifest comparison enforce the actual recipient/tenant. No new slot status, lease or attempt columns.

Admission/atomicity: TeamMessage `sendExecutionId` and TeamAttachment `reserveExecutionId` are NOT NULL same-tenant links. An admitted business executor commits its owner row, immutable plan/attachment claim and relevant mutation receipt in one PostgreSQL transaction. Finalization permits SEALED/BOUND only with its confirmed same-tenant `finalizeExecutionId` and matching storage receipt; nullable finalization fields mean an unfinalized reservation, never a usable attachment. A not-yet-materialized recipient slot exists solely in the frozen message manifest. Lower AE creation commits `teamMessageId` and `teamMessageSlotKey` **within admission**, not in a post-admission link update. Its unique slot binding and scoped CD boundary check confirmed message outcome, exact recipient/plan and current eligibility before effect. There is no admissible unbound package delivery. Crashes recover the same manifest slot/execution. Nullable withdrawal fields mean no withdrawal; an actual withdrawal atomically records actor, identity and execution together.

Virtual Prisma fields, not columns: message → Tenant, sender/withdrawer Membership, send/withdraw owning ActionExecution, optional attachment and delivery ActionExecutions; attachment → Tenant, owner Membership, reserve/finalize ActionExecution and optional message; ActionExecution → optional team message using the two added columns; corresponding inverse collections. No conversation table, delivery-slot table, new User/provider-attempt table or generic maintenance engine. Message payload/plan and attachment upload/retention lifecycle are the two independently necessary business owners.
