# MAYA → настоящий AI-native: чего не хватает (исследование 2026-06-18)

> Многоагентное исследование: аудит кода + прецеденты + ролевой доступ + скорость/простота.
> Связано: [VISION_AI_NATIVE.md](VISION_AI_NATIVE.md). 19 источников (Anthropic, OWASP, vertical-AI отчёты, voice-latency гайды).

## Вердикт
Ядро MAYA уже архитектурно верное для AI-native: LLM в цикле tool-use (`claude_ai.get_ai_response`), инструменты read+write, память (`remember_client_preference`/`barber_knowledge`), проактивные джобы (`_daily_report_job`/`_god_watch_job`/листы ожидания), ворота `is_admin`/`get_master_by_chat_id`, обезличивание под 152-ФЗ. Anthropic прямо рекомендует именно такой самописный простой loop, а не фреймворк. **Не усложнять. Добить 3 тонких слоя.**

## Гэп 1 — RBAC + «любая тема по уровню допуска» (главный, = запрос Стаса №1)
Сейчас: ВЕСЬ массив `TOOLS_CACHED` уходит в модель независимо от роли; разграничение — частью инлайн в хендлерах (`is_admin`), частью промпт-блоками («## Режим владельца») — а промпт **уговариваем** (OWASP LLM01/06: авторизацию нельзя держать в промпте).
Что внедрить (тонко, без фреймворка):
1. **ROLE_TOOLS dict** `{client:[...], master:[...], manager:[...], owner:[...], founder:'*'}` → в `tools=` слать СРЕЗ по серверной роли. Клиент перестаёт видеть `get_business_report`/`get_client_dossier`. Срезы держать стабильными (не ломать prompt-cache).
2. **Детерминированный `authorize(user_id, role, tool, args)`** между «модель предложила tool_use» и вызовом хендлера (propose→decide→execute). Deny → возвращать tool_result-ом («доступно только владельцу»), не падать. Слой-2 поверх существующих inline-проверок.
3. **Identity на сервере**: staff_id/phone/tenant — из сессии (chat_id/web_auth), НИКОГДА из аргументов LLM (иначе IDOR через агента). Часть уже так — закрепить инвариантом.
4. **Topic-scope ≠ data-scope (две ОСИ).** «Любая тема» = ослабить ТЕМАТИЧЕСКИЙ guardrail для доверенных: client → только домен салона; founder (tg 948205934) → «обсуждай что угодно». Но деньги/данные всё равно режутся гейтом независимо от темы.
5. **Аудит-лог** каждого tool-call (роль, user_id, allow/deny, причина) — дебаг + 152-ФЗ + в GOD-режим «Здоровье».

## Гэп 2 — операционная автономия + проактивность (= запрос «полностью заниматься операционкой»)
Сейчас: LLM читает/советует, но многие write-действия не автономны (рассылки, смена графика, выплаты, склад). По дизайну нет HITL-контура.
Что внедрить:
1. **Риск-тиринг инструментов + human-in-the-loop**: read-only → автономно; нейтральный write (запомнить привычку, перенос на свободный слот) → автономно + лог; деньги/разрушающее (`set_record_paid`, выплаты, перенос на занятое) → подтверждение владельца + JSON-схема действия + проверка суммы в границах + **идемпотентность по record_id** (закрывает уже найденную гонку двойной оплаты).
2. **Проактивный слой — 3 типа триггеров**: cron (дайджест/обзвон неподтверждённых за N ч/no-show), event-driven на вебхуках YClients (создание/отмена → решение агента), monitoring (загрузка/выручка ниже порога → черновик владельцу). Частично есть — осознанно расширить, с дедупликацией, тихими окнами, контролем бюджета TTS.
3. **Procedural-память** (правила салона + выученные паттерны «этот клиент всегда переносит») поверх уже имеющихся semantic/episodic. Хранить redacted в SQLite.
4. **Фазы автономии**: сейчас approval-gate на всё write → потом авто-аппрув низкорисковых по статистике → потом проактивные действия с пост-отчётом. Ложится на Фазы 0-4.

## Гэп 3 — скорость (= «значительно быстрее»), сохраняя простоту
Замер: голосовой ход ~12-15с (мозг Sonnet 9с с tool-раундами + TTS 3.5с). Цель «живого» диалога <800мс через прокси РФ недостижима, НО ощущение мгновенности даёт стриминг.
Что внедрить (по убыванию пользы):
1. **Sentence-boundary chunking для голоса** (ГЛАВНЫЙ рычаг): как только в стриме `/api/chat/stream` накопилось первое предложение — сразу в `voice.py` TTS и проигрывать, не дожидаясь финала. TTFA из «весь ответ+весь TTS» → «первое предложение+TTS чанка». Уже есть SSE — дотянуть до голоса.
2. **Tiered routing** (уже частично: голос→Haiku): быстрый Haiku-классификатор интента; сложное → Sonnet.
3. **Prompt caching** на Claude: системный промпт + бизнес-константы (503759/кассы/OWNER_STAFF_ID) + tools → кэш-префикс; ПД и время — ПОСЛЕ брейкпоинта (заодно держит 152-ФЗ). Проверять `usage.cache_read_input_tokens` (гоча: `datetime.now()`/имя/UUID в начале убивают кэш).
4. **Filler-фразы** при tool-calls («секунду, смотрю расписание») + keep-alive к прокси/YClients.
5. **Гоча**: прокси РФ не должен буферизовать SSE (иначе стрим придёт целиком в конце — см. скилл sse-chat-streaming, `import json as _json`).
Будущее: speech-to-speech (160-400мс) недоступно через прокси РФ — реалистична оптимизированная 3-ступенчатая цепочка со стримингом, либо Yandex SpeechKit (телефония).

## Что НЕ делать (чтобы осталось простым)
- НЕ мигрировать на LangChain/LangGraph (over-engineering для 1 салона; тихие петли, сложная отладка).
- НЕ давать автономный write на деньги без HITL+идемпотентности (152-ФЗ + EU AI Act авг-2026: человеческий надзор обязателен).
- НЕ держать авторизацию в промпте; НЕ принимать чужие ключи (phone/staff_id) из аргументов LLM.
- НЕ ломать prompt-cache волатильным префиксом; НЕ раздувать инструменты без риск-тиринга.

## Приоритет внедрения
1. **RBAC-слой** (ROLE_TOOLS + authorize() + topic-scope) — даёт «любую тему по допуску» + закрывает дыру безопасности. Тонкий: ~dict + одна функция.
2. **Sentence-boundary стриминг голоса** — самый крупный выигрыш по ощущению скорости.
3. **HITL риск-тиринг + идемпотентность оплаты** — открывает безопасную операционную автономию.
4. Проактивный слой + procedural-память — превращает в «оператора».
