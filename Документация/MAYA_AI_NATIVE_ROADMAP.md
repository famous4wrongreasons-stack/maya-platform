> Технический план превращения MAYA (AI-ассистент барбершопа «Мужская Эстетика» → SaaS для салонов) в полноценную AI-Native систему.

# МОДУЛЬ 1. ГОЛОСОВАЯ MAYA

## 0. Честная оценка готовности (что реально стоит в проде)

| Подсистема | Файл | Готовность | Что осталось |
|---|---|---|---|
| Мост realtime↔Claude (мозг=Claude, рот=realtime) | `realtime_bridge.py` | **~85%** | устойчивость к разрывам, метрики латентности, multi-tenant голоса |
| Дуплекс/barge-in/эхо | `realtime_bridge.py` (server-VAD, полудуплекс `state["speaking"]`) | **~75%** | полудуплекс грубоват — теряем перебивы клиента, пока MAYA говорит; нужен клиентский AEC |

| TTS-фоллбэк (Telegram-голос, не-realtime) | `voice.py` | **~80%** | не подключён в `bot.handle_voice` (код-сниппет в докстринге, флаг `VOICE_REPLIES_ENABLED`) |

| Биллинг голоса | `ai_billing.log_audio_usage/log_tts_usage` | **~90%** | ставки «ПРИБЛИЗИТЕЛЬНЫЕ» (коммент в коде) — выверить по факту |
| Выбор голоса/эмоции/стиль per-салон | — | **~10%** | нет UI/таблицы; зашито `REALTIME_VOICE="marin"` |
| **РФ-альтернатива (Yandex SpeechKit)** | — | **0%** | не начато — критично для телефонии и для отказоустойчивости при падении прокси |

**Вывод CTO:** «голос как ChatGPT» в PWA реально работает и архитектурно правильный (realtime = только уши+рот, Claude = мозг с инструментами/RBAC/152-ФЗ). Это редкая, дорого-стоящая часть, которую НЕ надо переделывать. Оставшиеся 15-20% — это **надёжность под РФ-прокси, второй (РФ-нативный) голосовой контур и продуктовые фичи (выбор голоса, эмоции).**

## 1. Цель

Довести голосовую MAYA до **продакшн-надёжного, естественного дуплексного голосового диалога** с двумя независимыми контурами:
- **Контур А (есть):** премиум-голос «как ChatGPT» через gpt-realtime + прокси — для PWA/in-app, где допустима задержка прокси.
- **Контур Б (достроить):** РФ-нативный голос на **Yandex SpeechKit** (STT+TTS, серверы в РФ, без прокси, минимальная латентность, естественный русский) — как (1) фоллбэк при падении/деградации прокси и (2) **единственно пригодный стек для телефонии** (gpt-realtime по PSTN не звонит).

Плюс продуктовый слой: выбор голоса, скорость, эмоциональная подача, per-салон настройка (для SaaS).

---

## 2. Польза владельцу салона

- **Голосовой «директор в кармане»**: владелец за рулём/между клиентами спрашивает голосом «сколько сегодня выручки», «кто в смене завтра», «перенеси Иванова на 15:00» — MAYA отвечает голосом, дёргая те же 26 инструментов (RBAC уже различает owner/founder).
- **SaaS-дифференциатор**: «голосовой ассистент как у ChatGPT, но для салона» — продаётся дороже. Per-салон выбор голоса (брендинг).
- **Снижение нагрузки на админа**: голосовой контур = задел под телефонию (Контур Б) → автоприём звонков «запишите меня».
- **Контроль расходов**: `ai_billing` уже разбивает голос отдельной строкой «🎙 Голос MAYA» в GOD-режиме «Деньги».

## 3. Польза мастерам

- Руки заняты (стрижёт) → голосом: «во сколько следующий клиент», «какой у него прошлый раз был фейд», «добавь к текущему визиту бороду». Инструменты `get_client_dossier`/`set_record_services` уже есть.
- Советы по технике голосом из `barber_knowledge` без отрыва от работы.

## 4. Польза клиентам

- Запись голосом в PWA в стиле живого разговора с администратором (а не текстовый чат) — выше конверсия и «вау».
- Доступность: пожилым/занятым проще сказать, чем печатать.
- (Контур Б, перспектива) позвонил на номер салона в нерабочее время → MAYA голосом записала.

## 5. Архитектура (как ложится на текущий стек)

### Что переиспользуем (НЕ трогаем ядро)
- `realtime_bridge.run_session` — главный цикл, GA-события, barge-in, филлеры, общая память по `chat_id` (`load/save_conversations`), `anonymizer.redact_pii` на входящем транскрипте (152-ФЗ соблюдён — в LLM уходит обезличенный текст).
- `claude_ai.get_ai_response` как мозг (executor, чтобы не вешать сокет).
- `ai_billing.log_audio_usage/log_tts_usage`.
- WS-эндпоинт `webhook_server.py:5512` + тикет-авторизация в query (браузерный WS без кастом-заголовков) + nginx TLS на `rt.malesthetic.pro`.

### Новые/изменённые модули Python

1. **`voice_provider.py` (новый, абстракция провайдера).** Интерфейс `VoiceBackend` с методами `stream_stt(audio_chunks)`, `synthesize_stream(text)`. Реализации: `OpenAIRealtimeBackend` (обёртка текущего моста) и `YandexSpeechKitBackend` (новый). Выбор бэкенда — по конфигу/состоянию здоровья прокси. Это превращает «один жёстко зашитый realtime» в переключаемый контур.

2. **`yandex_speech.py` (новый, Контур Б).** Yandex SpeechKit v3 gRPC-стриминг:
   - STT: streaming recognition (отправляем PCM-чанки, получаем партиалы+финал) — заменяет server-VAD OpenAI на VAD SpeechKit.
   - TTS: streaming synthesis (текст Claude → аудио-чанки, голос напр. `marina`/`alena`, эмоция `neutral/good`, `speed`). Серверы в РФ → **прямой вызов, БЕЗ прокси, низкая латентность**.
   - Мост остаётся тем же: SpeechKit = уши+рот, Claude = мозг. `think_and_reply` не меняется — меняется только транспорт аудио.

3. **`realtime_bridge.py` (изменения, не переписывание).**
   - Вынести транспорт за `voice_provider` (минимальный рефактор: `say()` и pump-функции работают через бэкенд).
   - Heartbeat/reconnect: при обрыве WS к OpenAI (частый кейс через прокси) — не падать всей сессией, а переподключить `ws_oa` либо деградировать на Контур Б (Yandex), уведомив клиента `{type:"backend_switch"}`.
   - Метрики: засекать `t_transcript → t_first_audio` (ответ Claude) и `t_filler` — писать в SQLite для дашборда латентности.

4. **`bot.py` (изменение, активация TTS-фоллбэка для Telegram).** Подключить готовый `voice.synthesize` в `handle_voice` (сниппет уже в докстринге `voice.py`) — голосовой ответ на голосовое сообщение в Telegram. Это «дешёвый» контур без realtime-сессии.

### Таблицы SQLite (`database.py`, миграции через `migration.py`)

- **`voice_settings`** (per-tenant для SaaS, сейчас один салон): `company_id, backend('realtime'|'yandex'), voice_id, speed REAL, emotion TEXT, enabled INT`. Источник для `_session_config()` и Yandex TTS вместо хардкода `REALTIME_VOICE="marin"`.
- **`voice_sessions`** (метрики/аудит): `id, chat_id, started_at, ended_at, backend, turns, ms_to_first_audio_avg, interruptions, cost_usd, error`. Кормит GOD-режим «Здоровье»/«Деньги».

### Эндпоинты aiohttp
- (есть) `GET /api/realtime` — WS-мост.
- (новый) `GET /api/voice/settings` / `POST /api/voice/settings` — RBAC owner: выбор голоса/скорости/эмоции/бэкенда. Пишет в `voice_settings`.
- (новый, опц.) `GET /api/voice/health` — статус прокси/бэкендов для GOD-режима.

### Где живёт ИИ
Без изменений: мозг = Claude (Sonnet 4.5) в `claude_ai.get_ai_response`. Голосовые провайдеры — **только транспорт речи** (STT/TTS), не принимают решений. Это и есть гарантия 152-ФЗ и RBAC: текст обезличен `redact_pii` до Claude, инструменты под `authorize`.

## 6. Какие API

**Внешние:**
- **OpenAI Realtime** (`wss://api.openai.com/v1/realtime`, gpt-realtime) + **OpenAI TTS** (`/v1/audio/speech`, gpt-4o-mini-tts) — **через прокси PROXY_URL** (геоблок РФ). Уже работает.
- **Yandex SpeechKit v3** (gRPC `stt.api.cloud.yandex.net` / `tts.api.cloud.yandex.net`) — **прямой вызов из РФ-VPS, без прокси**. Auth: IAM-токен или API-ключ сервис-аккаунта Yandex Cloud. Это РФ-сервис → ПД допустимы (как YClients/ЮKassa), но в LLM всё равно идёт обезличенный текст.
- (Telegram) `reply_voice` для TTS-фоллбэка.

**Наши новые эндпоинты/инструменты Claude:**
- Новые инструменты Claude НЕ нужны для самого голоса (голос — транспорт). Достаточно существующих 26.
- Опционально 1 инструмент: `set_voice_preference(voice_id, speed)` — чтобы клиент/владелец голосом просил «говори помедленнее/другим голосом» → пишет в `voice_settings`.

### Явная рекомендация (цена/качество для RU в РФ)
**Двухконтурная стратегия, без отказа от уже внедрённого realtime:**
1. **Контур А = gpt-realtime через прокси** — оставить как премиум-голос для PWA. Он уже работает и звучит «как ChatGPT». Менять не на что: ElevenLabs дороже и тоже за прокси; Cartesia не про русский.
2. **Контур Б = Yandex SpeechKit** — достроить как РФ-нативный фоллбэк и обязательный стек для телефонии. Лучшая цена/качество для русского без прокси-хопа, серверы в РФ (152-ФЗ комфортнее), нет геоблока.
3. **Гибрид (рекомендуемый дефолт): мозг Claude + рот/уши = выбираемый бэкенд.** PWA-премиум → realtime; деградация прокси/телефония → Yandex. Мост уже спроектирован под это (Claude отвязан от транспорта).

**НЕ брать ElevenLabs/Cartesia/Azure** для RU-в-РФ: дороже и/или тоже требуют прокси, не дают преимущества над связкой realtime+Yandex.

## 9. Приоритет

- **P0:** Reconnect/деградация моста + метрики латентности (**M**). Прокси РФ нестабилен → сейчас обрыв `ws_oa` роняет всю сессию (видно по `run_session` except). Это бьёт по уже-работающей фиче — чинить первым.
- **P0:** Активация TTS-фоллбэка в Telegram (**S**) — почти бесплатно, расширяет охват голоса на Telegram-аудиторию.
- **P1:** Yandex SpeechKit как второй контур (**L**) — отказоустойчивость + обязательный фундамент телефонии + 152-ФЗ-комфорт.
- **P1:** Per-салон выбор голоса/эмоций (**M**) — SaaS-дифференциатор, нужен до масштабирования на тенанты.
- **P2:** Клиентский AEC (**M**) — улучшает дуплекс, но полудуплекс уже закрывает эхо.
- **P2/отдельный модуль:** Телефония (**XL**).

## 10. Пошаговый план внедрения (MVP → полная версия)

**MVP-укрепление (то, что уже есть → надёжно), ~2 недели:**
1. Добавить reconnect к `ws_oa` в `realtime_bridge.run_session`: при `CLOSE/ERROR` от OpenAI — попытка переподключения (1–2 раза), при неудаче `{type:"backend_unavailable"}` клиенту вместо тихой смерти.
2. Завести таблицу `voice_sessions`, писать метрики `ms_to_first_audio`, число перебиваний, стоимость. Вывести в GOD-режим «Здоровье».
3. Подключить `voice.synthesize` в `bot.handle_voice` (сниппет готов), включить `VOICE_REPLIES_ENABLED` за флагом, прогнать на VPS.
4. Rate-limit и лимит конкурентных WS-сессий в `realtime_handler` (защита бюджета ИИ).

**Фаза 2 — РФ-контур, ~3 недели:**
5. Завести сервис-аккаунт Yandex Cloud, ключи в env (НЕ в `config.py` — учесть SECURITY_REMEDIATION).
6. Написать `yandex_speech.py`: streaming STT (gRPC) + streaming TTS, формат PCM16 24k (совместимо с клиентским PCM в app.html).
7. Ввести `voice_provider.py`, обернуть оба бэкенда; мост выбирает бэкенд по конфигу/здоровью прокси.
8. Авто-деградация: при N ошибках прокси за окно — переключить активные сессии на Yandex, уведомить клиента (`backend_switch`), плавно.

**Фаза 3 — продукт/SaaS, ~1.5 недели:**
9. Таблица `voice_settings` + эндпоинты `GET/POST /api/voice/settings` (RBAC owner) + экран в app.html: выбор голоса (realtime: marin/cedar…; yandex: alena/marina/filipp…), скорость, эмоция.
10. Прокинуть выбор в `_session_config()` (realtime) и в Yandex TTS-параметры вместо хардкода `RT_VOICE`.
11. Голосовой инструмент `set_voice_preference` (опц.) — «говори помедленнее» голосом.

**Фаза 4 — качество дуплекса, ~1.5 недели:**
12. Клиентский AEC (WebAudio `echoCancellation`/собственный) → снять грубый полудуплекс `state["speaking"]`, разрешить перебивать MAYA реально.
13. Тюнинг VAD (`silence_duration_ms`, `threshold`) и порога филлера (0.6с) по собранным метрикам латентности прокси.

**Телефония — выносится в отдельный XL-модуль** (Voximplant/Novofon SIP + Yandex SpeechKit + мост к Claude; счета Стаса).

## Риски и ловушки этого модуля (и обход на нашем стеке)

1. **Обрыв прокси роняет всю голосовую сессию.** Сейчас `except` в `run_session` просто закрывает сокет. → Reconnect + авто-деградация на Yandex (P0, шаг 1/8). **Главный риск надёжности.**
2. **Эхо/самопрослушивание.** Грубый полудуплекс (`if state["speaking"]: continue`) глушит микрофон, пока MAYA говорит → теряем перебивы клиента. Обход на сейчас — server-VAD barge-in уже ловит `speech_started`; полноценно — клиентский AEC (P2).

# МОДУЛЬ 2. MAYA KPI — Причинная KPI-система барбершопа

> Не дашборд цифр, а **аналитик, который объясняет ПОЧЕМУ цифра изменилась**. Поверх уже работающего `analytics.business_pulse` достраиваем материализованный слой дневных срезов + движок декомпозиции метрик на факторы + Claude-нарратив. Грундировано в реальный стек: YClients-обёртка, SQLite-WAL, Claude tool-loop, РФ-прокси, 152-ФЗ.

---

## 1. Цель

Превратить MAYA из «отвечает на вопрос про выручку» в **автономную систему причинной KPI-аналитики**, которая:

- считает **полный набор KPI** (а не только выручка/чек/визиты, что есть сейчас): новые/возвратные/удержание, % загрузки кресла и мастера, выручка-на-кресло, выручка-на-мастера-час, средний межвизитный интервал, конверсия запись→визит, no-show rate;
- при любом отклонении даёт **причинно-следственное объяснение через декомпозицию**: метрика = произведение/сумма факторов, MAYA находит, какой фактор «съел» дельту («выручка −12%: визитов −3%, средний чек −2%, но главный вклад — мастер Иван отработал на 18 ч меньше → −9% к его выручке-на-час»);
- работает в трёх режимах: **pull** (владелец спрашивает голосом/чатом), **push** (включается в дневной отчёт 21:00 и god-watch 09:00), **alert** (аномалия → проактивный пуш).

Ключевое отличие от текущего `business_pulse`: тот считает дельту на уровне 3 метрик. Модуль 2 раскладывает каждую дельту на **дерево факторов до уровня мастера/услуги/дня/часа** и превращает дерево в человеческий текст.

---

## 2. Польза владельцу салона

- **«Почему», а не «сколько».** Сейчас god-watch говорит «выручка −12%». Стас всё равно звонит уточнять. Модуль 2 сразу: «−12%, потому что в среду никто не работал в смену Ильи (отпуск), а это −22 000 ₽ — компенсируй догрузкой субботы».
- **Раннее предупреждение** на опережающих метриках: падение конверсии запись→визит и рост межвизитного интервала видны за 2–3 недели до падения выручки. Это «датчик дыма», а не «отчёт о пожаре».
- **Объективная база для решений по мастерам:** выручка-на-час и % загрузки кресла по каждому мастеру → понятно, кому добавить часы, кому поднять прайс, чей простой кресла стоит денег.
- **Бенчмарк для SaaS:** те же KPI по тенантам в god-режиме «Подписчики» → «ваш салон в топ-20% по удержанию» как продающий аргумент.

## 3. Польза мастерам

- **Личная панель KPI** (расширение уже существующего кабинета мастера): «твоя загрузка 74%, выручка-на-час 1 850 ₽, удержание клиентов 61% — выше среднего по салону». Геймификация без публичного рейтинга (152-ФЗ/этика — только свои цифры + анонимный «средний по салону»).
- **Понятная связь усилий и денег:** видно, что догрузка простаивающих окон или допродажа услуги напрямую двигает их выручку-на-час, а ЗП считается прозрачно (переиспользуем `salary_percent`).
- **Совет от MAYA** (через уже готовый `masters_ai.py`/Haiku): «у тебя межвизитный интервал клиентов 42 дня против 31 по салону — предложи привычным запись наперёд».

## 4. Польза клиентам

Косвенная, но реальная:
- **Меньше простоя кресла** = больше свободных слотов в удобное время (выручка-на-кресло толкает владельца открывать окна спроса).
- **Удержание как метрика** → MAYA триггерит заботу о «выпадающих» клиентах (связка с уже готовыми `reactivation.py` и `slot_waitlist`), клиент получает релевантное «давно не виделись» вместо спама.
- **Стабильность мастеров:** прозрачная справедливая аналитика → ниже текучка → клиент стрижётся у своего мастера.

## 5. Архитектура (как ложится на текущий стек)

### Принцип: материализованный дневной слой + декомпозиция on-demand
YClients API медленный и пагинируемый (`get_company_records` до 25 страниц, `get_company_transactions` до 40), плюс весь Claude-трафик идёт через РФ-прокси с задержкой. Гонять полный пересчёт за месяц на каждый вопрос нельзя. Решение — **ETL раз в сутки в SQLite, причинность считаем из кэша мгновенно**.

```
YClients API ──(nightly ETL 03:30)──► kpi_daily / kpi_master_daily (SQLite-WAL)
                                              │
        ┌─────────────────────────────────────┼───────────────────────────┐
        ▼                                      ▼                           ▼
  kpi_engine.py                         claude_ai.py tool                webhook эндпоинты
  (чистая математика:                  get_kpi_report / explain_kpi    /api/panel/kpi*
   агрегация, дельты,                   (Claude видит ДЕРЕВО факторов,  (PWA-панель мастера/
   дерево декомпозиции)                  пишет нарратив, НЕ считает)      владельца)
```

### Новые модули Python

| Файл | Роль |
|---|---|
| **`kpi_etl.py`** | Ночной ETL. Тянет за прошедший день `get_company_records` + `get_company_transactions` + графики мастеров (`get_staff_schedule` по каждому активному), считает атомарные показатели дня и пишет в `kpi_daily`/`kpi_master_daily`. Идемпотентен по дате (UPSERT). Запускается из `bot.py` cron-джобой (рядом с `_daily_report_job`). |
| **`kpi_engine.py`** | Чистая математика, без сети и без ИИ. Читает кэш-таблицы, агрегирует за период, считает все KPI, строит **дерево декомпозиции** (см. §ниже). Возвращает структуру `{kpi, value, prev, delta, factors:[...]}`. Тестируемо юнитами. |
| **`kpi_narrative.py`** (тонкий) | Формирует промпт-«пакет факторов» для Claude и парсит ответ. Сам по себе ИИ-логики не содержит — мост между `kpi_engine` и `claude_ai`. |

### Изменённые модули
- **`analytics.py`** — `business_summary`/`business_pulse` остаются как fallback и переиспользуются в ETL (логика подсчёта нал/карта/ЗП уже верная — не дублируем). ETL вызывает существующий парсинг транзакций.
- **`claude_ai.py`** — +2 инструмента (`get_kpi_report`, `explain_kpi`), оба owner/master-only (расширяем `_OWNER_ONLY`/RBAC `ROLE_TOOLS`; мастер видит ТОЛЬКО свои + анонимный средний).
- **`webhook_server.py`** — +эндпоинты панели; god-watch/daily-report дёргают `kpi_engine` для богатого нарратива.
- **`bot.py`** — регистрация `_kpi_etl_job` (03:30 МСК) и `_kpi_alert_job` (после ETL).

### Новые таблицы SQLite (кэш)

```sql
-- атомарный дневной срез по салону (1 строка/день)
CREATE TABLE IF NOT EXISTS kpi_daily (
  day            TEXT PRIMARY KEY,          -- YYYY-MM-DD
  gross          REAL,                       -- валовая по услугам
  cash_sum       REAL, card_sum REAL,
  visits         INTEGER,                    -- уникальные оплаченные записи
  avg_check      REAL,
  new_clients    INTEGER,                    -- первый визит в истории
  returning_clients INTEGER,
  noshow         INTEGER,                    -- attendance==-1/2
  booked         INTEGER,                    -- всего записей на день (для конверсии)
  attended       INTEGER,                    -- attendance==1
  chair_open_min INTEGER,                    -- сумма рабочих минут всех кресел (из графиков)
  chair_busy_min INTEGER,                    -- сумма seance_length пришедших
  computed_at    TEXT
);

-- срез по мастеру в день (N строк/день)
CREATE TABLE IF NOT EXISTS kpi_master_daily (
  day        TEXT, staff_id INTEGER,
  gross      REAL, visits INTEGER,
  work_min   INTEGER,                        -- фактически отработанные минуты (график YClients)
  busy_min   INTEGER,                        -- занятые услугами минуты
  new_clients INTEGER, noshow INTEGER,
  PRIMARY KEY (day, staff_id)
);

-- для удержания/межвизитного интервала: последний визит клиента
-- (НЕ имя/телефон — только client_id YClients + дата = не ПД-чувствительно)
CREATE TABLE IF NOT EXISTS client_visit_state (
  client_id   INTEGER PRIMARY KEY,
  first_visit TEXT, last_visit TEXT,
  visit_count INTEGER,
  preferred_staff_id INTEGER
);
```

> 152-ФЗ: в кэше KPI **нет ПД** — только числовые агрегаты, `staff_id`, `client_id` (внутренний ID YClients, не имя/телефон). Имена клиентов сюда не попадают, в LLM уходят только обезличенные числа и `staff_id`→имя мастера (имя мастера — не клиентские ПД, как уже принято в `analytics.py`). Биометрии нет вообще. Контур чистый.

### Где живёт ИИ и как генерит причинность

ИИ **не считает математику** (LLM плохо считает, плюс это дорого/медленно через прокси). Декомпозицию делает детерминированный `kpi_engine`, Claude получает **готовое дерево факторов** и его задача — выбрать главное и написать человеку.

**Метод декомпозиции — мультипликативный/аддитивный bridge-анализ** (как в финансовом variance analysis):

Выручка раскладывается тождеством:
```
Gross = Σ_master ( work_hours_m × utilization_m × revenue_per_busy_hour_m )
```
Дельта между периодами раскладывается по факторам **методом последовательной подстановки** (sequential substitution / LMDI-подобно): фиксируем все факторы на «вчера», меняем по одному, измеряем вклад каждого в рубли. Получаем атрибуцию: «из −18 000 ₽: график −12 000 (Иван −18ч), загрузка −4 000, чек +0... » — это **точная арифметика, не галлюцинация ИИ**.

`kpi_engine` отдаёт:
```json
{
  "kpi": "gross", "value": 132000, "prev": 150000, "delta": -18000, "delta_pct": -12,
  "factors": [
    {"name":"Иван: −18 рабочих часов", "contrib_rub": -12000, "kind":"schedule", "staff_id":1460233},
    {"name":"Загрузка кресел −6 п.п.", "contrib_rub": -4000, "kind":"utilization"},
    {"name":"Средний чек +1.3%",       "contrib_rub": +900,  "kind":"avg_check"},
    {"name":"Новых клиентов −2",        "contrib_rub": -2900, "kind":"acquisition"}
  ],
  "data_quality": "ok"
}
```
Claude (Sonnet) превращает это в 2-3 предложения на русском + рекомендацию. Для голоса/быстрого — Haiku. Промпт жёстко инструктирует: **использовать только переданные числа, не выдумывать**.

## Риски и ловушки (под наш стек)

1. **YClients как единственный источник правды лжёт в ретро.** Оплаты/неявки правят задним числом (отметили attendance через 2 дня, провели транзакцию позже). Дневной срез, посчитанный ночью, устаревает. → **Ловушка:** «выручка вчера» в kpi_daily ≠ реальной через неделю. **Обход:** ETL пересчитывает не только вчера, а **скользящее окно последних 14 дней** каждую ночь (UPSERT затирает). Дорого по API, но иначе цифры расходятся с кассой.

2. **Знаменатель загрузки — самый хрупкий KPI.** «Рабочие минуты кресла» из `get_staff_schedule` включают перерывы, неявки мастера, технические окна. Если знаменатель кривой — загрузка и выручка-на-час врут, и причинность («Иван −18ч») становится ложью. **Обход:** считать `work_min` строго из `is_working`+`slots` графика (как `who_works_on` уже парсит часы), вычитать перерывы; на старте показывать загрузку как «ориентир», валидировать на 2-3 реальных днях со Стасом перед тем как пускать в причинные выводы.

3. **Атрибуция дельты зависит от порядка подстановки** (классическая проблема variance analysis — interaction terms). Наивная последовательная подстановка даёт разный результат при разном порядке факторов. **Обход:** использовать LMDI или равномерное распределение остатка (residual), фиксировать порядок факторов, в нарративе честно отделять «основной фактор» от «остаток/взаимодействие», не присваивать копеечную точность.

4. **Claude всё равно попытается посчитать сам и приврать.** Даже с готовым деревом LLM любит «уточнить» арифметику. **Обход:** промпт-контракт «числа брать ТОЛЬКО из factors[], запрещено вычислять новые проценты»; постпроверка — если в ответе появилось число, которого нет во входе, отбросить/перегенерировать (как в HITL-контуре уже есть паттерн валидации).

5. **Backfill упрётся в rate-limit YClients** и «истекла лицензия YClients» (известная гоча из `yclients-api-patterns`). **Обход:** throttle + ретраи + резюмируемость по дате (чекпоинт в settings), запуск ночью.

6. **Малые числа → шумные проценты.** В выходной с 2 визитами «−50% выручки» — статистический шум, не сигнал. **Обход:** в `kpi_engine` порог абсолютных значений (как `business_pulse` уже делает с `no_prev_data`/«рост с нуля»); алерты только при значимом и абсолютном, и относительном отклонении.

7. **`new vs returning` требует полной истории клиента**, а `get_client_history` дорог по-клиентно. **Обход:** не дёргать по каждому — вести `client_visit_state` инкрементально из ночного ETL (первый раз увидели client_id → new; есть в таблице → returning). Backfill заполняет стартовое состояние.

# МОДУЛЬ 3. MAYA BI

> Грунднуто в реальный код: `analytics.py` (`business_summary`, `top_services`, `business_pulse`, `resolve_period`), `claude_ai.py` (tool-loop, `get_business_report` на строке 367/1299, `_OWNER_ONLY`), `webhook_server.py` (:8080), `database.py` (SQLite WAL), `yclients.py` (`get_company_transactions`/`get_company_records`/`get_masters`). 🔴 **Главный архитектурный факт:** вся аналитика сейчас считается **на лету из YClients API** (см. `business_summary` → `_yc.get_company_transactions(from,to)`), локального хранилища фактов **нет**. Это и есть корневое ограничение, вокруг которого строится модуль.

---

## 1. Цель

Превратить разовый read-only инструмент `get_business_report` (плоская сводка за период) в **разговорный BI-слой**: владелец/менеджер спрашивает «почему упала выручка в мае», «почему просел средний чек», «кто из мастеров растёт быстрее», «какие услуги дают максимум прибыли, а не оборота» — и MAYA отвечает **с разложением на факторы и цифрами**, плюс рисует интерактивные дашборды в PWA. Технически: построить **локальный слой фактов (data mart) в SQLite**, поверх него — **семантический слой метрик** и **NL→запрос→объяснение** через Claude-loop, не ломая 152-ФЗ и геоблок.

Граница: BI = **диагностика и ответ на «почему/кто/что»** (декомпозиция, тренды, прогноз, сравнение). Это надстройка над Модулем 2 (KPI), а не его дубликат.

---

## 2. Польза владельцу салона

- **«Почему упала выручка»** разложенная на факторы автоматически: `Δвыручка = Δтрафик × средний чек + трафик × Δсредний чек`, далее — за счёт каких мастеров/услуг/дней недели/новых-vs-постоянных. Сейчас он видит только итог, а не причину.
- **Сравнение периодов с объяснением** (`business_pulse` уже считает предыдущее окно — наращиваем интерпретацию).
- **Прибыльность ≠ оборот:** услуга может давать оборот, но при 50–60% ЗП мастера маржа ниже, чем у короткой услуги. BI считает вклад в маржу (есть `salary_percent`, `OWNER_STAFF_ID`).
- **Прогноз выручки** на конец месяца/недели по темпу + сезонности + уже забронированным будущим записям (`get_company_records` на будущие даты).
- **Когортный анализ удержания:** сколько клиентов вернулось через 30/60/90 дней, отток (база для Модуля 8).
- **Аномалии с причиной:** не просто «-18%», а «-18%, потому что мастер X не работал 4 смены + вторник был выходной».

---

## 3. Польза мастерам

- **Личный кабинет роста (RBAC role=master):** своя выручка/средний чек/загрузка кресла/% повторных клиентов, динамика месяц-к-месяцу, **только свои данные** (телефоны клиентов скрыты — паттерн уже есть в журнале).
- **«Что подтянуть»:** «у тебя загрузка вторника 40% — самый слабый день», «средний чек ниже среднего по салону на 15% — реже допродаёшь уход».
- **Геймификация без токсичности:** позиция в анонимном рейтинге роста (а не абсолюта), чтобы новичок не демотивировался.

---

## 4. Польза клиентам

Клиент BI напрямую не видит (это owner/master-инструмент), но выигрывает косвенно:
- Оптимизация расписания под спрос → меньше отказов «нет слотов» в пик.
- Связка с листом ожидания (`freed_slot.py`) и реактивацией (`reactivation.py`): BI вычисляет «угасающих» клиентов → триггерит персональное касание (Модуль 8).
- Прозрачно: **никакие персональные BI-данные клиента в LLM не уходят** — агрегаты обезличены.

## 5. Архитектура

### Корневая проблема и решение
Сейчас каждый отчёт = живые вызовы YClients (`get_company_transactions` + `get_company_records`). Для BI это не годится: медленно (через тот же РФ-прокси-латентность нет, YClients в РФ — но rate-limit и «истекла лицензия YClients» — известная гоча), нельзя считать когорты/тренды за полгода, нельзя гонять NL→SQL. **Нужен локальный data mart в SQLite (WAL).**

### Новые/изменённые модули Python

| Модуль | Что делает |
|---|---|
| **`bi_etl.py`** (новый) | Инкрементальный ETL: тянет `get_company_transactions`/`get_company_records` за окно, нормализует в факт-таблицы. Запускается cron-джобой (рядом с `_daily_report_job`). Идемпотентность по `(record_id, tx_id)` — паттерн как в импорте сертификатов из памяти. |
| **`bi_facts.py`** (новый) | Слой запросов к факт-таблицам: чистые функции `revenue_by_factor()`, `cohort_retention()`, `master_growth()`, `service_margin()`, `forecast_revenue()`. Без LLM. |
| **`bi_semantic.py`** (новый) | Семантический слой: реестр метрик/измерений (`metric: revenue|avg_check|visits|margin|utilization`, `dim: master|service|weekday|client_type|day`), их SQL-шаблоны. Источник истины для NL→запрос. |
| **`analytics.py`** (изменить) | `business_summary`/`top_services` переключить читать из data mart (с фолбэком на live YClients, если ETL отстал). Сохранить сигнатуры — `webhook_server._period_report` не трогаем. |
| **`claude_ai.py`** (изменить) | Добавить инструменты `bi_query`, `bi_explain`, `bi_forecast` в список tools и в диспетчер (рядом со строкой 1299). Добавить в `_OWNER_ONLY` (+ master-scoped вариант). |
| **`webhook_server.py`** (изменить) | Новые эндпоинты для дашбордов PWA (см. п.6). |

### Таблицы SQLite (data mart, отдельный неймспейс `bi_`)

```sql
-- Звезда: один факт = одна оплаченная услуга в визите
CREATE TABLE bi_fact_service (
  tx_id INTEGER, record_id INTEGER, dt TEXT,          -- ISO дата-время
  staff_id INTEGER, service_id INTEGER, service_title TEXT,
  amount REAL, is_cash INTEGER,
  client_hash TEXT,                                    -- HMAC телефона, НЕ сам телефон (152-ФЗ)
  attendance INTEGER,                                  -- пришёл/неявка
  PRIMARY KEY (tx_id, service_id)
);
CREATE INDEX ix_bi_fact_dt ON bi_fact_service(dt);
CREATE INDEX ix_bi_fact_staff ON bi_fact_service(staff_id, dt);

CREATE TABLE bi_dim_master (staff_id INTEGER PRIMARY KEY, name TEXT, percent REAL);
CREATE TABLE bi_agg_daily (                            -- предрассчитанные дневные агрегаты
  day TEXT, staff_id INTEGER,
  gross REAL, visits INTEGER, cash REAL, card REAL,
  PRIMARY KEY (day, staff_id)
);
CREATE TABLE bi_etl_state (key TEXT PRIMARY KEY, last_synced_dt TEXT, updated_at TEXT);
```

- **`client_hash`** = `hmac_sha256(salt, normalized_phone)` — даёт когорты/удержание/новый-vs-повторный **без хранения и без отправки ПД в LLM**. Соль в `config.py`/env.
- **Материализация vs на лету:** `bi_agg_daily` пересчитывается ETL (день — естественный квант). Произвольные срезы (по услуге/мастеру/дню недели) считаем **на лету из `bi_fact_service`** — SQLite на годовом объёме одного салона (≈десятки тыс. строк) делает это за миллисекунды. Материализованных VIEW SQLite не имеет → используем агрегатную таблицу + триггер-on-ETL, а не SQL VIEW.

### Поток данных
```
YClients API ──(cron bi_etl.py, инкремент)──> bi_fact_service / bi_agg_daily (SQLite WAL)
                                                       │
PWA дашборд ──GET /api/bi/dashboard──> bi_facts.py ────┤ (чистый SQL, без LLM, мгновенно)
                                                       │
NL-вопрос ──/api/chat──> claude_ai loop ──tool bi_query──> bi_semantic→SQL→bi_facts
                                          └─tool bi_explain──> декомпозиция факторов ──> Claude формулирует ответ
```

### Где живёт ИИ
ИИ **не пишет сырой SQL** (опасно, и 152-ФЗ). Claude выбирает **метрику + измерения + период из закрытого реестра** `bi_semantic` (structured tool-call), бэкенд детерминированно строит параметризованный SQL. Claude получает **обезличенные числа** и формулирует объяснение. Декомпозицию факторов («почему упало») считает **Python (`bi_explain`)**, а не LLM — LLM только вербализует. Это и быстрее (через прокси гоняем мало токенов), и безопаснее.

### Переиспользуем готовое
- `analytics.business_pulse` (уже считает предыдущее окно/anomaly) → ядро `bi_explain`.
- `salary_percent`, `OWNER_STAFF_ID` → расчёт маржи.
- RBAC `_OWNER_ONLY` + `authorize` + `tool_audit` → доступ к BI-инструментам.
- `anonymizer.redact_pii` → страховка на выходе в LLM.
- SSE-стриминг чата (скилл `sse-chat-streaming`) → ответы BI печатаются.
- cron-инфраструктура (`_daily_report_job`) → расписание ETL.

## 6. Какие API

**Внешние:**
- **YClients API** (РФ, без геоблока) — единственный источник фактов: `get_company_transactions`, `get_company_records`, `get_masters`, `get_services` (для duration/маржи). Уже в `yclients.py`. Учитывать rate-limit → ETL батчами по дням, ретраи, гоча «истекла лицензия».
- **Anthropic Claude** через `PROXY_URL` (геоблок) — только вербализация и выбор метрики. Минимум токенов: в LLM уходят итоговые числа, не сырые строки.
- НЕ нужны зарубежные BI/vision-сервисы → 152-ФЗ-блокеров в этом модуле нет (биометрии нет, ПД хешируется до ETL).

**Наши новые эндпоинты aiohttp (`webhook_server.py`):**
- `GET /api/bi/dashboard?period=&role=` — данные для дашборда (KPI-карточки, тренд, разбивки). Read, RBAC.
- `GET /api/bi/master/{staff_id}` — личный кабинет мастера (own-scope гард).
- `GET /api/bi/forecast?horizon=month` — прогноз.
- `POST /api/bi/explain` — { metric, period } → факторная декомпозиция (для кнопки «почему» в UI без чата).

**Новые инструменты Claude (`claude_ai.py` tools):**
- `bi_query(metric, dimensions[], period, compare?)` — структурный запрос к семантическому слою.
- `bi_explain(metric, period)` — разложение изменения на факторы.
- `bi_forecast(metric, horizon)` — прогноз с доверительным интервалом.

**Визуализация в PWA (что рисуем, app.html, без тяжёлых либ — лёгкий SVG/canvas):**
- KPI-карточки (выручка/чек/визиты/загрузка) со стрелкой Δ к прошлому периоду.
- Линия тренда выручки по дням + наложение прогноза (пунктир).
- Bar: топ услуг по **марже** (новинка) и по обороту (есть).
- Хитмэп загрузки: день недели × час (где простаивают кресла).
- Водопад (waterfall) «почему изменилась выручка»: трафик / средний чек / микс услуг / мастера — визуализация `bi_explain`.
- Воронка удержания когорт (30/60/90 дней).

| Выбор метрики/измерений из NL (router) + вербализация ответа | **Claude Haiku 4.5** через `PROXY_URL` | Дёшево, быстро, задача простая (structured tool-call по закрытому реестру). Через прокси — но токенов мало, латентность приемлема. |

| Факторная декомпозиция, прогноз, когорты | **Без LLM — чистый Python/SQL** (`bi_facts`, `bi_explain`) | Детерминированно, быстро, проверяемо, не жжём токены и не гоняем через прокси. Прогноз: скользящее среднее + сезонность по дню недели + линейный тренд; при росте данных — Holt-Winters (`statsmodels`, локально на VPS). |
| Запасной NL-router без прокси (риск геоблока/деградации) | **YandexGPT / GigaChat** (РФ, без прокси) | Только для роутинга «вопрос→метрика», где не нужны ПД и качество терпит. Финальную формулировку лучше оставить Claude. Опционально, P2. |

Принцип: **числа считает Python в РФ, LLM только переводит в речь** → минимум зависимости от геоблока и нулевой риск утечки ПД (в модель уходят только обезличенные агрегаты).

## Риски и ловушки этого модуля (и обход на нашем стеке)

1. **🔴 Цифры BI разойдутся с дневным отчётом 21:00.** `_daily_report`/`business_summary` считают из live YClients, а data mart — из снапшота → владелец увидит «-18% тут, -15% там» и потеряет доверие. **Обход:** единый код-путь — `business_summary` после п.8 читает из mart; дневной отчёт берёт из того же источника; ETL запускать ПОСЛЕ закрытия дня; в UI показывать «данные на HH:MM».
2. **YClients задним числом меняет/удаляет/доплачивает записи.** Инкрементальный sync «только новое» пропустит правки. **Обход:** ETL пересобирает не только новые, но и скользящее окно последних 7–14 дней (upsert по PK), плюс полный реконсиляционный sync раз в неделю.
3. **«Истекла лицензия YClients»** (известная гоча из памяти) обрушит ETL. **Обход:** ETL устойчив к пустому ответу (как `business_summary` уже делает `except→[]`), пишет `bi_etl_state.last_synced_dt`, не затирает прошлые факты, алертит владельцу в GOD-режим «Здоровье».
4. **NL→SQL-инъекция / LLM выдумывает метрику.** **Обход:** Claude НЕ генерит SQL — выбирает из закрытого enum метрик/измерений `bi_semantic`; неизвестная метрика → отказ, не свободный запрос; всё параметризовано.
5. **Утечка ПД через BI.** Когорты соблазняют джойнить телефон/имя. **Обход:** в data mart только `client_hash` (HMAC), сырого телефона нет; `redact_pii` на выходе в LLM как второй контур; master видит только свои агрегаты без контактов.
6. **LLM галлюцинирует причину («выручка упала из-за погоды»).** **Обход:** причины считает `bi_explain` в Python из фактов; Claude получает готовую декомпозицию и инструкцию «объясняй только по этим факторам, не выдумывай» (паттерн уже в промпте: «вызывай инструмент, а не выдумывай», `claude_ai.py:1582`).
7. **SQLite-конкуренция:** ETL пишет, дашборды читают, бот работает — все в одной WAL-БД. **Обход:** WAL уже включён (читатели не блокируют писателя); ETL батчами короткими транзакциями; тяжёлые BI-чтения — по индексам (`ix_bi_fact_dt`), не full-scan.
8. **Прогноз на малых данных переобучится.** Один салон, сезонность шумная. **Обход:** на MVP — простой наивный прогноз (темп × дни + сезон-коэффициент по дню недели) с явным «±интервал, мало данных»; сложные модели (Holt-Winters) только на >6 мес истории.

# МОДУЛЬ 4. AI ДИРЕКТОР

> «Управляющий партнёр», который каждое утро сам смотрит на бизнес, формулирует **действенные** рекомендации с обоснованием и приоритетом, и даёт исполнить их в один тап. Наращивается поверх `_god_watch_job` (09:00) + `_daily_report_job` (21:00) + `analytics.business_pulse`.

**Готовность модуля как целого: ~35%.** Есть фундамент (аналитика с динамикой/аномалиями, два cron-канала с пушем владельцу, RBAC-гейт `get_business_report`, реестр данных в YClients). Нет: слоя превращения цифр в рекомендации, движка приоритизации, дедупа/тихих окон, «действий в один тап», таблиц состояния директора.

---

## 1. Цель

Превратить пассивную отчётность («вот цифры») в **проактивного управляющего партнёра**, который:
- ежеутрено сам диагностирует бизнес за вчера/неделю/месяц на сводках, которые мы уже умеем считать;
- генерирует **3–5 конкретных рекомендаций** с обоснованием на цифрах, ожидаемым эффектом и приоритетом — не «поднимайте качество сервиса», а «у услуги X маржа просела на 18% за 2 недели при росте загрузки — подними прайс на 100₽, потенциал +14 600₽/мес»;
- каждую рекомендацию сопровождает **кнопкой действия в один тап** (запустить реактивацию N клиентов, изменить цену услуги через YClients, отправить промо сегменту), уважая HITL/риск-тиринг, который уже есть;
- **не спамит**: дедуп повторяющихся советов, тихие окна, ограничение N/день, «отложить/не показывать».

Ключевая инженерная задача — **action-grounding рекомендаций**: Claude видит не только метрики, но и *перечень исполнимых действий с реальными ID* (service_id, staff_id, client-сегменты), поэтому совет физически привязан к кнопке, а не к воздуху.

---

## 2. Польза владельцу салона

- **Замена управляющего за ~0₽/мес сверх ИИ-токенов.** Один салон, владелец = практикующий мастер; у него нет времени на аналитику. Директор делает это за него в 09:00.
- **Деньги на столе становятся видимыми**: недозагруженные окна, услуги с просевшей маржой, отвалившиеся постоянники, мастера с падающим средним чеком — всё это уже лежит в YClients, но никто не смотрит.
- **Действие, а не отчёт**: «вернуть 7 уснувших клиентов» — кнопка, а не задача «когда-нибудь сделать». Снижает trust-разрыв «ИИ посоветовал — я забыл».
- **SaaS-аргумент №1**: при продаже другим салонам «AI-директор, который сам говорит, где ты теряешь деньги» — это headline фичи, а не «ещё один дашборд».

## 3. Польза мастерам

- **Справедливость и рост дохода**: рекомендации вида «у мастера Ильи средний чек ниже салонного на 22% — предложить ему скрипт допродажи укладки» повышают их заработок (% от выручки), а не штрафуют.
- **Прозрачные цели**: директор может формировать персональную мини-сводку мастеру («твоя загрузка вт-чт 40%, давай заполним» с кнопкой открыть лист ожидания) — переиспользуя `_MASTER_ONLY` инструменты.
- Защита: персональные сравнения мастеров видит **только владелец** (RBAC-гейт), мастеру уходит только его собственный позитивно-сформулированный срез.

## 4. Польза клиентам

- **Косвенная, но реальная**: реактивация уснувших — это «мы соскучились, вот −20%», а не спам (контур `reactivation.py` уже с лимитами и согласием).
- Рекомендация «продвигать услугу Z» часто = персональное релевантное предложение клиенту, которому эта услуга подходит (через `suggest_upsell`/привычки), а не веерная рассылка.
- Лучше заполненное расписание → меньше «нет окон на удобное время».

### Новые модули Python
1. **`director.py`** — ядро. Не новый LLM-loop, а **слой подготовки фактов + вызов Claude одним промптом + парсинг JSON**. Функции:
   - `collect_signals(date_ref)` — детерминированно собирает «сигналы» из `analytics` + новых аналитик (см. ниже). Без LLM. Возвращает структурированный `signals: list[dict]` (метрика, дельта, severity, привязанный action-template).
   - `build_recommendations(signals)` — формирует промпт, вызывает Claude (Haiku/Sonnet, см. п.7), получает строгий JSON рекомендаций, валидирует, привязывает к action-templates.
   - `dedup_and_throttle(recs)` — отсев по `director_recs` (см. таблицы): тот же `signal_key` не чаще раза в N дней; уважение «не показывать»; кап N активных карточек.
   - `morning_brief(app)` — оркестратор, который зовёт `_director_brief_job`.
2. **`director_actions.py`** — реестр **action-templates**: декларативная карта `action_type → {tool, required_role, risk_tier, param_schema, executor}`. Каждый шаблон знает, как исполнить себя (реактивация / смена цены услуги через YClients / запуск промо / открыть лист ожидания). Это то, что делает рекомендации исполнимыми в один тап и **не даёт Claude придумать несуществующее действие** — он выбирает только из enum зарегистрированных типов.
3. Расширение **`analytics.py`** (а не новый файл): добавить read-only функции для сигналов, которых пока нет:
   - `service_margin_trend(window)` — динамика выручки/частоты по услугам (есть `top_services`, нужна дельта период-к-периоду);
   - `master_avg_check_vs_salon(window)` — средний чек мастера против салонного;
   - `utilization(window)` — загрузка по дням/мастерам (свободные окна из графиков YClients vs занятые);
   - `churn_candidates(window)` — кандидаты на отвал (переиспользует логику `reactivation` `days_since`, но как аналитический сигнал, без рассылки).

### Новые таблицы SQLite (в `database.py`, паттерн как у `salon_rules`/`tool_audit`)
```
director_recs          -- сгенерированные рекомендации
  id, created_date, signal_key, kind, severity,
  title, rationale, expected_effect_rub, priority(P0/P1/P2),
  action_type, action_params(json), status(new/done/snoozed/dismissed),
  acted_at, result_json, dedup_hash
director_feedback      -- обучающий сигнал: что владелец реально делал
  id, rec_id, action(open/snooze/dismiss/execute), at
director_settings      -- тихие окна, частота, выключенные типы (или хранить в settings)
```
`director_recs.dedup_hash` = md5(signal_key + округлённое значение) — точно как анти-спам в `_god_watch_job`, только на уровне отдельной рекомендации.

### Эндпоинты aiohttp (в `webhook_server.py`, через `api-proxy.php`, RBAC owner/founder)
- `GET /api/director/brief?date=` — лента актуальных рекомендаций для GOD-UI.
- `POST /api/director/act` — `{rec_id, action: execute|snooze|dismiss}`; для `execute` идёт через тот же HITL/идемпотентность, что и денежные действия.
- `POST /api/director/run` (owner-only) — ручной триггер пересборки (кнопка «обновить» в кабинете).
Все — в ту же RBAC-группу прокси, что `panel_*`/`god_*` (role owner/founder), что уже отлажено.

### Потоки данных
```
09:00 cron  _director_brief_job
   → director.collect_signals()         [YClients read + analytics, без LLM]
   → director.build_recommendations()   [Claude через PROXY_URL, строгий JSON]
   → dedup_and_throttle()               [SQLite director_recs]
   → persist + _send_client_push + Telegram (брифинг + кнопки)
   → ai_billing.log(...)                [учёт токенов]

Тап владельца «Выполнить»
   → POST /api/director/act
   → director_actions.execute(action_type, params)
        → HITL gate (если денежное) → исполнитель (reactivation/YClients/...)
        → tool_audit + payment_idempotency
   → status=done, director_feedback
```

### Где живёт ИИ
Только в `build_recommendations`: **один не-стриминговый вызов Claude в сутки** (плюс ручные). Это НЕ tool-use loop — сбор данных детерминирован в Python, Claude получает готовые факты и возвращает приоритизированный JSON. Так дешевле, предсказуемее и обходит риск, что Claude «нагенерит» действия вне реестра.

## 7. Какие AI-модели

| Задача | Модель | Обоснование |
|---|---|---|
| **Генерация рекомендаций (основное)** | **Claude Haiku 4.5** через `PROXY_URL` | вход — структурированные факты, выход — строгий JSON 3–5 пунктов. Это классификация+ранжирование+формулировка, а не сложное рассуждение. Haiku хватает, в ~15–20× дешевле Sonnet, latency не критичен (фон 09:00). |
| **Сложный месячный «разбор полётов»** (раз в неделю/месяц, многофакторный) | **Claude Sonnet 4.5** через `PROXY_URL` | когда сигналов много и нужно увязать тренды (маржа↓ + загрузка↑ + отвал постоянников) в единую гипотезу. Дороже, но редко. |
| **Резервный путь при недоступности прокси** | **YandexGPT 5 / GigaChat** (РФ, без прокси) | деградация, а не отказ: если прокси упал, директор всё равно выдаёт рекомендации на РФ-LLM (качество формулировок ниже, цифры — те же, считает Python). 152-ФЗ-чисто, в РФ. Это страховка под уже описанный в проекте геоблок-риск. |

**Почему не нужны vision/STT/TTS:** Модуль 4 — текст и цифры. Биометрия/фото (152-ФЗ-блокер CutMatch) здесь не участвует. Голосовая озвучка брифинга — опция поверх готового `voice.py`, не критпуть.

**Промпт-инжиниринг для действенности (ядро ценности модуля):**
1. **Структурированный вход**: каждый сигнал = `{kind, metric, now, prev, delta_pct, anomaly, attached_action_type, action_params}`. Claude видит, что под сигналом есть исполнимое действие.
2. **Жёсткие правила в system-prompt**: «Запрещено: общие советы без числа. Каждая рекомендация ОБЯЗАНА содержать: конкретную метрику с дельтой, ожидаемый эффект в ₽ (оцени по данным), ровно один `action_type` из предложенного enum. Если действия в реестре нет — рекомендация запрещена.»
3. **Few-shot**: 2 примера хорошей (с числом+₽+action) и плохой (банальность) рекомендации.
4. **Приоритизация по формуле, не на вкус LLM**: severity считаем в Python (`|delta_pct| × деньги_на_кону`), Claude только формулирует и сортирует в рамках наших P0/P1/P2 порогов. Это убирает «галлюцинацию важности».
5. **Строгий JSON-выход** + валидация: невалидное/без action — выбрасываем перед показом.

## Риски и ловушки этого модуля (и как обойти на нашем стеке)

1. **Банальности вместо инсайтов** (главный риск). Обход: severity и ₽-эффект считает **Python по формуле**, Claude только формулирует; запрет в промпте на рекомендации без числа+₽+action; валидатор режет невалидное. Без action-grounding не показываем.
2. **Галлюцинация цифр/несуществующих действий.** Обход: Claude НЕ считает метрики (всё из `analytics`/YClients) и выбирает `action_type` только из enum реестра `director_actions`. Любой action с неизвестным типом отбрасывается до показа.
3. **Спам/усталость владельца.** Обход: дедуп по `dedup_hash`, кап активных карточек, «не показывать этот тип», тихие окна; `_god_watch_job` уже молчит, когда всё спокойно — сохраняем это поведение и для рекомендаций (нет сигналов P0/P1 — брифинг короткий или не шлём).
4. **152-ФЗ.** В промпт уходят только агрегаты и псевдо-ID клиентов; имена/телефоны — никогда; `anonymizer.redact_pii` на свободном тексте сигналов как страховка. Биометрия не участвует.
5. **Геоблок/прокси.** 09:00 — не пиковое время прокси; не-стриминговый одиночный вызов устойчив к лагам; резерв на YandexGPT при недоступности (деградация, не отказ).
6. **«Срабатывание действия дважды».** Денежные действия (смена цены, выплаты-промо) — через уже готовую `payment_idempotency` и HITL-подтверждение; идемпотентность по `rec_id`. Не изобретаем заново.
7. **Стоимость YClients-запросов в сборке сигналов.** `business_pulse` тянет транзакции+записи дважды (тек/пред период). Кэшировать сырьё на время сборки (одна загрузка → много сигналов), а не дёргать API на каждый сигнал.
8. **Расхождение «касса vs services».** Уже задокументировано в `analytics._top_from_records` (скидки). Для рекомендаций по марже опираться на транзакции (каноничная касса), `top_services` — только для частоты/паттернов.
9. **Фронт app.html — один файл.** Лента директора в GOD добавит заметный объём; делать отдельным экраном-роутом `?god=director`, не раздувая существующие плитки. Деплой — раздельно (бэк VPS / фронт Beget), как принято.

# МОДУЛЬ 5. AI МАРКЕТОЛОГ

> MAYA как штатный маркетолог салона: сама находит, кто уходит и почему, кого вернуть, что предложить, по какому каналу, и доказывает деньгами. Не «рассыльщик», а аналитик-стратег с детерминированным контуром согласий.

---

## 1. Цель

Превратить разрозненные точечные механики (реактивация уснувших, ДР-промокоды, рефералка, `first_source`, лист ожидания) в **единый замкнутый маркетинговый контур**:

**Сегментация → Гипотеза → Оффер (Claude) → Кампания (канал) → Доставка → Атрибуция → ROI → Обучение на результате.**

Ключевой сдвиг: сегодня проактивность «зашита» в отдельные cron-джобы с жёсткой логикой. Цель — дать MAYA **данные о клиентской базе как первоклассный объект** (RFM-снимки, отток, LTV) и **движок кампаний**, чтобы она формулировала и запускала маркетинг сама (под HITL-апрувом владельца), а не по хардкоду.

Конкретный измеримый результат: на дашборде владельца появляется «MAYA нашла: за 45 дней ушло 23 клиента сегмента „регуляры стрижка+борода“, потенциальный недозаработок ~78 000 ₽/год. Предлагаю кампанию: вернуть 23 → ожидаемо 9 (по прошлым реактивациям), стоимость 23 SMS = 138 ₽. [Запустить] [Изменить оффер] [Отклонить]».

---

## 2. Польза владельцу салона

- **Видит деньги, а не графики.** Не «retention упал», а «теряете ~78к/год, вот кого и за сколько вернуть».
- **Маркетинг без маркетолога.** Зарплата маркетолога в регионе 40–80к/мес — MAYA закрывает 80% рутины (сегменты, тексты, расписание, отчёт ROI) за ~стоимость токенов.
- **Контроль и безопасность.** Каждая массовая рассылка — через HITL-апрув (риск-тиринг уже есть). Защита от «спам всем» и от штрафа по ст.18 ФЗ «О рекламе» (контур согласий).
- **Атрибуция каналов.** `first_source` уже собирается → MAYA честно показывает, какой канал (Telegram/сайт/рефералка/Avito) приводит платящих, а не кликающих.
- **A/B без эксперта.** MAYA сама бьёт сегмент на 2 группы, сравнивает конверсию, на следующей кампании использует победивший оффер.

## 3. Польза мастерам

- **Загрузка окон.** Сегмент «клиенты конкретного мастера, не были 35+ дней» → точечная рассылка на ИМЕННО его окна (переиспользуем лист ожидания и графики YClients). Мастер не простаивает.
- **Свои клиенты возвращаются.** Привязка `staff_id` в сегменте: «верни МОИХ ушедших» — мастер видит в кабинете, кого MAYA вернула на его кресло.
- **Не дёргают руками.** Сейчас мастер сам пишет «давно не виделись» — MAYA делает это от имени салона с учётом тона (мужская эстетика, без приторности).

## 4. Польза клиентам

- **Релевантность, не спам.** RFM-сегмент → клиент получает оффер про услугу, которой реально пользуется (стрижка/борода/уход), а не «общую акцию».
- **Уважение к согласию.** Жёсткий opt-in/opt-out, частотный кап (не чаще 1 промо в N дней), тихие часы. Не достаём в 7 утра.
- **Реальная выгода.** Возврат уходящего = персональный промокод/слот у любимого мастера, а не «−5% всем».
- **Прозрачность.** В PWA — «Почему я это вижу» + кнопка «Не присылать акции» в один тап (это и есть техническая реализация ст.18 + 152-ФЗ).

## 5. Архитектура — как ложится на текущий стек

### Принцип: ИИ не трогает сырые ПД и не «решает в вакууме»
Детерминированный Python считает сегменты и метрики из YClients/локальной БД. Claude получает **обезличенные агрегаты** («сегмент A: 23 чел, ср.чек 1500, давность 45д, услуга „стрижка+борода“») и генерит **гипотезу + текст оффера + расписание**. ПД (телефон/имя) подставляются движком доставки на лету, **после** генерации, минуя LLM. Это прямое продолжение контура `redact_pii`.

```sql
  offer_text, offer_meta_json,-- сгенерённый Claude текст + промокод/слот
  ab_variant,                 -- null | 'A' | 'B'
  scheduled_at, approved_by, approved_at,
  cost_estimate_kop, cost_actual_kop
)

campaign_recipient(
  id, campaign_id, client_phone_hash, variant,
  consent_ok,                 -- снимок проверки согласия на момент отправки
  delivery_status,            -- queued/sent/delivered/failed/skipped_consent/skipped_freqcap
  sent_at, provider_msg_id
)

-- Атрибуция: связь промокод/utm → запись YClients
campaign_conversion(
  id, campaign_id, client_phone_hash,
  record_id, revenue_kop, converted_at, attribution_type  -- promo/utm/window
)

-- Контур согласий (юридический артефакт)
marketing_consent(
  client_phone_hash, channel,
  status,                     -- granted/revoked
  source,                     -- 'pwa_checkbox'/'bot_optin'/'verbal_owner'
  evidence_json,              -- что именно нажал/сказал + ts + ip (для PWA)
  updated_at
)

-- Частотный кап
marketing_contact_log(client_phone_hash, channel, sent_at, campaign_id)
```

> `client_phone_hash` = HMAC(phone, локальный secret). Маркетинговые таблицы джойнятся по хэшу; реальный телефон достаётся `delivery.py` из YClients/локального кэша только в момент отправки и НЕ логируется в тело. Снижает поверхность 152-ФЗ.

### Потоки данных

**A. Ночной скан (детерминированный + ИИ-резюме):**
```
cron _marketing_scan_job
 → segments.py: pull визитов из YClients → RFM/churn → segment_snapshot
 → segments.py: diff со вчерашним снимком → «событие»: «−23 из at_risk за 45д»
 → offers.py → Claude: агрегаты (без ПД) → гипотеза+оффер+оценка ROI
 → campaign(draft) + дайджест владельцу (Telegram + карточка в «Рост»)
```

**B. Апрув и запуск (HITL):**
```
owner [Запустить] → /api/marketing/approve
 → риск-тир: массовая платная рассылка = всегда HITL (контур уже есть)
 → campaigns.py: материализует recipient-лист из segment_snapshot
 → consent.py фильтр + freq-cap фильтр + тихие часы
 → delivery.py по каналу, идемпотентно (паттерн payment_idempotency)
```

**C. Атрибуция (онлайн + ночью):**
```
YClients webhook на создание записи → attribution.py
 промокод/UTM матч на campaign → campaign_conversion + revenue
 ROI = (Σ revenue − cost_actual) / cost_actual
```

## 9. Приоритет

**P1** (после голоса P0 и базовой аналитики, но раньше «директорских» модулей).

Почему P1, а не P0:
- Голос (Модуль голос, 80% готов) и операционная автономия дают вау-эффект и удержание раньше.
- Маркетинг **окупается напрямую деньгами** (возврат клиентов) → сильнейший аргумент для SaaS-продажи салонам, второй по бизнес-приоритету после стабильности ядра.

Почему не P2:
- У салона главная боль — отток и пустые окна. Это **прямой revenue-driver** и киллер-фича для тарифа Pro/Max в SaaS-плане (`plan_catalog.py`). Конкуренты (YClients-надстройки) этого AI-уровня не дают.

**Внутри модуля:** P0 — `consent.py` (без согласий рассылать НЕЛЬЗЯ юридически), затем сегменты+движок (MVP), потом A/B+ROI.

## Риски и ловушки (под наш стек)

1. **🔴 Юр-риск ст.18 ФЗ «О рекламе» + 152-ФЗ.** Рассылка без согласия = штраф (до 500к юрлицу) + жалоба оператору. **Обход:** `consent.py` как hard gate ПЕРЕД каждой отправкой; существующие клиенты по умолчанию НЕ `granted`; явный рекламный чекбокс отдельно от оферты; хранить evidence (что нажал + ts + ip).
2. **🔴 YClients rate-limit / «истекла лицензия».** Полный пул базы ночью может упереться в лимиты (известная гоча из памяти). **Обход:** инкрементальный пул (только изменения с прошлого снимка), бэкофф, кэш в `segment_snapshot`, никогда не дёргать YClients в рантайме отправки.
3. **🔴 Идемпотентность массовой отправки.** Падение/рестарт `barbershop-bot` посреди рассылки → двойные SMS (это деньги и раздражение). **Обход:** статус на каждого `campaign_recipient` + паттерн `payment_idempotency`; повторный запуск шлёт только `queued`.
4. **⚠️ ПД утекают в LLM через текст оффера.** Claude может сгенерить «Иван, вернитесь». **Обход:** ИИ генерит ШАБЛОН с плейсхолдером `{name}`, подстановка — в `delivery.py` после LLM; валидатор `offers.py` режет любые имена/телефоны в теле от ИИ.
5. **⚠️ Атрибуция-самообман.** Клиент и так бы пришёл → кампания припишет себе чужую выручку. **Обход:** контрольная группа (holdout 10% сегмента не получают рассылку) → честный uplift, а не валовая выручка. Показывать владельцу именно uplift.
6. **⚠️ Churn-порог «один на всех» врёт.** У клиента раз в 2 недели и у клиента раз в квартал — разный «уход». **Обход:** churn относительно ЛИЧНОГО среднего интервала клиента, не глобального порога.
7. **⚠️ Частотный кап и тихие часы.** Несколько кампаний наложатся → клиент получит 3 SMS за день. **Обход:** `marketing_contact_log` + глобальный кап на клиента (не канал), тихие часы зашиты в `campaigns.py`.
8. **⚠️ SQLite WAL под нагрузкой рассылки.** Массовые апдейты статусов + параллельный прод. **Обход:** батч-апдейты в транзакции, отправка чанками, single-writer (бот и так один процесс); тяжёлый скан — ночью.
9. **⚠️ Прокси-флап в момент генерации офферов.** **Обход:** фолбэк `MARKETING_LLM=yandex` (РФ), плюс офферы можно готовить заранее ночью, а не в момент апрува.
10. **⚠️ Telegram как канал: достучимся не до всех.** Только до тех, кто стартовал бота/в PWA. **Обход:** приоритет каналов на клиента (push > telegram > sms по стоимости), SMS как платный фолбэк для остальных.

# МОДУЛЬ 6. AI КОНСУЛЬТАНТ ПО ФОТО

> Грануляция под реальный стек MAYA. Что есть в коде сейчас: `cutmatch.py` (31 КБ, рабочий движок analyze_face + примерка), таблицы `stylist_consents` и `cutmatch_usage` в `database.py`, проброс `try_haircut`/`haircut_status`/`analyze_face` в `api-proxy.php`, 28 упоминаний UI в `app.html`. Маршруты в `webhook_server.py` отключены, но код жив. **Текущая реализация НЕЗАКОННА**: фото лица (биометрия) уходит в OpenAI gpt-5.1 + Claude-фолбэк + fal.ai — все за пределами РФ. Это прямое нарушение 152-ФЗ (ст. 12 — трансгран в страну без адекватной защиты + биометрия требует письменного согласия и локализации). Задача модуля — пересобрать на **законную** архитектуру.

---

## 1. Цель

Клиент в PWA/боте загружает 1–3 фото (анфас + профиль) → MAYA анализирует **геометрию лица** (овал/квадрат/круг/треугольник/удлинённое), тип и текстуру волос, густоту/залысины, направление роста, форму/плотность бороды → выдаёт **2–4 персональные рекомендации стрижки и формы бороды** с RU-названиями, кратким «почему тебе» и **визуальной примеркой** (image-edit на референсном кадре клиента). Всё — в правовом контуре 152-ФЗ: биометрия **не покидает РФ** (либо РФ-vision, либо on-device), с явным письменным согласием на обработку биометрических ПД, контролируемым хранением и удалением.

Это не «игрушка», а **верхняя воронка**: фото-консультация → конкретная стрижка → кнопка «Записаться к мастеру, который это делает» → запись в YClients.

---

## 2. Польза владельцу салона

- **Конверсия холодного трафика.** Фото-консультация — лёгкий первый контакт для тех, кто стесняется «прийти наугад». Воронка `фото → рекомендация → запись` пристёгивается к уже готовому `book_record`.
- **Средний чек ↑.** Рекомендация бороды/ухода рядом со стрижкой = апсейл комплексных услуг (у вас уже есть план `complex` в `subscriptions.py`).
- **Дифференциация для SaaS.** «AI-стилист по фото в законном 152-ФЗ-контуре» — редкая фича: конкуренты либо не делают, либо нарушают закон. Сильный аргумент продающего сайта (`saas-site.html`).
- **Данные о спросе.** Агрегированная (обезличенная) статистика «какие стрижки чаще рекомендуются/выбираются» → в `get_business_report` для планирования обучения мастеров и закупки косметики.
- **Снижение юридического риска.** Текущий CutMatch — мина (биометрия за границу). Легализация снимает риск штрафа/блокировки и репутационного удара.

---

## 3. Польза мастерам

- **Готовый бриф до кресла.** Клиент приходит с понятной рекомендацией и примеркой — мастер не тратит 10 минут на «а что вам идёт». Рекомендация и фото-примерка прокидываются в карточку записи (через `append_record_comment`, как настроение визита `vmood_`).
- **Меньше «сделайте как на картинке из инстаграма» с нереалистичными ожиданиями** — MAYA фильтрует по реальной геометрии лица и густоте, не обещает невозможного.
- **Связка с базой знаний.** Рекомендация ссылается на `barber_knowledge` (Модуль 7) — мастер видит технику исполнения предложенной стрижки.
- **Защита от споров.** Примерка задаёт реалистичное ожидание результата → меньше конфликтов «я хотел не так».

---

## 4. Польза клиентам

- **Снимает барьер выбора.** Большинство мужчин не знают терминов и боятся экспериментов. «Покажи фото — получи 3 варианта что тебе пойдёт» — низкий порог.
- **Приватность как фича.** Честное «твоё фото не уходит за границу, обрабатывается в России / прямо в твоём телефоне, можешь удалить в один тап» — доверие, особенно на фоне общей тревоги об утечках.
- **Примерка до стрижки.** Видишь себя с предложенной стрижкой/бородой — решаешься осознанно.
- **Бесшовный переход к записи.** Понравилось → «Записаться» → выбор слота → готово, в том же экране PWA.

## 5. Архитектура — как ложится на стек

### Базовый принцип разделения (это и есть решение 152-ФЗ)

Два независимых конвейера с разным правовым весом:

1. **АНАЛИЗ ЛИЦА (биометрия, тяжёлый правовой режим)** — здесь нельзя зарубеж. Варианты движка в п.7.
2. **ПРИМЕРКА (image-edit)** — генерация нового изображения по фото = тоже обработка биометрии. Тот же контур. Разносим, потому что у них разная стоимость, латентность и движки.

### Переиспользуем (НЕ строим заново)

| Готовое | Как используем |
|---|---|
| `cutmatch.py` | Каркас сохраняем: `_JOBS` стор, submit/poll-контракт, `_BARBER_SYSTEM` промпт, каталог `_CATALOG_RU`, лимит. **Рвём только провайдеров** (OpenAI/Claude/fal → РФ-движок). Переименуем в `photo_consult.py`, оставив shim `cutmatch.py`. |
| `stylist_consents` (таблица) | Уже есть! Доработать до **биометрического** согласия (текст + версия `v2.0-biometric`). |
| `cutmatch_usage` | Лимит N/день готов. |
| `two-stage-ai-preview` (скилл) | submit→poll, превью→HD — точно ляжет на РФ-примерку. |
| `consent_gate_status` / `save_consent` | Паттерн гейта согласия, расширяем на биометрию. |
| `ai_billing.py` / `log_ai_usage` | Учёт расхода — добавить feature=`photo_consult`. |
| `append_record_comment`, `_notify_client_record` | Прокидывание рекомендации в карточку записи + пуш. |
| `api-proxy.php` cases `analyze_face`/`try_haircut`/`haircut_status` | Контракт фронта оставляем, меняем бэкенд за ним. |
| RBAC / `tool_audit` / HITL | Инструмент `recommend_haircut` регистрируем в `ROLE_TOOLS` (client-доступный, low-risk). |

### Новые / изменённые модули Python

- **`photo_consult.py`** (рефактор `cutmatch.py`): драйвер-абстракция `VisionDriver` с реализациями `GigaChatVisionDriver`, `YandexVisionDriver`, `OnDeviceDriver` (последний — no-op на бэке, анализ во фронте), выбор по `config.PHOTO_CONSULT_ENGINE`. `EditDriver` для примерки (`KandinskyDriver`/`YandexARTDriver`).
- **`database.py`**: новые таблицы (ниже) + функции `biometric_consent_*`, `photo_consult_save_session`, `photo_consult_delete_session`, `photo_consult_purge_expired`.
- **`webhook_server.py`**: вернуть маршруты, обернуть в `has_biometric_consent` гейт, добавить `/api/photo/consent`, `/api/photo/delete`.
- **`claude_ai.py`**: новый инструмент `recommend_haircut` (см. п.6) + `get_my_photo_consult` (последняя рекомендация в контекст диалога).
- **`bot.py`**: cron `_photo_purge_job` (ежедневно — удаление просроченных биометрических данных по сроку согласия).

### Таблицы SQLite

```sql

CREATE TABLE IF NOT EXISTS photo_tryon_jobs (   -- примерки (как _JOBS, но персистентно)
```

Ключевое для 152-ФЗ: **по умолчанию исходное фото не хранится** (on-device-режим) или хранится **зашифрованным** (`pii_crypto.py` уже есть в проекте!) с жёстким TTL и физическим удалением по cron. В БД лежит только **обезличенный** результат анализа (тип лица, рекомендации) — это уже не биометрия.

### Потоки данных (on-device-вариант — рекомендуемый MVP)

```
PWA: камера → <canvas> ресайз/кроп лица → MediaPipe FaceMesh (WASM, в браузере)
   → извлекает ГЕОМЕТРИЮ (пропорции лица, тип) ЛОКАЛЬНО, фото НЕ уходит
   → POST /api/photo/recommend { face_type, ratios, hair_hint, beard_hint }  ← это НЕ биометрия
api-proxy.php → webhook_server → photo_consult.recommend()
   → Claude/GigaChat (ТЕКСТ, не фото!) подбирает стрижки по геометрии + barber_knowledge
   → возвращает рекомендации
[опц.] примерка: фото остаётся on-device, edit-модель в РФ или клиент сам грузит ТОЛЬКО для примерки с отдельным согласием
```

В on-device-варианте **в зарубежную LLM уходит только текст** («лицо квадратное, соотношение X, волосы прямые густые») — биометрии нет, можно использовать Claude через прокси для качественного styling-резонинга. Это юридически самый чистый и при этом качественный путь.

## 6. Какие API

### Внешние (с учётом геоблока)

| Назначение | Сервис | Геоблок | Примечание |
|---|---|---|---|
| Геометрия лица on-device | **MediaPipe Face Mesh / Tasks Vision** (WASM, Google) | н/п — статика, грузится один раз, инференс локально | Фото не уходит. CDN можно self-host на Beget. |
| РФ-vision (если не on-device) | **GigaChat MAX (vision)** | в РФ, **без прокси** | Early access vision, мультимодал. ПД в РФ — законно. |
| РФ-vision альтернатива | **Yandex AI Studio** (мультимодальные модели) | в РФ, без прокси | Отдельно `Yandex Vision` = детекция, не styling. |
| Styling-резонинг по тексту | **Claude Haiku/Sonnet** через `PROXY_URL` | через прокси | Только если on-device — уходит ТЕКСТ, не фото. |
| Примерка (image-edit) | **Kandinsky (Sber, FusionBrain API)** или **YandexART** | в РФ, без прокси | РФ-генерация, биометрия не уходит. Качество ниже gpt-image, но законно. |

### Наши новые эндпоинты aiohttp (в `webhook_server.py`)

- `POST /api/photo/consent` — подписать биометрическое согласие (→ `stylist_consents` v2.0). Гейт перед всем модулем.
- `POST /api/photo/recommend` — on-device: принимает геометрию (не фото) → рекомендации. РФ-vision-режим: принимает фото → РФ-движок.
- `POST /api/photo/tryon` — submit примерки → `job_id` (контракт как `try_haircut`).
- `GET /api/photo/tryon-status` — поллинг (как `haircut_status`).
- `POST /api/photo/delete` — удалить мои биометрические данные (право на удаление, 152-ФЗ).
- `GET /api/photo/last` — последняя рекомендация (для прокидывания в чат/карточку).

### Новые инструменты Claude (`claude_ai.py`, в `ROLE_TOOLS`)

- `recommend_haircut(face_type, hair_type, density, beard, occasion?)` → 2–4 стрижки + борода, с привязкой к `barber_knowledge`. **client-доступный, low-risk.** Вызывается и из фото-флоу, и просто из диалога («что мне пойдёт?»).
- `get_my_photo_consult()` → последняя рекомендация клиента в контекст (привычки/история).

## 7. Какие AI-модели — обоснование под геоблок/152-ФЗ

**Три законных варианта движка анализа** (рекомендация в конце):

### Вариант A — On-device геометрия + Claude по тексту (РЕКОМЕНДУЮ для MVP)
- **Геометрия:** MediaPipe FaceMesh (WASM) в браузере. Фото **не покидает устройство** → формально это даже не «обработка биометрии оператором» в части передачи.
- **Резонинг:** Claude Haiku 4.5 через `PROXY_URL` — получает **только текст** (тип лица, пропорции, тип волос). Качество styling-советов высокое, стоимость копеечная.
- **Законность:** максимальная. Биометрия не уходит ни в РФ-облако, ни за границу.
- **Качество:** анализ геометрии — отличный (FaceMesh точный); «густота/направление роста/борода» по фото on-device слабее (нужна доп. ML-модель в WASM или клиент отвечает на 2 вопроса кнопками).
- **Цена:** разработка фронта выше; операционка ~0 (Claude по тексту ≈ $0.001/консультация).

### Вариант B — GigaChat MAX vision (РФ-облако)
- **Анализ:** фото → GigaChat MAX (vision) в РФ, без прокси. Полный анализ (геометрия + волосы + борода) одним вызовом.
- **Законность:** законно при наличии биометрического согласия + хранение/обработка в РФ (GigaChat — Сбер, РФ-резидентность). Это и есть «трансгран нет».
- **Качество:** styling-домен у GigaChat слабее OpenAI, но для «подобрать из 12 пресетов» достаточно. Vision в early access — риск нестабильности API.
- **Цена:** операционка по токенам GigaChat (рубли, дёшево); разработка средняя.

### Вариант C — Self-hosted vision на РФ-GPU
- Open-weight VLM (напр. Qwen-VL класса) на арендованном РФ-GPU (Selectel/VK Cloud).
- **Законность:** полная, всё в РФ, контроль над данными.
- **Минусы:** дорого (GPU ~$150–400/мес), DevOps-нагрузка, для одного салона нерентабельно. Имеет смысл только на масштабе SaaS (десятки тенантов).

**Примерка (отдельно):** Kandinsky (FusionBrain, Сбер) или YandexART — оба в РФ. Качество edit ниже gpt-image-2, но это единственный законный путь. Для MVP примерку можно **отложить** (P2) и запускать только текстовые рекомендации + статичные референсы стрижек из каталога.

**Рекомендация CTO:** **Вариант A для MVP** (максимальная законность, низкая операционка, не зависим от early-access GigaChat-vision), с **Вариантом B как опциональным «глубоким анализом»** под явное доп-согласие для тех, кому мало геометрии. На масштабе SaaS — мигрировать тяжёлый анализ на C. Примерку — отдельной фазой на Kandinsky.

## Риски и ловушки этого модуля

1. 🔴 **«Полу-удалён» = всё ещё опасен.** Главная ловушка: код CutMatch жив (`cutmatch.py`, проброс в `api-proxy.php`, UI в `app.html`). Любая реактивация = утечка биометрии в OpenAI. **Обход:** Фаза 0 до всего; жёсткий гейт `has_biometric_consent` на уровне `api-proxy.php` И `webhook_server.py` (defense in depth), CI/grep-проверка что ни один путь с фото не идёт на зарубежный хост.
2. ⚠️ **On-device ≠ автоматически законно, если фото потом всё же ушло.** Если примерка отправит фото в зарубеж — весь правовой выигрос Варианта A теряется. **Обход:** примерка только на РФ-движках (Kandinsky/YandexART), и она вообще опциональна.
3. ⚠️ **GigaChat vision — early access.** API нестабилен, формат ответа может меняться, styling-домен слабый. **Обход:** держать за флагом, основной путь — Вариант A; парсинг ответа толерантный (как сейчас `_analyze` с фолбэком).
4. ⚠️ **Согласие на биометрию строже обычного ПД** (152-ФЗ ст. 11 — отдельное письменное согласие, конкретная цель, срок). Галочки «я согласен» в общем потоке недостаточно. **Обход:** отдельный экран, отдельная версия согласия `v2.0-biometric`, лог в `stylist_consents`, право отзыва/удаления реализовано кодом (`/api/photo/delete` + cron-purge).
5. ⚠️ **Хранение фото = ответственность.** Даже зашифрованное фото на VPS — это хранение биометрии. **Обход:** по умолчанию **не хранить** исходник (on-device), в БД только обезличенный результат; если храним (опция B) — `pii_crypto` + жёсткий TTL + физическое удаление + аудит `deleted_at`.
6. ⚠️ **iOS-PWA камера/`getUserMedia`** капризна в standalone; WASM FaceMesh тяжёлый на старых устройствах. **Обход:** фолбэк на загрузку фото из галереи; ленивая загрузка WASM; деградация на «ответь на 3 вопроса кнопками» если FaceMesh не стартовал. (Учесть гочу: `window.prompt` мёртв в iOS-PWA — только кастомные модалки.)
7. ⚠️ **Завышенные ожидания от примерки.** РФ-генерация (Kandinsky) даёт менее «фотореалистичный» результат, чем gpt-image — клиент может разочароваться. **Обход:** позиционировать как «эскиз/набросок», не «фото результата»; качество ставить medium; примерка — P2, не блокер MVP.

# МОДУЛЬ 7. AI-ТРЕНЕР ДЛЯ МАСТЕРОВ
*(на базе `barber_knowledge.py` / `barber_knowledge.md`, инструмента `barber_knowledge`, аналитики `get_business_report` и роли MAYA-«наставник»)*

## 1. Цель

Превратить разовый retrieval-справочник `barber_knowledge` в **замкнутый цикл развития мастера**: «знание → проверка усвоения → измеренный навык → персональный план → KPI». MAYA из «отвечает на вопрос по технике» становится **наставником с памятью о каждом мастере**: знает, что мастер уже сдал, где плавает по выручке/услугам, и адресно подтягивает слабое.

Конкретно достраиваем 5 петель поверх готового:
1. **База знаний 2.0** — структурированная (не плоский md), версионируемая владельцем через чат, с метаданными для генерации тестов.
2. **Генерация тестов/экзаменов** из базы (Claude, owner-curated, не «на лету клиенту»).
3. **Прогресс** — таблицы `kb_articles`, `kb_quiz_attempts`, `master_skills`, `master_dev_plan`.
4. **Привязка к KPI** — связка с `get_business_report` по мастеру: слабая услуга по деньгам/частоте → авто-предложение модуля обучения.
5. **Интерфейс мастера в PWA** — вкладка «Обучение» (карточки знаний / тест / мой план / прогресс) + голосовой тренажёр через готовый realtime-мост.

> % готовности модуля сейчас: **~15%**. Готов retrieval-движок (`barber_knowledge.py`), черновик контента (10 секций), инструмент в loop, роль «наставник» в промпте, RBAC (`master`), `tool_audit`, биллинг ИИ. Нет: структуры/метаданных, тестов, прогресса, KPI-связки, UI.

## 2. Польза владельцу салона

- **Стандартизация качества** — «как стрижём фейд» перестаёт быть в голове Стаса/Ильи и зашивается в базу + проверяется экзаменом. Новый мастер выходит на стандарт салона за дни, а не за сезон.
- **Управляемый онбординг** — план развития для новичка собирается автоматически; владелец видит «сдал/не сдал» вместо «вроде учил».
- **Деньги, а не вайб**: KPI-связка показывает «Артём почти не делает оформление бороды и его средний чек ниже» → система сама предлагает Артёму модуль «борода» и upsell-скрипты. Обучение привязано к выручке.
- **Удержание мастеров** — рост и аттестация = причина остаться (барберы текучи). Это аргумент и для SaaS-продажи салонам.
- **Актив для франшизы/SaaS**: курируемая база + экзамены — то, что нельзя скопировать у конкурента, и killer-фича тарифа PRO/MAX в `plan_catalog.py`.

## 3. Польза мастерам

- Ответ по технике **фактами из базы салона**, а не галлюцинация LLM (это уже принцип `barber_knowledge.py`).
- **Голосовой тренажёр в зале**: между клиентами спросил голосом «как блендить висок под 0.5» — MAYA ответила из базы (готовый realtime-мост + Haiku).
- **Понятный путь роста**: «сдай экзамен по бороде → разблокируется надбавка/процент» (геймификация под решение владельца).
- Видит **свой прогресс и слабые места** без неприятного разговора с боссом — приватно, в PWA.

## 4. Польза клиентам

- Косвенная, но реальная: ровнее качество между мастерами и сменами; меньше «у Ильи фейд огонь, у новенького дырки». Связка с `visit_mood` и оценками визита → обучение бьёт точно в то, что клиенты ругают.

## 5. Архитектура — как ложится на стек

### Принцип: владелец курирует → Claude генерит черновики → владелец одобряет → мастер потребляет
Никакой генерации экзамена «на лету» в проде на каждый запрос (дорого через прокси + недетерминированно + риск галлюцинации в аттестации). Тесты генерятся **офлайн при правке статьи**, кешируются в БД, владелец ревьюит.

### Таблицы SQLite (WAL — импорт по паттерну из памяти: backup+integrity+dry-run)
```sql
CREATE TABLE IF NOT EXISTS kb_articles (
  id INTEGER PRIMARY KEY, slug TEXT UNIQUE, title TEXT, body TEXT,
  tags TEXT,                       -- csv: fade,beard,...
  service_ids TEXT,                -- csv YClients service_id, для KPI-связки
  difficulty INTEGER DEFAULT 1,    -- 1..3
  version INTEGER DEFAULT 1, updated_by INTEGER, updated_at TEXT,
  status TEXT DEFAULT 'draft');    -- draft|published
CREATE TABLE IF NOT EXISTS kb_quizzes (   -- сгенерённый и одобренный тест к статье
  id INTEGER PRIMARY KEY, article_id INTEGER, kb_version INTEGER,
  questions_json TEXT,             -- [{q, options[], correct_idx, explain}]
  status TEXT DEFAULT 'draft', created_at TEXT);
CREATE TABLE IF NOT EXISTS kb_quiz_attempts (
  id INTEGER PRIMARY KEY, master_staff_id INTEGER, quiz_id INTEGER,
  answers_json TEXT, score REAL, passed INTEGER, is_exam INTEGER DEFAULT 0,
  created_at TEXT);
CREATE TABLE IF NOT EXISTS master_skills (   -- агрегированный навык по теме/услуге
  master_staff_id INTEGER, skill_key TEXT,   -- 'fade' | service_id
  kb_score REAL, kpi_score REAL, level INTEGER,  -- 0..5
  updated_at TEXT, PRIMARY KEY(master_staff_id, skill_key));
CREATE TABLE IF NOT EXISTS master_dev_plan (
  id INTEGER PRIMARY KEY, master_staff_id INTEGER, skill_key TEXT,
  reason TEXT,                     -- 'low_revenue' | 'failed_exam' | 'owner'
  article_id INTEGER, status TEXT DEFAULT 'open',  -- open|done|skipped
  created_at TEXT, done_at TEXT);
```
`master_staff_id` = YClients staff_id (уже линкуется через `masters_telegram` и RBAC-резолвер) — единый ключ, чтобы биться с аналитикой по мастеру.

### Потоки данных
- **Курирование:** владелец в чате «обнови статью про фейд: …» → инструмент `kb_upsert_article` (owner-only, по аналогии с `remember_business_rule`) → запись в `kb_articles` (status=draft) → инструмент `kb_generate_quiz` зовёт Claude → `kb_quizzes` draft → владелец «опубликуй» → status=published.
- **Обучение мастера:** PWA «Обучение» → `/api/trainer/feed` отдаёт статьи + рекомендованные из `master_dev_plan`. Запрос «объясни» → инструмент `barber_knowledge` (как сейчас). Тест → `/api/trainer/quiz/{id}` → ответы POST → `trainer.py` скорит детерминированно (correct_idx, **Claude не судит** — дёшево, честно, оффлайн-устойчиво) → `kb_quiz_attempts` + пересчёт `master_skills`.
- **KPI-связка (nudge):** `_trainer_nudge_job` → `get_business_report(top_services, by master)` → услуги, где у мастера доля/чек ниже салонной медианы → ищет `kb_articles` с этим `service_id` → создаёт `master_dev_plan(reason='low_revenue')` → пуш.

`barber_knowledge.py` retrieve · `get_business_report` (KPI) · RBAC `ROLE_TOOLS`/`_authorize`/`tool_audit` · биллинг `ai_billing.py` · паттерн owner-памяти (`remember_business_rule`→`salon_rules`) · realtime-мост (голосовой тренажёр) · `telegram-pwa-push` (нуджи) · `client_preferences`/журнал как образец таблиц · SSE-стриминг чата для объяснений.

### Где живёт ИИ
Только в 2 точках, обе оффлайн/редкие: **генерация теста** (Claude Sonnet, при правке статьи) и **объяснение/тренажёр** (Haiku, на запрос мастера). Скоринг, прогресс, план — **детерминированный Python**, без LLM.

## 11. Риски и ловушки (и обход на нашем стеке)

1. **RAG vs prompt-stuffing.** База мала (10 секций, 94 строки) → **сейчас prompt-stuffing/keyword retrieve правильнее**: эмбеддинги в РФ = или зарубеж через прокси (latency, оверкилл), или Yandex/GigaChat-эмбеддинги. **Не вводить RAG до ~50+ статей.** Порог-триггер прямо в коде (`barber_knowledge.py` уже это предупреждает в docstring). Когда вырастет — Yandex SpeechKit-соседний `Yandex Foundation Models embeddings` (РФ, без прокси, ПД нет) → хранить вектора в той же SQLite (blob) + косинус в Python, без отдельной векторной БД.
2. **Галлюцинация в тесте = подрыв доверия к аттестации.** Обход: Claude генерит **только из текста статьи** (prompt-caching статьи + инструкция «вопросы строго по тексту, не добавляй фактов»), и **владелец обязательно ревьюит draft** до publish. Скоринг детерминированный — модель не «судит» ответ.
3. **Кириллица/морфология retrieve.** Текущий стемминг — обрезка до 5 символов; на узких терминах даёт ложные совпадения. Для MVP ок; при росте — словарь синонимов в статье (поле `tags`) важнее эмбеддингов.
4. **Геоблок при генерации.** Генерация — единственная LLM-точка через прокси; делать её **оффлайн (фон, submit→poll-паттерн `two-stage-ai-preview`)**, не в синхронном запросе владельца, чтобы флап прокси не ломал UX.

# МОДУЛЬ 8. AI ПРОГНОЗИРОВАНИЕ

> Контекст из ревизии кода: аналитика (`analytics.py`) — **read-only поверх YClients** (`get_company_records` + `get_company_transactions`), считается на лету per-request, **локального исторического хранилища метрик НЕТ**. Есть KV-хранилище `settings` (`get_setting`/`set_setting`), APScheduler (`Europe/Moscow`) в `bot.py`, дайджесты владельцу через `_god_watch_job` (09:00) и `_daily_report_job` (21:00), декларативные инструменты Claude в `claude_ai.py` с гейтом `_OWNER_ONLY`. Один салон, `COMPANY_ID=503759`, ~2-3 года истории в YClients. Это база, на которую модуль ложится почти бесшовно — но **главный пробел — отсутствие накопителя временных рядов**, и именно с него начинается работа.

---

## 1. Цель

Дать MAYA способность **смотреть вперёд, а не только назад**. Сейчас вся аналитика (`business_pulse`) реактивна: «прошлая неделя против позапрошлой». Модуль 8 добавляет проактивный слой: MAYA **заранее** (за дни-недели) предупреждает владельца о:

- **падении загрузки / выручки** (тренд вниз, пустеющая запись на ближайшие 7-14 дней);
- **перегрузке мастеров** (booking density выше комфортного порога → риск выгорания/качества);
- **оттоке клиентов** (клиент вышел за свой персональный межвизитный цикл × 1.5 → «уходит»);
- **сезонных провалах/пиках** (предновогодний бум, январский/майский спад);
- **прогнозе выручки** на конец недели/месяца с доверительным интервалом.

Честная рамка: на данных **одного салона** это **не «ML-предсказание»**, а **статистика малых данных + reasoning Claude над агрегатами**. Промышленный ML (градиентный бустинг на признаках) экономически и статистически оправдан только при мультитенанте (десятки салонов) — это явно отложено в P2/SaaS.

---

## 2. Польза владельцу салона

- **Раннее предупреждение о провале выручки**: «На след. неделю заполнено 38% слотов против обычных 70% к этому дню — вероятен спад ~30%. Запустить акцию?» MAYA сама предлагает действие (промокод спящим, контент в SMM).
- **Прогноз кассы к концу месяца** с интервалом: «Идём на ~520-560k, против 610k в мае. Отставание из-за провала вторников».
- **Сезонное планирование**: за 2-3 недели до прогнозного пика — «через 3 недели Новый год, в прошлом году +40% к декабрю, добери смены/расходники».
- **Защита от оттока ядра**: список «клиенты на грани ухода» с потенциалом выручки → точечная реактивация (переиспользует существующий `reactivation.py`).
- Всё это **встроено в уже существующий GOD-режим** и утренний дайджест — никакого нового места входа учить не надо.

## 3. Польза мастерам

- **Прогноз личной загрузки и ЗП**: «На следующей неделе у тебя забронировано 18 визитов ≈ 22k к выплате — на 15% ниже обычного, есть 6 пустых слотов в чт-пт». Мастер сам зовёт клиентов / постит.
- **Предупреждение о перегрузе**: «3 дня подряд по 11+ визитов — риск качества, MAYA может притормозить онлайн-запись или предложить перенос». Защищает от выгорания.
- **Заблаговременный список «пора напомнить»**: клиенты мастера, у кого подходит персональный цикл (стыкуется с `cycle_reminder.py`).

## 4. Польза клиентам (косвенная, но реальная)

- Прогноз перегруза → **меньше «нет мест»** и спешки в кресле (качество стрижки).
- Прогноз провала → акции/скидки именно тогда, когда салон в них заинтересован (клиент ловит выгоду).
- Отток-предупреждение → **персональная забота вместо спама**: «давно не виделись» приходит в нужный момент, не раньше и не позже.
- Прогноз свободных окон → MAYA в чате честнее советует «лучше во вторник, будет свободнее и спокойнее».

## 5. Архитектура (как ложится на текущий стек)

Ключевой принцип: **YClients — не база для прогноза**. Дёргать `get_company_records` на 2 года при каждом запросе медленно (пагинация 25 стр × прокси) и хрупко («истекла лицензия YClients» — известная гоча). Нужен **локальный накопитель временных рядов** в том же `barbershop.db`.

### Новые таблицы SQLite (`database.py`)

```sql
-- Ежедневный снапшот метрик салона (заполняется cron 23:30 + бэкфилл истории)
CREATE TABLE IF NOT EXISTS metrics_daily (
  d            TEXT PRIMARY KEY,        -- 'YYYY-MM-DD'
  gross        INTEGER NOT NULL,        -- валовая выручка (из transactions, sold_item_type=service)
  visits       INTEGER NOT NULL,        -- уникальные оплаченные записи
  avg_check    INTEGER NOT NULL,
  cash         INTEGER, card INTEGER,
  new_clients  INTEGER,                 -- первый визит за период
  weekday      INTEGER,                 -- 0=Пн..6=Вс (для сезонных профилей)
  is_holiday   INTEGER DEFAULT 0,
  raw_json     TEXT                     -- top_services и т.п. для гибкости
);

-- Снапшот загрузки на БУДУЩЕЕ (forward booking) — снимаем каждый день
-- "сколько уже забронировано на дату D по состоянию на дату snapshot_at"
CREATE TABLE IF NOT EXISTS booking_forward (
  snapshot_at  TEXT NOT NULL,           -- когда сняли
  target_date  TEXT NOT NULL,           -- на какой день
  booked_slots INTEGER, capacity_slots INTEGER,
  fill_pct     REAL,
  PRIMARY KEY (snapshot_at, target_date)
);

-- Загрузка по мастерам по дням (перегруз/недогруз)
CREATE TABLE IF NOT EXISTS master_load_daily (
  d TEXT, staff_id INTEGER, visits INTEGER, busy_minutes INTEGER, gross INTEGER,
  PRIMARY KEY (d, staff_id)
);

-- Персональный цикл клиента и отток (обезличенно: client_id из YClients — это РФ-сервис, не уходит в LLM)
CREATE TABLE IF NOT EXISTS client_cadence (
  client_id      INTEGER PRIMARY KEY,
  last_visit      TEXT,
  visits_count    INTEGER,
  avg_cycle_days  REAL,                 -- средний межвизитный интервал
  std_cycle_days  REAL,
  ltv_gross       INTEGER,
  usual_staff_id  INTEGER,
  churn_score     REAL,                 -- 0..1, считается ночью
  state           TEXT                  -- active / slipping / churned
);

-- Лог сформированных прогнозов и предупреждений (чтобы не дублировать алерты + измерять точность post-hoc)
CREATE TABLE IF NOT EXISTS forecast_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at TEXT, kind TEXT,           -- revenue/load/churn/seasonal/master_overload
  horizon_to TEXT, payload_json TEXT,
  predicted REAL, actual REAL,          -- actual дозаполняется потом → меряем MAPE
  alerted INTEGER DEFAULT 0, owner_ack INTEGER DEFAULT 0
);
```

### Новые модули Python

- **`forecasting.py`** (ядро, чистая статистика, без сети, тестируемо):

  - `recompute_cadence()` — пересчёт `client_cadence`/`churn_score` (раз в сутки).
  - `forecast_revenue(horizon)` — сезонная декомпозиция: базовый тренд (скользящее среднее по неделям) × **weekday-профиль** (медиана выручки по дню недели за 8-12 недель) × коэффициент текущей заполненности (`booking_forward`). Возвращает точку + интервал.

## 9. Приоритет: **P1**

- **Не P0**, потому что: критичный фундамент (накопитель метрик) ещё не построен, а холодный старт без бэкфилла даёт слабый прогноз первые недели — ценность отложена. Сначала логичнее закрыть P0-вещи (ротация секретов, операционная автономия).
- **Не P2**, потому что: это **главный дифференциатор «AI-директора»** из vision и сильнейший аргумент для SaaS-продажи («MAYA предупреждает заранее»). Реактивная аналитика уже есть — следующий честный шаг именно проактивность. Бэкфилл из YClients (2-3 года) даёт мгновенную базу без месяцев ожидания.

## 10. Пошаговый план внедрения

**MVP (3-4 недели):**

1. Добавить 5 таблиц в `database.py` (`metrics_daily`, `booking_forward`, `master_load_daily`, `client_cadence`, `forecast_log`) + хелперы записи/чтения.

5. `forecast_revenue("month")`: тренд (скользящее среднее 4-8 недель) × weekday-профиль (медиана по дню недели) × поправка на текущий forward fill. Интервал = ±1 std исторической ошибки. Юнит-тесты на синтетике + бэктест по истории (меряем MAPE, пишем в `forecast_log`).
6. `client_cadence`/churn: `state='slipping'` если `now - last_visit > avg_cycle × 1.5`, `'churned'` если `> ×3`. `churn_score` взвесить на LTV.

## Риски и ловушки (под наш стек)

1. **Малые данные = шум.** Один салон, ~15-30 визитов/день, высокая дисперсия по дням. → Прогноз держать на уровне **недели/недельных профилей**, не дней; всегда показывать интервал; «прогноз» формулировать как «тенденция/риск», а не точное число. Не обещать дневную точность.
2. **Холодный старт.** Без бэкфилла первые недели бесполезны. → Шаг 3 (бэкфилл 2 года из YClients) — обязателен в MVP, не опционален.
3. **«Истекла лицензия YClients» / падения API** (известная гоча). → Снапшоты делаются 1×/сутки и кэшируются локально; прогноз считается из `metrics_daily`, а не из живого YClients. Сбой снапшота не ломает прогноз (работаем на последних данных), логируем пропуск.
4. **Прокси-задержка LLM** для дайджеста. → Числа считаются локально мгновенно; LLM зовётся только для финальной формулировки 1×/день. Можно увести на YandexGPT (РФ, без прокси).
5. **Усталость от ложных алертов.** Если MAYA каждое утро кричит «спад!» — владелец перестанет читать. → Жёсткий дедуп через `forecast_log` + cooldown в `settings`; алерт только при выходе за исторический интервал (severity-порог), а не при любом колебании.
6. **Churn по `client_id` без имени.** Скоринг — на агрегатах (YClients, РФ); в реактивацию имя подставляется уже на стороне РФ-исполнителя, в LLM не уходит. Не сломать контур 152-ФЗ.
7. **WAL-БД в проде.** Бэкфилл и снапшоты пишут в живую `barbershop.db`. → Online-backup + integrity-check перед бэкфиллом, idемпотентность по PRIMARY KEY (`d`), dry-run — ровно по выученному паттерну импорта сертификатов.
8. **Соблазн «настоящего ML» сразу.** На одном салоне переобучится и даст хуже, чем медиана. → Сознательно держим простую статистику в MVP; ML — только P2/мультитенант, честно зафиксировано.
9. **Capacity для forward-fill** — YClients не отдаёт «ёмкость» одним полем. → Считать capacity из `get_staff_schedule` (число мастеров в смене × рабочие часы / средняя длительность услуги); приблизительно, но достаточно для тренда заполненности.

# МОДУЛЬ 9. AI АДМИНИСТРАТОР (ЗВОНКИ)

> MAYA как живой телефонный администратор: входящие + исходящие звонки на обычные мобильные/городские номера (PSTN), поверх уже работающего «мозга» Claude и YClients-инструментов.
>
> Сразу главный технический вывод, который определяет весь модуль: **готовый голосовой мост `realtime_bridge.py` для телефонии переиспользуем НЕ напрямую.** Он рассчитан на PCM16 24 kHz из браузерного WebSocket и ходит в OpenAI Realtime через РФ-прокси. Телефония даёт другой кодек (G.711 µ-law / Opus 8 kHz), другой транспорт (RTP/SIP, не WS), и — главное — **gpt-realtime по телефону не звонит**: он умеет только WS-аудио, а не SIP-сигнализацию. Поэтому Модуль 9 — это **новый медиаконтур**, который переиспользует из готового только архитектурный паттерн «realtime = уши+рот, Claude = мозг» и сам мозг `get_ai_response`.

---

## 1. Цель

Дать салону работающий телефонный канал, в котором MAYA:
- **принимает входящие** на номер салона (запись, перенос, отмена, «во сколько вы работаете», «сколько стоит фейд», статус брони) — без участия человека в 90%+ типовых обращений;
- **совершает исходящие** в трёх сценариях: (а) подтверждение записи за день/за 2 часа, (б) обзвон листа ожидания при освобождении слота, (в) реактивация уснувших клиентов / напоминание о визите — голосом, а не только SMS/Telegram-пушем;
- ведёт диалог теми же инструментами YClients и той же памятью, что текстовый/браузерный голос, с теми же RBAC/HITL/152-ФЗ гарантиями;
- **корректно эскалирует на человека** (переключение на телефон Стаса/мастера) там, где не уверена или клиент просит живого.

Нефункциональная цель — латентность «клиент договорил → MAYA начала отвечать» ≤ **1.2 с** по телефону (иначе разговор ощущается мёртвым), при том что Claude через РФ-прокси даёт 0.8–2.5 с до первого токена.

---

## 2. Польза владельцу салона

- **Не теряются заявки в нерабочее время и в часы пик.** Сейчас входящий звонок, когда мастер с клиентом, = упущенная запись. MAYA берёт 100% звонков 24/7.
- **Подтверждение записей голосом снижает no-show.** SMS/пуш игнорят; живой звонок «Подтверждаете завтра в 15:00?» с возможностью тут же перенести — другой conversion. Меньше пустых слотов = прямая выручка.
- **Лист ожидания закрывает дыры в расписании.** Освободился слот — MAYA за минуту обзвонила 3 человек из `slot_waitlist` голосом и закрыла окно, пока оно не остыло.
- **Ноль ФОТ на ресепшн.** Для SaaS-перспективы — это якорная фича, за которую салоны платят: «AI-администратор, который реально берёт трубку».
- Все звонки — в `tool_audit` и в GOD-режим «Деньги» (стоимость минуты в ИИ-бюджете).

## 3. Польза мастерам

- **Не отрывается от клиента на телефон.** Звонок не дёргает мастера в кресле.
- **Меньше «глухих» окон** — лист ожидания и подтверждения держат расписание плотным, а плотное расписание у нас = прямой доход мастера (50/60%).
- **Эскалация по делу:** если клиент хочет именно мастера (сложный кейс), MAYA переключит звонок или поставит callback-задачу, а не потеряет.

## 4. Польза клиентам

- **Можно просто позвонить и записаться**, как привыкли «старшие» клиенты, не открывая PWA/Telegram. Голос — самый низкий барьер.
- **Звонок берут мгновенно, без музыки и очереди**, в любое время.
- **Живой человеческий голос** (тот же тембр, что в PWA-голосе) — не «нажмите 1».
- **Перенос/отмена в одном звонке**, без переписки.

## 5. Архитектура — как ложится на текущий стек

### Ключевое решение по медиаконтуру (две дороги)

| | **Дорога A — РФ-нативная (Yandex SpeechKit + Voximplant)** | **Дорога B — мост SIP↔gpt-realtime через прокси** |
|---|---|---|
| STT/TTS | Yandex SpeechKit streaming (в РФ, без прокси, русские голоса, ~50–150 мс) | OpenAI realtime через РФ-прокси |
| Латентность | низкая и стабильная (всё в РФ) | +200–600 мс на прокси, дрожит |
| 152-ФЗ | чисто: аудио/ПД не покидают РФ | аудио (голос — биометрия) уходит за рубеж → **юридический блокер** |
| Сложность | надо самим клеить STT→Claude→TTS стриминг | realtime уже умеет дуплекс, но его надо «приземлить» на SIP-RTP |
| Стоимость | SpeechKit ~предсказуема в ₽ | realtime-audio дорогой + прокси-трафик |

**Рекомендация CTO: Дорога A — основная и единственная для прод.** Причина не только латентность, а 152-ФЗ: **запись телефонного разговора — это биометрия + ПД (имя/телефон звучат вслух), и гнать сырое аудио звонка в OpenAA за рубеж — это тот же класс риска, что снёс CutMatch.** В браузерном голосе пользователь явно жмёт кнопку и это его устройство; телефонный поток клиента, который просто позвонил, — гораздо более скользкая зона. Дорога B остаётся опциональным экспериментом для не-РФ тенантов SaaS в будущем, не для Ставрополя.

Итого медиапоток (Дорога A, входящий звонок):

```
PSTN ──> Voximplant (SIP-номер, VoxEngine-сценарий)
            │  audio stream (WebSocket из VoxEngine)
            ▼
   наш VPS  telephony_bridge.py  (новый, aiohttp WS-сервер :8090 за nginx/TLS)
            │  PCM ──▶ Yandex SpeechKit STT (streaming, gRPC, РФ)  ──▶ транскрипт
            │  транскрипт ──▶ get_ai_response(history, chat_id)   ← СУЩЕСТВУЮЩИЙ МОЗГ
            │  ответ Claude ──▶ Yandex SpeechKit TTS (streaming)  ──▶ PCM
            ▼
   обратно в Voximplant ──> PSTN (клиент слышит MAYA)
```

**Внешние:**
- **Voximplant** — SIP-номер РФ + VoxEngine (JS-сценарий звонка) + Management API для исходящих + WebSocket-стриминг медиа на наш VPS. РФ-присутствие есть, геоблок не мешает. - `end_call(summary)` — корректно завершить, записать `outcome`.
- `confirm_or_reschedule(record_id, action)` — узкий инструмент сценария подтверждения (поверх существующего неразрушающего PUT `record/{company}/{id}`).

## 9. Приоритет

**P1 — но расщеплённый:**

## Риски и ловушки (этого модуля, на нашем стеке)

1. **Латентность убивает телефонный разговор.** В PWA-голосе пауза терпима, в телефоне 2 с тишины = «алло?». Связка SpeechKit(РФ) + Claude(прокси, 0.8–2.5 с) опасна. Обход: Haiku, prompt-caching, обязательный filler («секунду, смотрю…») как в `realtime_bridge`, TTS-стриминг по первой же фразе, режим выживания на YandexGPT если прокси лёг.
2. **152-ФЗ и биометрия (главный юр-риск).** Запись звонка = биометрия + голос ПД. Нельзя слать аудио за рубеж (это снесло CutMatch). Обход: всё аудио только SpeechKit+VPS, в Claude — только `redact_pii(transcript)`; голосовое согласие на запись в начале; записи лежат локально на VPS, не в облако; в `phone_calls.phone` — ПД только на VPS (как `barbershop.db`).
3. **Тихие часы и спам-обзвон.** Исходящий в 23:00 = жалоба + репутация. Обход: жёсткие `not_before`/тихие часы в `_outbound_call_job`, `max_attempts=2`, звонок только при `has_marketing_consent`, лёгкий отказ «больше не звонить».
4. **Эхо/barge-in по PSTN сложнее, чем в браузере.** Серверный полудуплекс из готового кода спасает на MVP, но «перебить MAYA» по телефону потребует реального AEC/VAD на стороне Voximplant. Обход: MVP полудуплексом, barge-in — отдельной фазой с тестами на живой линии.
5. **gpt-realtime не звонит по PSTN** — соблазн «переиспользовать как есть» приведёт в тупик. Зафиксировано: realtime не делает SIP; телефонный медиаконтур строится заново на SpeechKit.
6. **Voximplant биллинг и обрывы.** Незакрытая VoxEngine-сессия = утечка минут/денег. Обход: жёсткие таймауты сессии, `end_call`/таймер тишины, сверка `phone_calls.duration_sec` с vox-webhook, лимит ₽/день в GOD-режиме «Деньги».
7. **SQLite + параллельные звонки.** WAL держит читателей, но при росте конкуренции записи (несколько одновременных звонков) — узкое место. Обход: писать `call_turns` батчами/после хода, не на каждый чанк; на SaaS-масштабе — миграция этого контура на Postgres (он уже есть в `saas_blueprint`).
8. **Ошибочная запись/перенос «на слух».** STT перепутал «вторник/среда» → MAYA перенесла не туда. Обход: обязательное голосовое подтверждение перед любым write в YClients («Записываю на среду, 15:00, верно?»), HITL-тиринг как на деньгах, неразрушающий PUT (откат возможен).

## 3. MVP (4–8 недель) — максимум ценности, минимум риска

Цель MVP: **закрыть юр-дыры + довести почти-готовое до прода + дать первую «магию причинности».** Никакого нового медиаконтура, никаких внешних оплат.

| Входит в MVP | Откуда | Зачем |
|---|---|---|
| **Ротация секретов + env** | SECURITY_REMEDIATION | Открытый долг, блокирует SaaS и git. Дёшево, критично. |
| **Закрытие CutMatch** | M6 Фаза 0 (S, часы) | Биометрия в OpenAI = нарушение сейчас. Жёсткий гейт + аудит путей (LC_ALL=UTF-8!). |
| **Голос: reconnect+метрики+TTS-Telegram+rate-limit** | M1 P0+P0 (M+S) | Чинит уже-работающую дорогую фичу; расширяет голос на Telegram почти бесплатно. |
| **Общий ETL-слой `kpi_daily`/`metrics_daily` + backfill 90д** | M2/M8 фундамент (M) | Разовая инвестиция, на ней стоят 3 модуля. Снижает нагрузку на YClients. |
| **MAYA KPI: `kpi_engine` + `explain_kpi` в god-watch** | M2 MVP (L) | Превращает «выручка −12%» в «−12%, потому что Иван −18ч». Это разница между таблицей и директором. Read-only, ПД-чисто, без HITL — низкий риск. |

**Результат MVP:** правовые мины обезврежены; голос стабилен и звучит «как ChatGPT»; владелец каждое утро получает не цифру, а **причину** — главный вау-эффект «AI-директора» при минимальном риске (всё read-only, на готовом фундаменте, без внешних счетов).

## 4. V2 (после MVP, ~+8-10 нед) — «AI-директор зарабатывает деньги»

- **AI-Директор (M4):** утренний брифинг → 3-5 рекомендаций с ₽-эффектом → **действие в один тап** (вернуть N клиентов, сменить цену услуги через YClients под HITL). Severity считает Python, Claude формулирует.
- **AI-Маркетолог (M5):** `consent.py` (юр-фундамент) → RFM/churn-сегменты → Claude-офферы (шаблон с `{name}`, подстановка ПОСЛЕ LLM) → кампании Telegram/Push (бесплатно)→SMS → атрибуция с **holdout-группой** (честный uplift, не валовая выручка).
- **MAYA BI (M3):** разговорный «почему упала выручка в мае» с waterfall-декомпозицией, прогноз пунктиром, личный кабинет мастера. Claude выбирает метрику из закрытого enum — **не пишет SQL**.

V2 — это переход от «информирует» к «зарабатывает»: возврат клиентов и догрузка окон окупаются прямыми деньгами. Главный SaaS-аргумент.

## 5. V3 (~+12-15 нед) — проактивность, команда, телефония, SaaS

- **AI-Прогноз (M8):** time-series на накопленном слое — предупреждение о спаде/перегрузе/оттоке ЗА дни-недели. Честно: статистика малых данных + reasoning, не «ML» (ML только на мультитенанте).
- **AI-Тренер (M7):** база знаний 2.0 + Claude-генерация тестов (owner ревьюит) + скоринг (детерминир.) + KPI-связка «слабая услуга → модуль обучения». Удержание мастеров.
- **AI-Фото-консультант (M6):** легальный — on-device MediaPipe FaceMesh (фото не уходит) + Claude по тексту-геометрии; примерка опционально на Kandinsky/YandexART (РФ).
- **AI-Звонки (M9):** Voximplant+SpeechKit, исходящие подтверждения (режут no-show) → входящий приём. Аудио только в РФ. Самый дорогой модуль.
- **SaaS:** мультитенант, аналитика → Postgres, гейтинг фич по `plan_catalog.py`.

## 7. Самые дорогие функции

**По стоимости разработки (человеко-недели):**
1. **M9 Телефония — XL, 8-12 нед.** Новый медиаконтур (SpeechKit+Voximplant+SIP), полевая отладка латентности/эха. Самый тяжёлый.
2. **M5 Маркетолог — L-XL, 7-9 нед.** 6 модулей + юр-контур согласий + атрибуция с holdout.
3. **M7 Тренер — L, 7-9 нед.** База 2.0 + тесты + прогресс + KPI + PWA-вкладка в монолите.
4. **M2 KPI — L-XL, 6-7 нед.** Variance-декомпозиция — математическое сердце.
5. **M3 BI — L, 5-7 нед.** ETL + семантика + дашборды (SVG руками) + прогноз.

**По операционным $/мес:**
- **M9 Звонки — высший.** Минуты Voximplant + SpeechKit STT+TTS + Claude/звонок. Лимит ₽/день в GOD «Деньги» обязателен.
- **M1 Голос Контур А — высокий.** Realtime аудио-токены дороги (ставки «приблизительные»). Лимит конкурентных сессий + дефолт на Yandex для массовых сценариев.
- **M6 Фото опция B/C — средний-высокий.** GigaChat-vision дёшево; self-host GPU $150-400/мес (только на SaaS-масштабе).
- **Дёшево (~$1-5/мес):** M2/M3/M4/M7/M8 — числа считает Python, LLM только вербализует обезличенные агрегаты, вызовов мало.

**Главный вывод CTO:** ядро MAYA уже архитектурно верное (не тащить LangChain, не переписывать голос). 80% ценности достигается тремя разовыми инвестициями: **(1) обезвредить правовые мины** (секреты, CutMatch), **(2) построить общий материализованный ETL-слой** (на нём стоят 5 из 9 модулей), **(3) добить голос до прода**. Дальше — наслаивать агентов на готовый tool-loop, где Python считает, а Claude говорит. Это даёт дешёвую разработку, ПД-чистоту, устойчивость к флапу прокси и прямой путь к SaaS.
